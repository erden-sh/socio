# OpenBot computer services

Socio builds the computer service and supervisor from CopilotKit/OpenBot revision `b6932d31a8d6e7896c15139dfc27a6c6911deb27` (MIT). Their source is downloaded by BuildKit from the pinned Git context; it is not resolved from a moving branch or a `latest` image.

The supervisor keeps its narrow ensure/stop/reset/list implementation and resource ownership checks. Its image omits the unused SPIRE CLI, and applies fail-closed patches ([harden-supervisor.mjs](harden-supervisor.mjs)):

- Child environment construction: each computer receives `HMAC-SHA256(COMPUTER_TOKEN, "company-brain-computer:" + dotId)` instead of the master token. The application uses the same derivation. No supervisor token, model key, or master computer token is forwarded to a computer.
- Destroy: `POST /computers/:botId/destroy` removes a purged socio's computer for good, its container and its profile, workspace and private volumes ([computer-destroy.mjs](computer-destroy.mjs)), each only when its labels say this supervisor and namespace made it for that Bot. OpenBot's `reset` keeps the workspace and private volumes; this is for the operator purge (`purge-cli.ts`), which calls it after the purge commits. Removing what is already gone is fine.
- Resource readings (CB-197): `GET /computers/:botId/stats` reads one owned, running computer's CPU and memory ([resource-stats.mjs](resource-stats.mjs)). It no longer sizes volumes: Docker's `df` walks every volume on the host and took over 45 s on a busy host, so `volumeBytes` is always `null` here. The image also carries the computers' read-only disk usage proxy ([disk-usage-proxy.mjs](disk-usage-proxy.mjs)), which runs as its own service and is the only place that reads `df` (see [computer setup](../../docs/COMPUTERS.md#disk-usage-cb-197)).
- Computer containers (CB-125): each is created with an init process (`HostConfig.Init`), which reaps the processes Chromium leaves behind; without it PID 1 is `bun src/index.ts` and zombies pile up. Its healthcheck also fails when the computer reports `browserState: "stuck"`, and `GET /computers` reports each computer's Docker `health` (`starting`, `healthy` or `unhealthy`). The app fails browser calls at once for a computer reported `unhealthy`.
- Coding sandboxes (CB-239, dark): `/sandboxes` routes from [coding-sandbox.mjs](coding-sandbox.mjs), behind the same token. One container and one internal network per coding session from a spec fixed in code (no image, mount, capability or command in a request), inspected after each create and removed unless it matches, detached execs from a fixed set, and a start-up egress self-test in a canary sandbox. They use their own labels (`socio.coding.*`), so the computer listing never shows them. Off until `CODING_SANDBOX_IMAGE` names the `socio-coding` image by digest; see [the coding sandbox notes](../coding/README.md).

The computer image is the upstream `agent-computer` image (`company-brain-computer:b6932d3`) with the Git CLI (CB-130) and one fail-closed patch on top ([computer.Dockerfile](computer.Dockerfile), [harden-computer.mjs](harden-computer.mjs), helpers in [browser-guard.ts](browser-guard.ts)), tagged `company-brain-computer:b6932d3-isolated-v2` (CB-125). Upstream waits on a browser close with no time limit, and every later page request waits on that close first, so a Chromium that died without Playwright noticing left every snapshot and screenshot hanging until the container restarted. The patch:

- gives a close 10 s, then kills the browser's process group, so a stop, the idle sweep, the cap and shutdown always finish;
- has a page request check that a running browser answers before reusing it: a cheap evaluate on the page (1 s), and when the page is busy running its own script, the browser process itself over CDP (`Browser.getVersion`, 5 s). A busy page is reused as it is; one that disconnected, closed or crashed is dropped, and a browser that does not answer is replaced by killing its process group (checked against the start time recorded at launch, so a reused pid is never killed). A page request never waits more than 30 s on a close in progress, but always waits for a reset to finish deleting the profile, and a launch is given 60 s;
- adds `browserState` to `/health`: `stopped`, `starting`, `running`, `closing`, or `stuck` for a close pending over 20 s or a launch over 45 s. The image's healthcheck fails on `stuck`.
- answers `GET /screenshot?type=jpeg&quality=80` with a JPEG at that quality (30 to 95, 80 when unreadable) instead of the PNG (CB-157). The app asks for it for a socio's screenshots; without `type=jpeg` it is the PNG, as upstream. Rebuild the image under the same tag to get it; an older image ignores the query and sends PNGs, which the app also takes.

If a pinned upstream line changes, its patch refuses to build. Upgrades require reviewing the API contracts, ownership/volume behavior, and this patch together. On the next ensure request after a master-token change, the pinned supervisor replaces owned containers with the new credential while retaining their volumes. Do not delete profile or workspace volumes during normal updates.

See [computer setup](../../docs/COMPUTERS.md). OpenBot's MIT license is included in [LICENSE.openbot](LICENSE.openbot).

## Command isolation implementation (CB-227)

The new `principal-runtime.ts` and `principal-worker.ts` establish the Linux boundary for people, apps and jobs. The isolated computer image and matching supervisor integrate them; the application refuses shell/file operations on older images.

The service allocates stable numeric UIDs from a root-owned registry in a dedicated private volume. Each principal has a private home with mode 0700; files default to 0600. File operations and commands run after `setpriv` clears supplementary groups, drops to that UID and the shared GID, and applies no-new-privileges. Credentials travel to the worker through stdin, rather than its arguments or process environment. The worker may hand command variables to its own child, whose environment other UIDs cannot read.

The private volume root is 0755 so Bun 1.3 can resolve package scripts in private projects. This reveals only the fixed `control` and `homes` directory names: `homes` remains 0711, each principal home 0700, `control` 0700 and its UID registry 0600. Other principals cannot enumerate home names, read the registry, or enter another principal’s home.

The existing workspace remains an explicit `shared/` location. Its root is upstream's `WORKSPACE_DIR` (`/workspace` when unset, as Socio leaves it), which the patch keeps reading and requires to be a root-owned directory. File-tool writes there give the shared group access; shell commands keep a private umask and must deliberately set permissions when sharing a file. Apps and jobs get their own principals, separate from their owner. The UID registry must be retained and backed up with the private homes: missing, malformed, duplicate or stale mappings fail closed rather than reassigning an old UID.

The computer service needs only CHOWN, SETUID, SETGID and KILL in addition to dropping every other capability; unprivileged workers have no effective capabilities. The service must use one allocator instance per computer. Its private volume and shared workspace are separate mount roots. The supervisor retains the legacy workspace and browser profile volumes, and creates a third private volume for the UID registry and homes. Existing app source remains under shared/ while credentials and logs move into the app’s private home. Back up and restore the entire private volume together; never merge homes from one snapshot with a registry from another. Normal stop, replacement and browser reset retain this volume. An old computer image cannot safely serve the new application: upgrade the supervisor and computer image before the application.

Run the real kernel checks with the already built pinned computer image:

```sh
node scripts/smoke-computer-isolation.mjs
```

`COMPUTER_ISOLATION_TEST_IMAGE` can name a candidate computer image. This creates only a disposable container with no network, no ports, and no persistent volume; the candidate code is mounted read-only. It checks Bun package scripts in a private project, principal-name and registry denial, concurrent `/proc` and private-file denial, app/job separation, explicit sharing, symlink/traversal refusal, cancellation, setuid privilege refusal, stable UID reuse after restart, and missing/corrupt/stale-registry refusal. These checks prove the kernel boundary. Run `node scripts/smoke-computer-api-isolation.mjs` against the built candidate image to check authenticated HTTP dispatch, missing-identity refusal, private files and explicit sharing. Production acceptance still requires separate live application checks.
