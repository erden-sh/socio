# Socio ontology

An [Erden](https://erden.sh) project that describes Socio twice: its product domain (what a workspace, a socio, a room or a page is) and its code (packages, apps, server features and client modules), with a knowledge graph of this repository that links the two.

| Path                  | Contents                                                                                                                                      |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `ontology.ttl`        | The ontology's header                                                                                                                         |
| `modules/domain.ttl`  | Product concepts as OWL classes and properties, with definitions and the personal data each holds                                             |
| `modules/audit.ttl`   | The vocabulary for cross-file facts: mentions of paths, settings, flags, routes, tags and tables, each with its file and line                 |
| `modules/code.ttl`    | The code vocabulary: `Package`, `App`, `ServerFeature`, `Contract`, `ClientModule`, `partOf`, `dependsOn`, `implementsConcept`, `featureRank` |
| `data/socio.ttl`      | Socio as a project: its publisher, repository and license (hand-written)                                                                      |
| `data/repo.ttl`       | The repository's structure and the tables that hold personal data, generated by `scripts/build-repo-graph.mjs`                                |
| `audit/facts.ttl`     | Cross-file facts for the checks, generated by the same script; not committed                                                                  |
| `shapes.ttl`          | SHACL shapes the graph must meet                                                                                                              |
| `queries/*.rq`        | Competency questions `erden check` runs                                                                                                       |
| `queries/checks/*.rq` | Checks for problems across files that the compiler, linters and tests can't see                                                               |

## Reused layers

It reuses public layers instead of inventing their terms:

- **PROV-O:** socios and service accounts are software agents; work cycles, turns, coding sessions and audit entries are activities.
- **FOAF:** a person is a `foaf:Person`, a group a `foaf:Group`, a page a `foaf:Document`.
- **W3C Organization:** workspace roles are `org:Role`s; the publisher is an `org:FormalOrganization`.
- **DCAT:** a dataset is a `dcat:Dataset`.
- **DPV:** the personal data categories each concept holds.
- **ODRL:** the Sustainable Use License's grant and limits, as a policy.
- **SPDX:** a workspace package is an `spdx:Package`.
- **Dublin Core terms and SKOS:** titles, descriptions, licenses and definitions.
- **Schema.org:** apps are `schema:SoftwareApplication`s; Socio itself is `schema:SoftwareSourceCode`.

## Use it

The Erden CLI is a dev dependency of the repository (`@erden-sh/cli`, pinned), so `pnpm install` brings it, and `pnpm exec erden` runs it. There's no build for Intel Macs; there, install it some other way from [erden.sh](https://erden.sh/docs/getting-started/install-the-cli).

From the repository root:

```sh
pnpm ontology:graph    # regenerate data/repo.ttl from the tree
pnpm ontology:check    # reason, validate the shapes and run the competency questions
```

`erden install ontology` fetches the layers `erden.lock` pins. Regenerate the graph after adding a package, a server feature or a client module, and commit `data/repo.ttl` with the change. The concepts each feature implements are kept by hand in `FEATURE_CONCEPTS` in the script.

## Audit

`queries/checks/` holds checks for problems that span files: paths in comments and docs that name no file, environment variables read but never declared or documented (and the reverse), feature flags defined and never read, client calls and documented routes no server code registers, contract tags no layer provides, imports against the feature order, and tables holding personal data with no way to delete it. Each file's header says what it finds and why static tools miss it. A check expects 0 rows.

`erden check` runs the three that need only `data/`: `features-against-order.rq`, `personal-data-without-deletion.rq` and `personal-data-unmapped.rq`. The rest read `audit/facts.ttl`, which is about 100,000 statements: over Erden's reasoner request ceiling, and Erden runs SPARQL only as competency questions over what it reasons. Run them with any SPARQL 1.1 engine over `ontology.ttl`, `modules/`, `data/` and `audit/facts.ttl`. For example, with Python's rdflib (not a dependency of this repository):

```sh
pnpm ontology:graph
python3 - ontology ontology/queries/checks/*.rq <<'PY'
import glob, sys
from rdflib import Graph
root, *queries = sys.argv[1:]
graph = Graph()
for path in [f'{root}/ontology.ttl', *glob.glob(f'{root}/modules/*.ttl'), *glob.glob(f'{root}/data/*.ttl'), f'{root}/audit/facts.ttl']:
    graph.parse(path)
for query in queries:
    rows = list(graph.query(open(query).read()))
    print(f'{query}: {len(rows)}')
    for row in rows:
        print('  ', *row)
PY
```
