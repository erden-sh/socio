# Operations analytics store (CB-186)

The Operations dashboard (CB-164) reads its numbers from a DuckDB file of derived data, `analytics/ops.duckdb` next to the database (`/data/analytics/` in the stack). SQLite stays the system of record: everything in the file is copied from it by the ETL (CB-187), so the file can always be rebuilt and is not backed up.

One process owns the file: the analytics process, `src/server/operations/analytics/analytics-main.ts`, in the app's image. The app never runs analytics SQL on its own event loop; it asks the analytics process through `AnalyticsClient` (`platform.analytics`), with zod-typed requests and answers (`analytics/ipc.ts`, and the queries in `operations/domain/ops-queries.ts`).

## Modes

`OPS_ANALYTICS_MODE` picks one. It is env-only, a deployment choice; Health and `setup().analytics` show the mode and state.

|                 | `child` (default)                                                                                                                                        | `service`                                                                                               |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| For             | Development, single-container installs                                                                                                                   | The stack                                                                                               |
| Runs as         | Forked by the app. Its PID is recorded, it is stopped by that PID only, restarted with backoff (1 s, doubling to 60 s). It stops when the app goes away. | `socio-analytics`, one replica, `analytics-main.js`                                                     |
| Transport       | IPC                                                                                                                                                      | `POST /v1/rpc` on the internal network, `Authorization: Bearer <OPS_ANALYTICS_SECRET>`; `/healthz` open |
| Environment     | None of the app's: only the paths and its settings                                                                                                       | Its own, with the secret from a Docker secret                                                           |
| Memory, crashes | Inside the app task's limit                                                                                                                              | Its own limit; isolated                                                                                 |

`off` runs none; the dashboard then has no analytics.

## Safety

- DuckDB is pinned exactly (`@duckdb/node-api` 2.0.0-r.1, DuckDB 2.0.0 LTS) and opened with `autoinstall_known_extensions=false`, `autoload_known_extensions=false`, community and unsigned extensions off, `enable_external_access=false` (no `read_csv`, `ATTACH`, `COPY` or HTTP) and `lock_configuration=true`. It never reaches the network or a file but its own.
- DuckDB's `sqlite` extension is never used: it bundles a second SQLite, which can drop the app's locks and corrupt the database. The analytics process reads SQLite through its own `node:sqlite` connection, read-only and `query_only`, in short batches.
- Limits: `memoryMb` (512) and `threads` (2), with a temp spill directory (`analytics/tmp`) capped at 2 GB. The env sets the defaults (`OPS_ANALYTICS_MEMORY_MB`, `OPS_ANALYTICS_THREADS`, `OPS_ETL_EVERY_SECONDS`); what an admin saves under `settings.operations.analytics` wins, and the process reopens DuckDB with it at its next ETL cycle.
- Answers are cached 60 s per query and params; a query over 500 ms is logged as `ops slow query`.

## One writer

DuckDB allows one writing process per file. The analytics process holds `analytics/ops.lock` (a DuckDB file of its own) for its whole life and touches nothing in the directory before it has it. A second process waits, trying again every 10 s (`OPS_ANALYTICS_LOCK_RETRY_MS`), and shows **Analytics starting**:

- **child mode, blue/green (CB-108):** the new task's child waits until the old task's child stops.
- **service mode:** one replica with `update_config.order: stop-first`, so the old one lets go before the new one starts; both app colors talk to the one service.

The lock is a POSIX file lock: it needs the data volume on a local disk, not NFS.

## Rebuild

The file is rebuilt from SQLite when it is missing, can't be read (it is moved to `ops.duckdb.corrupt` first), or has another version: `ANALYTICS_SCHEMA_VERSION`, `ETL_VERSION` (`analytics/steps.ts`) or the DuckDB version. An admin's **Rebuild analytics** (the `rebuild` request) does the same.

A rebuild builds `ops.duckdb.next` with a pause between batches, and Operations shows **Rebuilding n%**. An admin's rebuild of a current file keeps answering from it meanwhile; a file of another version (after an upgrade that bumps a version) is never queried, since its tables may not be the ones the queries read: queries answer "not ready", and the dashboard shows the rebuild instead of numbers. When it has caught up it is checkpointed and swapped in, with queries held for the moment of the swap. During a rebuild two DuckDB files are open, each up to `memoryMb`: size the service's memory limit for both.

## The ETL (CB-187)

The analytics process copies the turns into DuckDB itself, every `etlEverySeconds` (60) and soon after each finished turn (the app sends a fire-and-forget nudge after the turn, never on its path). It reads SQLite through the `SourceReader` port (`operations/etl/source-reader.ts`; the SQLite adapter is `operations/infra/sqlite/source-reader.ts`), each read one statement or one short read transaction of at most 500 rows and about 8 MB of stored events (a bigger turn is read alone; the child shares the app task's memory), so the app's writer and Litestream's checkpoint are never held up. The steps are in `operations/analytics/steps.ts`; each batch and its watermark (`etl_state`) commit in one DuckDB transaction, so a crash loses nothing and repeats nothing.

| Step          | Reads                                                                                                  | Watermark                                                                                                                               | Writes                                                                                             |
| ------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `agent_runs`  | `agent_runs` by `seq`, with the chat's socio and owner                                                 | `{"seq":N,"running":[…]}`: every turn up to `seq` read; the running ones are read again, once the scan has caught up, until they finish | `f_turn`, `f_message`, `f_tool`, `f_participant`, and the rollups of the hours and days it touched |
| `dimensions`  | `users`, `dots`, `spaces`, `thread_bindings`, whole                                                    | a hash of what it read: written only when it changed                                                                                    | `d_person`, `d_socio`, `d_space`, `d_chat`, `d_source`                                             |
| `taxonomy`    | the store                                                                                              | the `TAXONOMY_VERSION` last applied                                                                                                     | the failure categories of `f_turn` and `f_tool` (CB-189), when the rules changed                   |
| `cost`        | prices, cost pools, readings and backends, whole                                                       | `{"hash":…,"hour":…}`: the inputs priced with, and the hour reached                                                                     | `f_turn`'s cost columns and `f_pool_hour` (CB-195, CB-196; see Cost below)                         |
| `work_cycles` | `work_cycles` by `(startedAt, id)` (index `work_cycles_started`, cycles 2), never the message or tools | `{"at":…,"id":…,"open":[…]}`: a cycle not ended is read again until it ends                                                             | `f_cycle` (CB-218; see Rooms below)                                                                |
| `issues`      | `issues` (the board), whole, 500 rows a statement                                                      | a hash of what it read: written only when it changed                                                                                    | `f_issue`                                                                                          |
| `retention`   | the store                                                                                              | the last cutoff                                                                                                                         | drops facts and rollups older than `factDays`                                                      |

Writes are idempotent: a batch deletes the facts of the turns it read (by `seq`) and appends them again, and recomputes whole buckets of the rollups. After downtime the ETL simply carries on from its watermarks. A rebuild reads every turn once and gives the same store.

**Facts.** Times are ms; no column is called `at` (a DuckDB keyword).

- `f_turn`: who and where (`run_id`, `thread_id`, `socio_id`, `source`, `trigger_kind`, `trigger_id`, `attribution`), outcome (`status`, `end_reason`, `failure_code`), timing (`received_at`, `started_at`, `finished_at`, `rounds`), tokens (`input_tokens`, `output_tokens`, `cached_tokens`, `reasoning_tokens`, `reasoning_kind` summary, raw, hidden, none, mixed or unknown, `reasoning_tokens_reported`), and work (`model`, `backend_key`, `tool_calls`, `tool_errors`, `tool_refusals`, `approval_waits`, `person_waits`, `retries`, `fallback_reason`), and the failure taxonomy's `failure_category` and `failure_rule` over the raw codes kept beside them (`last_stop`, the last round's stop, and `has_detail`, whether the run kept an operator detail, never its text).
- `f_message`: one row per message a turn added (`message_id`, `sent_at`, `author_kind` person, socio, schedule, agent or system, `author_id`, `attribution`, `chars`, `attachments`), with its turn's socio and source. Never content.
- `f_tool`: one row per tool call (`tool`, `outcome`, `code`, `started_at`, `duration_ms`, `round`, and its `category` and `category_rule`), with its turn's socio, source and trigger.
- `f_issue`: the board's items (`kind`, `priority`, `status`, `reporter_id`, `created_at`, `closed_at`, `deleted_at`), never their title or text.
- `f_participant`: per chat, every author, whoever started turns and each socio that ran them, with first and last time, messages, turns, and (CB-218) the turns that used a person's access (`acting`) and were billed to them (`paid`). Several people and several socios per chat.
- `f_cycle` (CB-218): one row per work cycle; see Rooms below.

**Who.** Turns that recorded who started them and wrote each message (CB-185's `trace.trigger` and `trace.messages`) are `attribution: exact`. Older ones are credited to the chat's owner, a person or a team (a shared Telegram topic), `owner`; in a room, whose owner is its placeholder `room:<id>`, to a person not known (no `trigger_id`, CB-213), except before a private chat became the room, when it was its one owner's, who converted it (CB-218); an automation's (a schedule) to the kind its source registers, `source`. Whose access a turn used and who paid are only what its work cycle recorded (CB-218, below).

**Sources** are an open registry (`packages/shared/src/runs/run-sources.ts`): a key, a label, `human` or `automation`, a channel, and optionally the table of its chats, for turns that don't record their source (Telegram's: `telegram_threads`). A module registers its own in a file of its own, imported by the module and by `operations/etl/sources.ts`. A key nobody registered still shows, as itself, with kind `unknown`.

**Drift.** `operations/etl/source-map.ts` lists every SQLite column the ETL reads, with its type; `tests/operations-etl.test.ts` fails when the modules' migrations rename, drop or retype one.

**Rollups.** `r_hourly` and `r_daily` add up turns, failed turns, tokens and people's messages per bucket, socio, source and person, in the reporting time zone (`settings.operations.timeZone` over `OPS_TIME_ZONE`, UTC by default). DuckDB has no time zone rules offline, so `d_calendar` holds the zone's buckets, made in JS exactly as the Overview cuts them, and facts are bucketed with an ASOF join. When the time zone changes, the calendar and every rollup are made again from the facts. Hourly rollups are kept `hourlyDays` (30); daily ones go with the facts.

**Retention** (admin settings under `settings.operations.analytics`, env defaults): `factDays` (`OPS_FACT_DAYS`, 0: keep as long as the database keeps the turns) and `hourlyDays` (`OPS_HOURLY_DAYS`, 0: no hourly pruning). Hourly rollups are derived from retained facts, so a positive `factDays` still bounds their history. Resetting hourly retention to 0 restores older buckets from facts that remain.

**Queries** (`OPS_QUERIES`): `freshness` ("Data as of" per source), and CB-184's `OpsReader` methods, one query each, answering exactly what the method returns: `status`, `overview` (scope), `series` (scope and `metric`), `turns` (scope, `cursor`, `limit`). The Operations routes read them through `AnalyticsOpsReader` (`operations/infra/analytics/reader.ts`), which passes each method to `platform.analytics`; while the store can't answer it gives the client's health, null values and empty lists. With analytics off, the empty in-memory reader answers. Tiles and lists read the facts; a series reads the rollups for the buckets that lie whole inside the window and the facts for the rest, so the window's first and last hours, older hours and another time zone are exact too.

**Failure taxonomy (CB-189).** `packages/shared/src/failure-taxonomy.ts` sorts a failed turn, tool call or other piece of work into one of nine categories by rules over its codes, the first match winning: Stopped (not a failure), Permissions and approvals, Quotas and limits, Not available or not set up, Model provider, Other external services, Invalid input, Runtime error, and Unclassified, where generic codes (`tool_error`, a bare `failed` with an operator detail) are marked ambiguous for a classifier to label later. The ETL applies it as it copies each turn; bumping `TAXONOMY_VERSION` makes the `taxonomy` step re-run the rules over every distinct set of stored codes, with no rebuild. Reliability's queries (`reliability`, `failureSeries`, `failureBreakdown`, `failures`, `friction`, `issueVelocity`; `operations/infra/duckdb/reliability.ts`) read the facts; the board is small, so its velocity is counted in code (`domain/issue-velocity.ts`) the same way by both readers.

**Failure labels (CB-198).** What the rules leave Unclassified can be labeled. The app's `classify` module (`src/server/classify/`, with its own migrations) holds the labels, and the `labels` ETL step copies them in. The flow has three parts:

- **The seam.** `Classifier.decide(use, state, questions)` asks a closed question and `Classifier.extract(use, state, fields)` pulls typed fields. Each use (`failures`, `intent` and `themes` from CB-199, and `learning` from CB-200) has its own versioned label list, provider, threshold, daily cap and switch. The switch is off by default, and settings live in `settings.classify` over `CLASSIFY_FAILURES*`. The seam scrubs every text in the state with Learning's `scrub()` and clips it to 300 characters before any provider sees it. Providers are tried in this order: the use's own, then `self-hosted`, then `workspace`, then no answer. Only `workspace` ships: the default shared backend over Chat Completions, asked for one JSON object that is validated with zod. Every call is written to `classify_calls` with its outcome, tokens and cost, which is null when the provider doesn't report one.
- **Labels.** `classify_labels` is append-only, and the newest row for a subject wins. A subject is a turn (`idx` -1) or a tool call (its place in the trace). The module's one-minute tick reads finished turns by `seq` from a cursor and asks the model about each Unclassified part that has text: the run's operator detail, or the failed tool call's result. It makes at most 5 calls a tick and stays within the daily cap. A model answer is stored with the scrubbed input it was given. It is `applied` only when the model was at least as sure as the threshold and its provider version (`workspace:<model>/p<prompt version>`) has passed an evaluation at that threshold or a stricter one; otherwise it is a suggestion. An admin's relabel in Reliability (`PUT /api/classify/failures/:runId/label`) is always applied. Opening a failure's label panel (`GET /api/classify/failures/:runId`) shows the scrubbed text and is written to the access log as `failure-label`.
- **Golden set and evaluation.** The golden set is each subject's newest admin label. An evaluation (**Evaluate** in Operations → Settings, `POST /api/classify/uses/failures/evaluate`, or `pnpm run classify:eval -- --use=failures --provider=workspace`) gives every golden input to the provider again. It records per-label precision and recall and a confusion matrix in `classify_evals`. A version passes when the set has at least 20 labels and, out of at least 10 sure answers, the share that is right is at least the threshold. A pass then applies that version's earlier sure suggestions, as new rows.

| Step     | Reads                                                                          | Watermark           | Writes                                                                                                                                      |
| -------- | ------------------------------------------------------------------------------ | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `labels` | applied rows of `classify_labels` (`use = 'failures'`) by `seq`, never `input` | the last `seq` read | `f_label` (the label in force per `run_id` and `idx`), then the categories of `f_turn` and `f_tool` that are Unclassified or labeled before |

A label replaces a category only where the rules say Unclassified, so a rule that learns to sort a failure wins over its label. The labeled rule reads `label:admin` or `label:<provider>`. The runs step applies `f_label` to the turns it copies, and the taxonomy step applies it again after re-running the rules, so neither undoes a label. Stopped is never a label, so the failed-turn rollups don't change. CB-198 bumps `ETL_VERSION` to 7.

**Intent and themes (CB-199).** Two more uses of the seam label people's sessions, and Operations → Themes and Value's **Completion by intent** read them. Both follow the seam's rules: off by default (`settings.classify.intent` and `.themes` over `CLASSIFY_INTENT*` and `CLASSIFY_THEMES*`), a daily cap (300) and threshold (0.8 for intent, 0.7 for themes), scrubbing, only the `workspace` provider, and an evaluation on the golden set before a model's labels count.

- **Subjects.** A session is known by the turn that opened it: a turn a person started (from a `human` source, with words of their own in `RUN_STARTED`) after the chat was quiet for the session gap in force. The module's tick (`classify/sessions.ts`) reads turns by `seq` from a cursor per use, like failures. It waits until the session has three person messages or has ended (the gap passed), then sends the chat's title and those first three messages, each scrubbed and cut to 300 characters, and stores the answer as `classify_labels` with `runId` the opening turn and `idx` -1. At most 5 calls a tick per use, within the cap; a session is asked about once.
- **Intent** is `decide` over a list admins edit in Operations → Settings (`settings.classify.intent.labels`; the default is ask, write, analyze, automate, research, admin, other). Each list has its own `labelsVersion` (1 for the default, else a hash of the values and hints), so an edit starts a new golden set and needs a new evaluation; labels already given keep their value.
- **Themes** is `extract`: one to three topics of at most 48 characters (the model is told never to name people), an outcome hint (`resolved`, `unresolved`, `unclear`) and a confidence. The label is JSON `{ topics, outcome }`. In an evaluation, an answer is right when its outcome hint matches the admin's and a topic shares at least half its words (filler words aside) with one of the admin's.
- **Review.** Themes' Review card lists labeled sessions (`GET /api/classify/sessions?use=`, on the access log as `session-labels`) and opens one with its scrubbed text (`GET /api/classify/sessions/:runId`, logged as `session-label`); an admin's `PUT …/intent` or `…/themes` is applied at once and joins that use's golden set.

| Step             | Reads                                                                                                 | Watermark           | Writes                                                                                                       |
| ---------------- | ----------------------------------------------------------------------------------------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------ |
| `session_labels` | applied rows of `classify_labels` with `use` intent or themes by `seq`, the label only, never `input` | the last `seq` read | `f_intent` (`run_id`, `intent`), `f_theme` (`run_id`, `topic`, `topic_key`, `outcome`), newest per turn wins |

Queries cut sessions as Value does and give each the intent and themes of its earliest labeled turn (a turn is in a session when one of its messages is), so a new session gap needs no relabelling. `value` gains `intents` (sessions and outcomes per intent, no intent last); `themes` answers intents, themes (topics clustered by `topicKey`: lowercase words without accents, filler words or plurals, sorted) with sessions, people, outcomes, outcome hints, their intents and sessions per week of the reporting time zone. Both readers aggregate with the same code (`operations/themes/aggregate.ts`), and `tests/operations-themes.test.ts` holds them equal.

**Privacy.** Themes are counts, never content: a theme is named only when at least `THEMES_MIN_PEOPLE` (3) different people had sessions on it in the range and filters; the rest are counted as smaller themes and never named, so a view narrowed to one person names none (and is on the access log). `f_theme` holds only the topics, which are the model's few words from scrubbed text. Retention drops a turn's `f_intent` and `f_theme` rows with it. CB-199 bumps `ETL_VERSION` to 8.

**Learning on the seam (CB-200).** Learning's triage and checks are the seam's fourth use, `learning`, with the same rules: off by default (`settings.classify.learning` over `CLASSIFY_LEARNING*`; Operations → Settings → **Learning triage**), a daily cap (200) and threshold (0.9), scrubbing, only the `workspace` provider, every call in `classify_calls`, and an evaluation before its answers count. Off, Learning works exactly as before. On (`learning/triage.ts`):

- **Triage.** Each finished conversation in a container's new evidence gets one `decide` call, "does it show a procedure the team would repeat?" (`repeatable` or `one-off`), from its title and what people asked in it, never the replies, scrubbed and cut to 1,500 characters (`LEARNING_INPUT_CHARS`). The answer is a `classify_labels` row with `runId` the thread ID and `idx` -1, asked once per finish (call subject `thread:<id>@<finishedAt>`). Learning's one-minute tick triages up to 5 conversations; an analysis triages the rest of its batch first, under the cap. Threads whose label in force is one-off (an admin's, which stays in force until an admin changes it, however the model answers later; else the model's when sure and its version passed) are read but not sent: the run counts them as `skipped` and its cursor moves past them, so fewer transcripts leave the store. What isn't triaged (cap, no model) is sent as before.
- **Intent.** A conversation's intent is the applied CB-199 intent of its sessions. When one intent other than "other" has `INTENT_RECURRENCE` (5) sessions among a container's new conversations, an analysis starts with trigger `intent`, besides the fixed count of 15; a run that started after the newest of them blocks another until new evidence comes, as the threshold does.
- **Checks.** A proposal that passed Learning's own checks (valid call, not a rejected, revoked or published skill by name and body, evidence from the batch, the privacy patterns) gets two more calls: is it the same skill as one on the reviewed list (dropped as `model-duplicate` when sure and the version passed), and does it hold private details (dropped as `model-private` when sure, even before an evaluation: a second privacy check fails safe). Both reasons join `learning_runs.dropReasons`.
- **Golden set and review.** Admins label conversations on each container's **Triage** list in Learning (`PUT /api/learning/threads/:threadId/triage`, a signed-in admin only); that is the golden set **Evaluate** and `pnpm run classify:eval -- --use=learning` use. Learning's page shows the use's state, its last 24 hours of calls, tokens and cost, each conversation's score and intent, and each proposal's evidence with its triage.
- **Cost of the analysis itself.** The analysis's own Chat Completions call is not a seam call (it writes skills, not labels); the tokens and cost it reports are kept on its run (`learning_runs.inputTokens`, `outputTokens`, `costUsd`, learning migration 4, expand only) and shown on the run's line.

The ETL doesn't read `learning` labels (its steps filter on `use`), so no `ETL_VERSION` bump.

**Activity and Value (CB-190).** Four more steps copy what sessions' outcomes and the Value page need: `approval_audit` by `(createdAt, id)` with its request's chat (`f_approval`); page writes, pages made by `(createdAt, id)` and edits (one per kept revision, `page_revisions` by `id`; a socio's page tool records `dot:<id>` and no chat) (`f_space_write`). A page made is a socio's when a person approved its draft (`page_reviews`, with the chat), or when one of its chats owned by the page's `createdBy` ran `create_space_page` while the page was made (that tool records the chat's owner and no chat; the match takes the chat too, and runs again whenever such calls reach `f_tool`); otherwise it is the person's, with the chat a "Save as page" came from; and, read whole when a cheap fingerprint changes, `message_reactions` (`f_reaction`) and chats' memories (`f_memory`). Sessions are not stored: each query derives them from `f_message` with `LAG` over each chat (gap `settings.operations.sessionGapMinutes` over `OPS_SESSION_GAP_MINUTES`, 30), reading from a gap before the window, once per request into a temporary table, and their outcome by CB-164: completed when the last turn finished and a signal (thumbs up, approval executed, a page the socio wrote from the chat, or edited during the session, a memory kept) came within 24 hours; abandoned when nobody wrote for 24 hours after a failed, interrupted or stopped turn, an expired approval or a last reaction of down, retry or needs work; answered otherwise. People's activity is people's messages from sources the registry calls `human`. `MemoryOpsReader` implements the same definitions; `tests/operations-activity.test.ts` holds them equal for every filter, two gaps and another time zone, and `tests/operations-activity-perf.test.ts` measures them at 20,000 turns: about 350 ms at the 95th percentile on a quiet machine.

**Size.** At 50,000 turns over 90 days a rebuild takes about 22 s, and the Overview's queries answer in 73 ms at the 95th percentile (`tests/operations-etl-perf.test.ts`: the suite runs 5,000 turns, `OPS_PERF=1` the 50,000, and `OPS_PERF_REPORT=1` prints the numbers).

## Health (CB-192)

Operations → Health reads four more ETL steps' tables, and a few things live in the app.

| Step         | Reads                                                                                                         | Watermark                                                                                     | Writes                                                           |
| ------------ | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `agent_runs` | (as above) each turn's `trace.rounds`, without summaries                                                      | (as above)                                                                                    | `f_round`: model, time to first output, reasoning kind per round |
| `job_runs`   | `job_runs` by `(queuedAt, id)`, never their output                                                            | `{"at":…,"id":…,"open":[…]}`: queued, starting and running ones are read again until they end | `f_job_run`                                                      |
| `runs`       | schedules' runs (`runs` of tasks with a cadence or an interval) by `(startedAt, id)`                          | the same; running ones are read again                                                         | `f_task_run`, with `due_at` (CB-185)                             |
| `schedules`  | live schedules, goals, long runs with their job's name, whole; long runs' items counted while open or changed | a hash of what it wrote                                                                       | `s_schedule`, `s_goal`, `s_long_run`                             |

A schedule's state is worked out at the cycle's time (`scheduleState` in `packages/shared/src/operations/operations-health.ts`): `failing` (its last run failed), `paused`, `overdue` (its next time passed over 5 minutes ago), `ok`, or `stopped`. A goal is `stalled` while its schedule fails or is paused, or after 14 days with no change. A scheduled run is late when it starts over 5 minutes after it came due; runs from before CB-185 have no due time and are left out of lateness (Collection coverage says how many).

**Queries:** `health` (tokens by model, socio, person and reasoning kind; time to first output and tool times by model and tool; turn queue, job queue wait, computer wake and schedule lateness; schedules, goals, long runs and job runs; collection coverage; every ETL source's last run), `healthSeries` (a metric's p95 per bucket), and the cursor-paged `healthSchedules`, `healthRuns` and `healthLongRuns`. Percentiles are nearest rank (`quantile_disc`). Reasoning tokens are added up only within one reasoning kind, and only for turns whose model reported them apart; turns with no recorded kind are `unknown`, never folded into another. The source filter narrows turn, model and tool numbers; job runs, schedules, goals and long runs follow the socio, Space and person.

**Live** (`operations/live-health.ts`, in the app, not the store): the analytics process's mode and state, backups with the continuous copy and the restore drill (`BackupService.status()`). A source not run for three ETL cycles (at least 5 minutes) shows as stale.

## Knowledge, storage and capabilities (CB-191)

More steps, after CB-187's, read what the Knowledge and Capabilities pages show. They read through their own port (`operations/etl/knowledge-source.ts`, SQLite adapter `operations/infra/sqlite/knowledge-source.ts`) and never read page text, revision bodies, audit targets or details, search queries or the wording of capability requests: titles, lengths and counts only.

| Step                | Reads                                                                                                                                                                                                                                                   | Watermark                                | Writes                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- | ---------------------------------------------------------- |
| `pages`             | the live pages' keys from the covering index `pages_live_keys` (pages 8) each cycle; only added, edited, moved or deleted pages in full (their length), at most 500 a batch; `page_use` and `page_search_daily` whole                                   | hashes of `page_use` and the search days | `d_page`, `d_page_use`, `f_search_day`, `f_search_latency` |

## Grounding and report links (CB-194)

What socios read to answer is recorded as it is read, as references only: ids, a kind and a Space, never what a page, dataset or chat says. A turn's tools write `run_refs` (runs 5, the Runs module's table, on the runner's own connection) through `DotTurn.ref`, each reference once per turn (`UNIQUE(runId, kind, refId)`, the first read's time); a reference over 200 characters, or a write that fails, is skipped and never fails the tool.

| --------- | -------------------------------------------------------------------------------- | ---------- |
| `page`    | `read_space_page`                                                                | the page's |
| `search`  | `search_space_pages`: each page in the results it returned                       | the page's |

## Cost (CB-195, CB-196)

Operations → Cost prices every turn and shows what it cost by model, socio, person and backend, the turns with no price, self-hosted backends' cost pools with their idle capacity, and the prices behind them.

**Prices.** SQLite `model_prices` (operations 4) holds effective-dated prices per provider and model: US dollars per million tokens for input, cached input, output and (when billed apart) reasoning, `effectiveFrom`, `source` (`sync:<list>`, `catalog:<list>` or `admin`) and `fetchedAt`. A turn is priced at its provider's price for its model in force when it started: an admin's from its date onward (provider `*` holds for every provider), else the provider's own list's, else a community list's; a turn from before a model's first synced price takes that first price, an admin's never reaches back. Input includes cached tokens and output includes reasoning, as the providers report them. The provider is the backend's (`providerOf` its base URL: `openai`, `openrouter`, `azure`, `aws`, … or `self-hosted` for a private address); ChatGPT connections are `chatgpt`, which has no per-token price. Models are matched by name, then by `modelKey` (lowercase, no vendor prefix, date stamp or revision, letters and digits only).

**The price sync** (`operations/pricing/`) runs in the app, once a day per list (a failed list again after an hour), while its switch is on: an admin's choice in Operations → Settings over `OPS_PRICE_SYNC` (on in production images when unset, off in development; the change is written to `workspace_audit`). It downloads each list whole and keeps only the models in use (backends', bring-your-own kinds' and turns' models), storing a row only when a price changed. Lists that need an API key are not read (Together's: it comes through the community lists). The large lists are narrowed in the request: Azure Retail Prices to `serviceName eq 'Foundry Models' and armRegionName eq 'eastus2'` (global deployments over data zones over regional ones; batch, fine-tuning, audio and image meters skipped), the AWS Price List to Bedrock's offer for `us-east-1` (on-demand input, output and cache-read tokens).

| List                | Read from                                                                    |
| ------------------- | ---------------------------------------------------------------------------- |
| OpenRouter          | `https://openrouter.ai/api/v1/models`                                        |
| DeepInfra           | `https://api.deepinfra.com/v1/openai/models`                                 |
| Azure Retail Prices | `https://prices.azure.com/api/retail/prices?$filter=…` and its next pages    |
| AWS Price List      | `https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonBedrock/…`    |
| models.dev          | `https://models.dev/api.json`                                                |
| LiteLLM             | `https://raw.githubusercontent.com/BerriAI/litellm/main/model_prices_….json` |

Every request is a plain GET with `User-Agent: research-script/0.1` and `Accept: application/json`: no cookies, credentials, referrer or redirects, and nothing about the workspace, its people or the server. Only a list's own hosts over https are fetched (a next-page link elsewhere is refused) and a body stops at 64 MB. `OPS_PRICE_SYNC_URL` (an origin) reads every list from there instead, path and query kept: an offline mirror, or the loopback fake the tests use (`tests/fixtures/price-lists.ts`; the suite refuses egress). With the switch off no request is made; turning it off stops a run before its next list.

**Cost pools** (`cost_pools`, `cost_meter_readings`) are what self-hosted backends and subscriptions cost. A fixed pool costs `amount` per `period` (an average month is 365.25/12 days), or, with `depreciationMonths`, its `amount` written off in a straight line over those months from `startsAt`; a variable (metered) pool costs its readings, each the use since the one before (or since the pool started) at its unit price (else the pool's `amount`), spread evenly over that span. Each hour's cost goes to that hour's turns on the pool's backends (a shared backend's id, or `byo:<kind>` for subscriptions) by weighted tokens: uncached input 1, cached input 0.1, output 4, editable per pool. An hour without turns is idle capacity, so allocated plus idle is always the pool's cost. `gpu_seconds` allocation is in the schema for when a GPU meter exists; until then such a pool's cost all shows as idle. Pools over subscriptions (ChatGPT connections) are labeled estimates.

**The `cost` step** runs after `taxonomy`. It reads `model_prices`, `cost_pools`, `cost_meter_readings` and `cost_backends` whole: they are small. `cost_backends` is the app's copy of each backend's provider and model (refreshed every minute through inference's store; the analytics process never reads inference's tables or keys), kept with `removedAt` after a backend goes so its old turns stay priced. When their hash changes it prices every turn and pool hour again; otherwise only from the oldest turn not yet priced and the hour it last reached, so a new turn shares its hour with the turns already in it and idle hours accrue. It writes `f_turn`'s `cost_backend` (the backend it priced by: the trace's `backendId`, recorded from this release; for older turns the one shared backend serving the turn's model, else `shared`), `cost_usd`, `cost_basis` (`pool`, `price` or `none`: no price, the cost unknown and never counted as 0), `cost_source` (the price's origin) and `ref_cost_usd` (a pooled turn at the cheapest listed cloud price for its model), and `f_pool_hour` (`pool_id`, `hour_at`, `cost_usd`, `allocated_usd`, `turns`) from the first turn the store holds up to the current hour. Retention's `factDays` also cuts pool hours.

**Queries:** `cost` (totals with the period before, cost per bucket, by model, socio, person and backend with each backend's pooled cost and cloud reference, pools' cost, allocated and idle in the window, and the unpriced models) and `costModels` (the models turns used, for the sync). Turns follow the filters; pools are the workspace's. `/api/operations/cost` lists spend by person, so it is on the access log (`cost`). Prices, the switch and pools are under `/api/operations/pricing`, admins only, every change in `workspace_audit`.

## Rooms (CB-218)

Operations attributes a room's work without counting it twice, and a room's own people see its use when an admin lets them.

**Three counts, three meanings.** A **work cycle** (CB-211, `work_cycles`) is one person's message and everything it leads to: model rounds, tools, waits for approvals and, once CB-206 lands, handoffs to other socios. A **turn** (`agent_runs`, `f_turn`) is one socio's step of a cycle: the first, plus one per handoff (`hop` 0, 1, …). A **retry** of a model request is part of its turn (`retries`), never a turn of its own. So cycles ≤ turns, and per-socio execution is turns grouped by the socio that ran them.

**Attribution.** Each turn that recorded its cycle (`trace.cycle`) is credited to:

| Who               | Column                        | From                                                                                  |
| ----------------- | ----------------------------- | ------------------------------------------------------------------------------------- |
| Initiating person | `trigger_id`                  | `trace.trigger` (CB-185): the sender of the message                                   |
| Acting person     | `acting_id`                   | `trace.cycle.actingUserId`: whose access, data and subscription it used               |
| Payer             | `payer_kind`, `payer_id`      | `trace.cycle.billing`: `person` (the acting person's own subscription) or `workspace` |
| Room or chat      | `thread_id`, `container_kind` | `person` (a private chat), `team` (a Telegram topic) or `room`, as it was then        |
| Socio             | `socio_id`                    | `trace.cycle.dotId`, the socio that ran the step; else the chat's (the lead)          |
| Cycle             | `cycle_id`, `hop`             | `trace.cycle.id`, `.hop`                                                              |

In a room the initiator, the acting person and a person payer are one person; they are three columns because a schedule's turn, say, is started by the schedule but acts for its owner. `socio_id` is per turn, so several socios answering in one room (CB-206) need no schema change: until then it is the room's lead. A turn from before work cycles records none of it: `cycle_id`, `acting_id` and `payer_kind` are null and show as **Not recorded**, never filled in from the chat's owner. `container_kind` comes from the cycle's kind; without one, from the chat now, except that a turn before a room's `convertedAt` ran in the private chat it was (or the Telegram topic, for a room a topic became, CB-214). `d_chat.owner_kind` is `room` for a room, with its name in `d_chat.title`; a private chat's title is never copied.

**`f_cycle`** holds each cycle as its ledger counted it: `kind`, `initiator_kind`/`initiator_id`, `acting_id`, `socio_id` (its last step's), `payer_kind`/`payer_id`, `status`, `started_at`, `ended_at`, `elapsed_ms` (the time its steps ran; waits between steps, such as for an approval, left out), `steps`, `handoffs`, `tokens_used`, `cost_usd` and `cost_known` (null and false once any request reported no cost: unknown, never 0), the `token_limit` and `spend_limit` it started with, and `end_reason` (`completed`, `failed`, `stopped`, `interrupted`, `expired`, or the limit that stopped it: `deadline`, `tokens`, `handoffs`, `spend`). Never its message, dispatch key or the tools left running. Retention's `factDays` drops cycles by `started_at`.

**No double counting.** Cost and tokens are summed per turn (each turn's own `cost_usd` from the cost step, and its own tokens), never from `trace.cycle.tokens` or `.costUsd`, which are the cycle's running totals. A cycle is counted once however many of its steps the window holds (`count(DISTINCT cycle_id)`). Time has two numbers: **time working** (`elapsed_ms`, summed over ended cycles) and **start to end** (`ended_at - started_at`), which includes waits.

**Queries.** `cost` adds `byPayer` (key a person, `workspace`, or `''` for not recorded), `byRoom` (per room: turns, tokens, cost, unpriced turns, cycles, handoffs, cycles a limit stopped, people who started turns and socios that ran them, by `d_chat.title`) and `cycles` (the cycles with a step in the window and filters: how many, in rooms, steps, handoffs, stopped per limit, stopped by a person, spend unknown, time working and start to end). A cycle is in a window when one of its steps started in it. Both readers answer the same (`tests/operations-rooms.test.ts`, for every filter). The Cost page is on the access log as before (`cost`).

**Members' view (not the store).** A room's people read its use from the cycles' ledger in SQLite (`GET /api/rooms/:id/usage`, the room's **Members** panel), so it answers whatever the analytics process's state, and CB-211's enforcement never depends on the store. Room admins always see it; members only when Settings → General → Rooms → **Members see their room's use and limits** is on (`settings.rooms.budgetVisible` over `ROOMS_BUDGET_VISIBLE`, off by default), and otherwise get `usage_hidden` (403), for `GET /api/rooms/:id/limits` too; only the handoff limit, which is no budget data, is every member's (`GET /api/rooms/:id/limits/handoffs`). It shows the limits in force, the running or last cycle's time, tokens, handoffs and spend against them, and the last 24 hours' cycles, tokens and limit stops, only once `ROOM_USAGE_MIN_PEOPLE` (3, as Themes' `THEMES_MIN_PEOPLE`) people started cycles in them, so it never shows one person's use. Spend shows only for the workspace's models or the reader's own cycle: another member's own subscription reads **on the sender's own model subscription**, never an amount, and the day's total has no spend. Someone outside the room gets the unknown room's 404. A setting change applies to the next request; nothing is cached.

This release bumps `ETL_VERSION` to 9 (the store is rebuilt from SQLite after the upgrade) and migrates cycles 1→2 (an index, expand-only).

## Docker

The `analytics` target in the Dockerfile is the app image with the analytics process as its command, port 4340 and its health check. The stack can run the `app` image itself with the command and health check below, so no other image is built. DuckDB adds about 94 MB to the app image (its glibc binding; `prod-deps` drops the musl one pnpm also installs); the build fails above 120 MB, measured in `node_modules/.pnpm/@duckdb+*`, where pnpm keeps the files. The browser and apps runtime images leave it out: they copy `prod-deps-slim`, which deletes those files before they are copied, so no layer holds them.

## Resource history and retention (CB-193)

Operations → Health records server measurements every five minutes into SQLite `ops_samples` and `ops_samples_hourly`: process RSS/CPU, system load/free memory, data-volume capacity/free space, database pages/free list and WAL bytes. Daily measurements include local userdata size and dataset/file/media byte totals. Hourly aggregates track each metric’s actual observation time; missing, stale or unavailable measurements appear in Collection gaps. A Linux directory scan is bounded to 20,000 entries, two seconds and depth 64, follows no symlinks, and reports an unavailable size rather than a partial total when incomplete.

Admins and operators change retention and the sampling interval in Operations → Settings. Saved values override environment defaults; **Use server default** removes the saved override. Changes are recorded in `workspace_audit`. Sampling accepts whole minutes from 60 to 3600 seconds. Retention accepts whole days from 0 to 36500; 0 disables that policy’s pruning. Defaults are 400 days for daily page-use aggregates, notification deliveries and resource samples/rollups; daily search aggregates, notification records, in-app notices and derived analytics facts/rollups default to forever. `agent_runs` is never pruned. Notification records stay while an independently retained delivery or notice still needs them. See `.env.example` for the environment names.

This release migrates SQLite pages 8→9, notifications 1→2 and operations 1→2. Update the app and any separately running analytics process together; child analytics follows its app image automatically. Retain a verified pre-upgrade database backup. An older image rejects the newer module versions, so rollback requires restoring that backup with the older image and deliberately handling writes made after it.
