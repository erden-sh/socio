# Coding sessions (CB-239)

A socio can run a coding agent ([OpenCode](https://opencode.ai) by default, or [Codex](https://github.com/openai/codex), [Claude Code](https://code.claude.com), [Gemini CLI](https://github.com/google-gemini/gemini-cli) or [Grok Build](https://docs.x.ai/build/overview)) on a listed GitHub repository for the person it acts for, in a sandbox of its own. The agent never holds a GitHub token, a provider key or anyone's credential: models go through Socio's model gateway and Git through its Git proxy, and the sandbox's network reaches nothing else but package registries, read-only. The sandbox and its proxy are in [deployment/coding/README.md](../deployment/coding/README.md).

It is in development and off: the **Coding sessions** flag (with **Socios use apps for you**) in Settings → Features.

## The session-host loop (CB-326, dark)

A session can run its coding agent through a **session host** — a small process inside the sandbox that drives the agent, streams its work back to Socio, and lets the person watch it live, approve its requests, steer, interrupt or roll it back. This is the long-running shape CB-326 builds, dark behind `CODING_HOST_MODE` (off by default). Today the host covers **Codex** only; the other four agents still run the one-shot CLI exec path.

When the host is on for a session:

- The person sees a **live transcript** in the session card — the agent's thread events (turns, steps, messages, requests) as they happen, with **Interrupt**, **Steer**, **Roll back** and **Fork** controls. Approvals (a command to run, a file to change) surface as Socio's approval cards, as always.
- The person and admins can view the session's logged **gateway exchanges** (every model request and response, metadata and content hashes) and export them as JSON Lines.
- A session keeps its sandbox for up to 4 hours while idle (the host stops at 30 min idle and resumes on the next prompt), instead of ending at the first idle timeout.

Inside the sandbox the host takes its paths from the environment, which are not operator settings: `SOCIO_HOST_CWD` (the repository, `/work/repo`), `SOCIO_HOST_STATE_DIR` (`/work/state`), `SOCIO_HOST_ATTACHMENTS_DIR` (where the agent's attachments are kept, `attachments` under `/work/state`), `SOCIO_HOST_TOKEN_FILE` (the session's token, `/run/socio/token`) and `SOCIO_HOST_CODEX_BIN` (`codex`; the tests point it at a fake peer). Each defaults to the sandbox's layout.

The one-shot adapters for Codex, Claude Code, Gemini CLI and Grok Build stay until the host covers each agent and the host is on at release.

## For people

- Ask your socio to work on a repository. It asks you on a card first, every time: the coding agent (OpenCode, Codex, Claude Code, Gemini CLI or Grok Build, always on Socio's model gateway), the repository, the base branch, its own branch (`socio/<socio>/…`), how long, the model and where it runs, the token budget, what it can and can't do, and, in a room, that everyone there sees its answers. No session starts without your click, read-only ones included.
- The socio sends the agent work with `coding_prompt`. If the work takes longer than its turn, it keeps going and the result comes back in the same conversation. The chat shows a card with the session's repository, branch, model, state, tokens used and pull request, and the agent's progress while it works.
- Pull requests are drafts, opened by Socio from the session's branch into its base. Marking one ready, reviewing and merging are yours, on GitHub.
- Only you can use a session you started, and only from the conversation you started it in. Telegram groups and scheduled runs can't start one.
- **Which coding agent.** Ask for one by name, or let the socio pick: OpenCode is the default. Whichever runs, it uses the same listed models, budgets and limits: it reaches models only through Socio's gateway, with the session's own short-lived credential, never a Codex, ChatGPT, Claude, Anthropic, Google or xAI sign-in.
- **Your own ChatGPT plan.** Where an admin allows it (Settings → Coding → Personal plans), a socio can run your session on the ChatGPT plan you connected under Account → Inference instead of a listed model, with OpenCode or Codex (Claude Code, Gemini CLI and Grok Build can't: your plan takes the Responses API only, in the Codex CLI's request shape): only your own session, only in your private chat with it, never in a room. The card says so: the repository's code goes to OpenAI through your plan, and it uses your plan's limits. Socio keeps your sign-in; the sandbox never sees it.
- A session ends when the socio stops it, after 30 minutes without a prompt, at its time limit, when it used its token budget, or when you end its access (Settings → Account → Socio access). Its branch stays as it is.
- In a room, what the agent did is yours: the session card, its summaries, changed files and diffs show to you only, and everyone else in the room sees one line saying a coding session's result is private to the person it works for. When a long prompt ends there, the socio only says that it ended; ask it for the details (`coding_status`) or open your card. If you can no longer use the repository, your card keeps the session's facts but not what the agent wrote.
- The socio's computer panel has a **Coding** tab: your sessions on that socio, with their status, repository, branch, age and workspace disk, and **Stop**. Admins see everyone's there and can stop any of them; that is recorded with their name.

## For admins and operators

- List repositories under Settings → Coding → Repositories (who may use each, its bases, branch prefix, and push after the checklist) and models under Settings → Coding → Models (outside providers only where you allow them per repository). Limits are in Settings → Coding over `CODING_*` defaults: tokens per session, per person and per socio over 24 hours, and sessions at once per person (2), per socio (4) and on the server (8). Each default comes from its variable when set; a value that isn't a whole number in its range stops the server at start, and an admin's saved value wins over it. There is no server-wide token budget: the budgets times the caps bound the total.
    - `CODING_SESSION_TOKENS` (2,000,000; 1,000 to 1,000,000,000): prompt and completion tokens one session may use in all.
    - `CODING_PERSON_DAILY_TOKENS` (5,000,000; same range): across all of a person's sessions, over a rolling 24 hours.
    - `CODING_SOCIO_DAILY_TOKENS` (10,000,000; same range): across everyone's sessions on one socio, over a rolling 24 hours.
    - `CODING_SESSIONS_PER_PERSON` (2; 1 to 50), `CODING_SESSIONS_PER_SOCIO` (4; 1 to 100) and `CODING_SESSIONS_PER_INSTANCE` (8; 1 to 200): sessions running at once for one person, on one socio, and on the server.
    - `CODING_GATEWAY_REQUESTS_PER_MINUTE` (60; 1 to 600): model requests a minute per session, counted on each server process, so at most doubled while a deploy overlaps.
    - `CODING_GATEWAY_IN_FLIGHT_PER_SESSION` (2; 1 to 16), `CODING_GATEWAY_IN_FLIGHT_PER_PERSON` (4; 1 to 64) and `CODING_GATEWAY_IN_FLIGHT_PER_INSTANCE` (16; 1 to 512): model requests in flight at once per session, per person and on the server, counted across server processes.
- **Settings → Coding → Personal plans** (off by default, or `CODING_PERSONAL_PLANS=on`): lets people run their own sessions on their own ChatGPT plan, where Settings → Platform allows the ChatGPT kind. It is your allowance for every listed repository they may use; turning it off stops their plan sessions' model calls within seconds and ends the sessions.
- **CI on pushed branches.** Turning on push for a repository asks you to confirm a checklist: workflows that run on `push` or same-repository pull requests for `socio/**` branches must get no deployment or publishing secrets; keep those in GitHub environments with required reviewers; protect the base branches. A pushed branch's tests and build scripts still run in CI with whatever secrets those workflows get, and Socio can't check GitHub's settings for you.
- **Settings → Coding → Sandboxes**: the package registries a sandbox may read, download only (`name=host`, one per line; default npm and PyPI, or `CODING_EGRESS_ALLOW`), and how long an unused workspace is kept (default 14 days, or `CODING_WORKSPACE_RETENTION_DAYS`). Each shows the server's default and can go back to it; changes apply to sandboxes started after them, and are in the access audit.
- The app needs `COMPUTER_SUPERVISOR_URL` and `COMPUTER_SUPERVISOR_TOKEN` (the computer supervisor, which runs the sandboxes), `CODING_EGRESS_SECRET` (shared with the coding egress proxy only) and `SESSION_SECRET`. Optional: `CODING_EGRESS_DIAGNOSTICS_URL` (the proxy's diagnostics listener, port 3129: refused requests per session, and the first per host in the access audit). The app's gateway listener runs only while `CODING_EGRESS_SECRET` is set: on `GATEWAY_PORT` (4340), bound to `GATEWAY_HOST` (all interfaces when unset), and accepting connections only from `GATEWAY_SUBNET`, the coding-gateway network's subnet (unset, it refuses every connection).
- Each session's sandbox is removed when it ends; the leader removes any sandbox no live session owns every minute. A person's workspace volume for a socio and repository is kept for their next session and removed once unused for the retention (Settings → Coding → Sandboxes), or at once when they are deactivated, the socio is archived or the repository leaves the list.
- **Coding agents (harnesses, CB-326).** Sessions reach the coding agent through a harness port (`src/server/coding/harness.ts`): an id, the sandbox image and pin that provide its CLI, how it reaches a model (`gateway` or `subscription`), whether it may run on a person's own plan, its terms record, the supervisor exec that starts a run, and a reader for its output. Five harnesses, all on the gateway route:
    - `opencode` (OpenCode, the default): Chat Completions, or Responses on a person's own plan.
    - `codex` (Codex): the Responses API, with the gateway as its only model provider and no OpenAI sign-in; may run on a person's own plan.
    - `claude-code` (Claude Code): the Anthropic Messages API (the gateway's `/v1/messages`) with the session's token as a bearer, no Anthropic sign-in, and its telemetry, error reports, auto-updater and other non-essential traffic off; not on a personal plan.
    - `gemini-cli` (Gemini CLI, CB-326): the Gemini API (the gateway's `/v1beta/models/<model>:generateContent` and `:streamGenerateContent`, for coding sessions only) with the session's token as its `x-goog-api-key`, no Google sign-in; a root-owned system settings file turns off its usage statistics, telemetry, updates, MCP servers, extensions and web tools, and points every helper model it uses (compression, loop detection, edit fixing) at the session's model; not on a personal plan.
    - `grok` (Grok Build, xAI's coding agent, CB-326): Responses (the gateway's `/v1/responses`, the wire API Grok Build itself uses for xAI's models) with the session's token as its key, no xAI sign-in, its web search, online model catalog, update checks, telemetry, feedback and memory off; not on a personal plan. The image builds it from its Apache-2.0 source at a pinned commit (`deployment/coding/grok.pin`), not from xAI's downloadable binary, which has no published checksum.

    `coding_start` takes `harness` (an id, `opencode` when left out); the card names the agent and says it runs on Socio's model gateway. Each session records its harness (`coding_sessions.harness`, `opencode` for every session from before), and the harness's own session id stays in `opencodeSession` (for the other four, the thread or session id their first prompt's output named, a UUID; later prompts resume it). The supervisor builds every command itself from the `prompt` exec's `harness` parameter (`opencode`, `codex`, `claude-code`, `gemini-cli` or `grok`); the app never sends an argv. Permission prompts and the agents' own sandboxes are off inside the sandbox, which is the boundary; the sandbox's network is unchanged (the gateway and package registries only, no vendor host). The CLIs are pinned in the `socio-coding` image (`deployment/coding/*.pin`): using Codex, Claude Code, Gemini CLI or Grok Build needs the image rebuilt and `CODING_SANDBOX_IMAGE` set to it, and the supervisor image rebuilt.

- **Settings → Coding → Coding agents** lists the harnesses: how each reaches models, whether it is the default, whether it may run on a personal plan, whether it is turned off, and its terms record: the plan types it is built for, when its terms were last checked ("Not checked yet" until someone has) and a link to them. Read only: the record is in code, and the switch is the setting below.
- **Each agent needs a model whose backend speaks its API.** The gateway forwards each API unchanged to the listed model's backend: Chat Completions for OpenCode, Responses for Codex and Grok Build (xAI's API speaks it), Messages for Claude Code (Anthropic, or a compatible proxy), the Gemini API for Gemini CLI (Google's, its base URL ending in `/v1beta`, or a compatible proxy). Settings → Coding doesn't record which APIs a backend speaks, so a mismatch shows only as the backend's error in the run.
- **Turning a harness off:** `CODING_HARNESSES_DISABLED` lists harness ids, separated by commas (empty by default; for example `codex,claude-code` or `gemini-cli,grok`). A listed harness starts no new session: the socio is told it's turned off on this server, and a card approved after the switch starts nothing. Sessions already running carry on until they end. A malformed list stops the server at start.
- What is recorded: in the access audit (Operations → Socio access), each session's request, approval, grant, sandbox open and close, credentials, revocation, pushes, pull requests and the first refused host; in the gateway's usage, token counts per request. Never prompts, diffs, file contents or tokens. The agent's last message and progress lines are kept with the run for the session card and forgotten after the workspace retention.
