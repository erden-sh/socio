# Translations (i18n)

How Socio shows people their language, and how to write UI text so it can be translated. The source language is **en-US**; every other locale falls back to it, key by key.

## Where things are

| What                                  | Where                                                                |
| ------------------------------------- | -------------------------------------------------------------------- |
| Source strings and translations       | `packages/i18n/locales/<locale>/<namespace>.json`                    |
| Supported locales and fallback chains | `packages/i18n/src/registry.ts`                                      |
| Shared setup (no React)               | `@socio/i18n`: `createI18n`, negotiation, formatters, manifest types |
| React binding                         | `@socio/i18n/react`: `useTranslation`, `Trans`, `createReactI18n`    |
| What each page route inlines          | `packages/i18n/src/route-namespaces.json`                            |
| Typed keys                            | `packages/client/src/i18n/i18next.d.ts`                              |
| The build                             | `scripts/i18n-build.mjs`, writing `dist/i18n`                        |
| The server's routes                   | `src/server/i18n/`                                                   |

`@socio/i18n` imports nothing from React, so the native app can run it outside React too. Its source follows the `socio/hermes` lint rule, like `packages/shared`.

## Keys and namespaces

- Keys are semantic and dotted (`title`, `errors.offline`), never the English sentence.
- A namespace is one file per locale. Name it by surface, and split a feature by screen when it grows: `settings.language`, `chat.composer`. A page inlines only its route's namespaces (below), so small namespaces keep pages small.
- In code, write the namespace into the key: `t('settings.language:title')`, with `useTranslation(['settings.language'])`. A test checks every `t('ns:key')` literal against en-US, and `tsc` checks the key and its variables against the en-US JSON.
- A new namespace needs a line in `packages/client/src/i18n/i18next.d.ts` (a test fails without it) and, if a route needs it on first render, an entry in `route-namespaces.json`.

## Writing strings

i18next's JSON v4 format, with its own interpolation (no ICU):

- **Variables:** `"saved": "Language: {{language}}"`. React escapes values, so `t()` in components doesn't escape; text for email or Telegram goes through `createI18n` with escaping on.
- **Plurals:** one key per CLDR form, `files_one`, `files_other` in en-US; Spanish adds `files_many`, Arabic `_zero`, `_two`, `_few` and `_many`. Call `t('ns:files', { count })`. Ordinals use `_ordinal_one`, `_ordinal_two`… with `{ count, ordinal: true }`. The build fails a plural that lacks a form its locale uses. Don't write plural ternaries in code.
- **Context:** `edited`, `edited_socio`, called with `{ context: 'socio' }`, for wording that depends on who acts or on state.
- **Nesting:** `$t(common:product)` reuses another string.
- **Formatters:** `{{n, number}}`, `{{price, currency(currency: EUR)}}`, `{{when, datetime(dateStyle: medium)}}`, `{{days, relativetime(range: day)}}`, `{{names, list}}`, `{{size, bytes}}` and `{{ms, duration}}`. They format in the string's locale through `packages/shared/src/locale.ts`.
- **Rich text:** `<Trans>` with components for links and emphasis inside a sentence (`"Read <0>the guide</0>"`). Never put HTML in a dictionary.
- Never leave a translation empty: leave the key out, and it falls back.
- Format through `@socio/shared/locale` (`numberFormat`, `dateTimeFormat`…). A formatter it makes follows the active locale at each call, so it is safe at module level or in a cache. A cache of `new Intl.*` instances must key on the locale; `tests/integration/intl-caches.test.ts` lists each one.

### Intl used by the formatters

What `@socio/i18n` and `locale.ts` construct, for engines with partial Intl (the native app checks these on Hermes):

- `Intl.NumberFormat`: default; `style: 'currency'` with `currency`; `style: 'unit'` with `unit` `byte`, `kilobyte`, `megabyte`, `gigabyte`, `terabyte`, `hour`, `minute`, `second` and `unitDisplay: 'short'`; `maximumFractionDigits`; and whatever options a string passes (`notation: 'compact'`, `signDisplay`, the digit options).
- `Intl.DateTimeFormat`: `dateStyle`, `timeStyle`, `timeZone` and the field options a string passes.
- `Intl.RelativeTimeFormat`: `numeric: 'auto'` (or `'always'`), `style: 'long'` (or what a string passes), units from `range`.
- `Intl.ListFormat`: `type: 'conjunction'` and `style: 'long'` by default; `type: 'unit'` with `style: 'short'` for durations.
- `Intl.PluralRules`: `type: 'cardinal'` and `'ordinal'` (i18next's plurals, and the build's `resolvedOptions().pluralCategories`).
- `Intl.Collator`: default options, for `compareText`.
- `Intl.DisplayNames`: `type: 'language'`, for the Language setting's names (web).

## Locales and fallbacks

Each locale in `registry.ts` has a fallback chain ending in en-US, for example **es-US → es-419 → es → en-US** (tags that aren't registered, like `es`, are skipped). A locale's files hold only what differs from the next one in its chain: es-US carries the few words that differ from Latin American Spanish, and everything else comes from es-419. The build checks sparse files like full ones and counts coverage through the chain.

A request's locale is, in order: the person's saved preference on this server (`locale` in `/api/preferences`; null means "match my device"), the `socio_locale` cookie (kept for signed-out pages), the browser's `Accept-Language`, then en-US. Every step chooses among one set, the locales over the coverage gate (95%, `eligibleLocales`): the server's negotiation, the cookie, the preference, Settings › Language's list and its "Match my device". So a partly translated locale is never picked, and a Portuguese browser gets en-US until pt-BR passes the gate, on the server and in the browser alike. Settings › Language stays hidden while en-US is the only one.

`en-XA` is a generated pseudo-locale: every string accented, lengthened and bracketed. Use it (with the `socio_locale=en-XA` cookie) to find untranslated text and layouts that break with longer words. It is the one exception to the gate: a cookie or preference may name it, but it is never negotiated from a browser and never offered in the picker.

### Socios' replies

A socio replies in the person's app language. Its turn's note (never the system prompt, a time marker or the history: CB-139) gets one line after the time, from `replyLanguageLine` (`@socio/i18n/reply-language`): `Language: reply in Spanish (es-419, the person's app language) unless they write in another language or ask otherwise.` The language is named in English from a fixed table (`LANGUAGE_NAMES`), not `Intl.DisplayNames`, so a locale's line is the same on every server.

- **Precedence:** what the person writes in wins (the model's job, as the line says); then their profile's **Language**, when the note gives the profile (memory on, and in a chat with other people only if they share it), which drops the line; then their app language; then nothing.
- **No line** for no preference, en-US or `en-XA`, so the note of a person who never chose a language is what it was, byte for byte.
- **Whose:** the turn's acting person: a room's sender, a schedule's or job's person, a private chat's owner. A cloud voice call's instructions end with the call owner's line.
- Thread titles and a long chat's notes are asked for in the conversation's language, the same words for everyone.
- `tests/agent-locale.test.ts` builds the whole request (system prompt, tools, history) for the same conversation with no locale, en-US, es-419 and pt-BR and checks that only the newest message's note differs.

### Adding a locale

1. Register it in `packages/i18n/src/registry.ts`, with its direction and fallback chain.
2. Add `packages/i18n/locales/<locale>/` with any namespaces translated so far.
3. Run `pnpm run check:i18n`: it lists every unknown key, changed variable and missing plural form, and prints each locale's coverage.

Translations come in as reviewed pull requests against these files, like code. A machine draft is a starting point for a reviewer, never merged unread.

## Build and delivery

`pnpm run build` runs `scripts/i18n-build.mjs`, which checks every file (valid JSON, keys known to en-US, the same variables, every CLDR plural form) and writes `dist/i18n/<locale>/<ns>.<hash>.json` (with gzip and Brotli copies) and `dist/i18n/manifest.json`:

```json
{
    "release": "0.56.0",
    "locales": { "es-US": { "coverage": 0.97, "ns": { "common": { "hash": "…", "sourceHash": "…" } } } }
}
```

`hash` names the file's content; `sourceHash` names the en-US source's keys and variables, so a client with its own copy can tell whether the server's fits its code (`acceptsServerNamespace`). `pnpm run check` runs the same checks without writing. The build prints each namespace's size and warns when one route's inlined en-US dictionaries are over 8 kB gzipped: split the namespace.

The server serves them itself, from the build, and never fetches dictionaries from anywhere:

- `GET /i18n/<locale>/<ns>.<hash>.json`: immutable (`Cache-Control: public, max-age=31536000, immutable`), with the hash as a strong ETag.
- `GET /i18n/manifest.json?locales=es-US`: `Cache-Control: no-cache` with an ETag, narrowed to the locales asked for and their fallbacks.

Both are public and hold only UI strings. In development and tests, the server builds the dictionaries in memory from `packages/i18n/locales`.

On the web, the server resolves the locale and inlines the root's and the matched route's namespaces into the page (`<html lang dir>` included), so the browser hydrates the same words. A route declares its namespaces in `route-namespaces.json` and passes `routeI18n(context, '<route id>')` from its loader. Changing the language loads the new locale's files through `i18next-http-backend`, without a reload.

## Lint

- `socio/no-literal-text` flags JSX text and the attributes people read (`aria-label`, `title`, `placeholder`, `alt`, `label`) given a literal. It is on only for the folders in its `.oxlintrc.json` override: Settings › Language first. Add a folder there in the same pull request that moves it to `t()`; the list only grows.
- `socio/translate-in-components` flags `i18n.t(…)`, `getFixedT(…)` and a `t` called outside a component or hook. Take `t` from `useTranslation()` where it is used: a `t` captured elsewhere doesn't follow a language change, and the React Compiler memoizes values.
