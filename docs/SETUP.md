# Running Socio

Socio runs a React app and a Node server. The server stores pages, Space and socio configuration, conversations and scheduled work in one SQLite file, and calls your configured model endpoint.

## Local development

Use Node.js 26.13.0, the latest LTS (`.nvmrc` and `.node-version` name it: `nvm use`, fnm or similar pick it up), and pnpm 10.15.0. package.json's `engines` allows Node 26.13.0 or later within 26 and pnpm 10.15 or later within 10; a mismatch fails the install (`engine-strict` in `.npmrc`). `corepack enable pnpm` gives you the pnpm that package.json's `packageManager` names (CB-183). The images and CI run the same Node, `node:26.13.0-bookworm-slim` pinned by digest.

```sh
pnpm install --frozen-lockfile
cp .env.example .env
pnpm run dev
```

Open http://127.0.0.1:4310. One process serves the pages and the API: the server renders the pages with React Router, and Vite runs inside it for the browser modules and hot reload (on the same port). Edits to `packages/client/src` show up without a restart; edits to the server restart it. Without a model configured, the app shows its setup state; it does not generate simulated replies.

During `pnpm run dev`, both http://localhost:4310 and http://127.0.0.1:4310 are allowed browser origins. If your `.env` still sets `APP_ORIGIN` to the old Vite port (`…:5173`), change it to `…:4310` or remove it. To use a different proxy or custom domain, set `APP_ORIGIN` to one exact origin or a comma-separated list, for example `APP_ORIGIN=http://localhost:4310,http://127.0.0.1:4310`. An explicit value replaces the development defaults. Origins must match the scheme, hostname, and port exactly; omit paths and trailing slashes. Whitespace around list entries is trimmed and empty entries are ignored. Outside development, leaving `APP_ORIGIN` unset requires the browser origin to match the request URL's origin. This setting preserves cross-site request blocking; it does not enable direct cross-origin browser access to the API.

For a built local app:

```sh
pnpm run build
pnpm start
```

Open http://127.0.0.1:4310. Keep the server running for background work. `pnpm run build` writes the pages' browser and server builds to `dist/web` (`react-router build`) and the server to `dist/server` (`tsc`); the server loads `dist/web/server/index.js` at startup (`WEB_BUILD_DIR` points elsewhere) and stops with "run pnpm run build" when it is missing.

Provider credentials belong in `.env`, not client-side variables or source code. Conversations run on the CopilotKit runtime in SSE mode with a local runner (`src/server/turns/local-runner.ts`); no conversation data leaves the server except the prompts sent to your model endpoint.

### Inference backends

The model settings above (`OPENAI_*`, `MODEL_*`, `TITLE_MODEL_OPTIONS`) only **seed** the first inference backend, once: on the first start with `OPENAI_BASE_URL` and `OPENAI_MODEL` set and no backend in the database, the server creates a self-hosted (OpenAI-compatible) backend from them and makes it the default. From then on the database is the source of truth: editing these variables changes nothing (the server logs a notice naming the ones that differ). Operators manage backends on **Settings → Platform** (`/settings/operator`): add, edit, enable or disable, test (a call to the backend's `/models`, only when an operator clicks), delete, and pick the default. Selection is manual; there is no failover.

The same page lists the bring-your-own subscription kinds the server has and lets operators allow them. People then connect their own subscription in **Account → Inference**; their chats and scheduled tasks run on it, while titles and Learning stay on the default backend (and wait while there is none). With neither, the chat says how to get a model instead of failing.

The server has one such kind, **ChatGPT** (`byo-chatgpt`): a person signs in with their own ChatGPT plan through the Codex CLI's device-code login (the account dialog shows a code and a link to OpenAI's sign-in page), and their socio turns then run on that plan's Codex limits through `chatgpt.com`. The operator picks the model for ChatGPT plans on the same page (default `gpt-6.1-sol`, the CLI's default; if chats fail with "model not available", choose `gpt-5.5`). A usage limit or an ended sign-in shows as its own message in the chat and in Telegram; a connection that can't serve a turn (sign-in ended, OpenAI unreachable with an expired token) falls back to the default backend. Disconnecting revokes the sign-in and deletes it. For local tests only, `CHATGPT_AUTH_ISSUER` and `CHATGPT_BASE_URL` point the kind at a fake server instead of `https://auth.openai.com` and `https://chatgpt.com/backend-api/codex`; never set them in a deployment.

#### xAI Grok as a shared backend

xAI's API speaks OpenAI Chat Completions, so Grok is added like any other backend; no extra adapter or setting is needed (CB-252). On **Settings → Platform → Add backend**:

| Field    | Value                                                                                                                                                                                                                                      |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Name     | Anything people will recognize, e.g. `Grok`                                                                                                                                                                                                |
| Base URL | `https://api.x.ai/v1`                                                                                                                                                                                                                      |
| Model    | An xAI model id, exactly as xAI's console lists it, e.g. `grok-4` or `grok-4-fast-reasoning`. Ids change as xAI releases models: check the list in the console (or the backend's **Test**, which calls `/models`) rather than this example |
| API key  | An xAI API key from the console. It is write-only: sealed under the data key like every backend key, never shown again or sent to a browser                                                                                                |

Then set the capabilities to the model's: **The model takes images** only for a model xAI lists with image input, its **Context window** from xAI's model page (long chats are tidied to about 70% of it), and **Completion tokens per turn** (reasoning models count their reasoning in it, so leave room). Click **Test**, then **Make default** if Grok should be the shared model. Each model is its own backend: add another backend with the same URL and key for a second Grok model.

To seed Grok as the first backend instead, set `OPENAI_BASE_URL=https://api.x.ai/v1`, `OPENAI_MODEL` to the model id and the key as a secret (`OPENAI_API_KEY_FILE` pointing at a Docker or swarm secret; never in stack env text) before the first start. Like every seed, that is read once; later changes go through Settings → Platform.

Things to know: every prompt of a turn on that backend, with the conversation and tool results it carries, goes to xAI under xAI's terms; usage is billed to the key's xAI account, shared by everyone whose chats use the backend. This is a shared backend, not a per-person connection: people can't bring their own Grok key yet. If xAI refuses a request parameter for a model, the failed **Test** or the chat shows xAI's message.

Backend keys and users' tokens are stored encrypted under the [data encryption key](#data-encryption-key); they are never sent back to a browser. Without one they are under a key derived from `SESSION_SECRET`, and rotating `SESSION_SECRET` makes them unreadable: operators enter keys again (the backend shows "Key unreadable") and people reconnect. Without either (loopback only) they can't be read after a restart.

### Data encryption key

`DATA_ENCRYPTION_KEY` (or `DATA_ENCRYPTION_KEY_FILE`, CB-62) seals the data space's files, chat attachments and stored inference credentials with AES-256-GCM. It is 32 random bytes as 64 hex characters or base64: `openssl rand -hex 32`. Each sealed value names the key it was sealed with (an id derived from the key, not the key), so the server reads three kinds: the current key, `DATA_ENCRYPTION_KEY_PREVIOUS` during a rotation, and the legacy key derived from `SESSION_SECRET`, which sealed everything before this key existed. `none` counts as unset (the stack's placeholder secret).

Once it is set, the server seals everything still under an older key again, in the background, at start and hourly: per file, under the user's lock, in whichever store holds it (the local disk or S3), and every stored credential. It is idempotent and picks up where it stopped after a crash. It logs counts only (`Data key: re-sealed 2 stored credential(s); re-sealed 41 file(s).`). Until it is done, `/healthz` says `"dataKey": "resealing"`, then `"ok"`; admins see the counts on the Settings dialog's Service setup. `"key_missing"` means something is sealed under a key the server doesn't have (a previous key removed too early): put it back as `DATA_ENCRYPTION_KEY_PREVIOUS`. It also shows when `DATA_ENCRYPTION_KEY` itself was removed after it sealed something; then the log says `Data key: N item(s) are sealed under a data key, but DATA_ENCRYPTION_KEY is not set…` at start: set it again.

From then on `SESSION_SECRET` can rotate without losing files or credentials (it still signs everyone out), and backups need the data key, not `SESSION_SECRET`, to be restored. Keep a copy of the key apart from the backups: a backup without its key can't be read.

To rotate the data key: set the new key as `DATA_ENCRYPTION_KEY` and the old one as `DATA_ENCRYPTION_KEY_PREVIOUS`, restart, wait for `"dataKey": "ok"`, then remove `DATA_ENCRYPTION_KEY_PREVIOUS` and restart again. Backups taken before the rotation need the old key.

Without `DATA_ENCRYPTION_KEY`, nothing changes: development keeps working on the key from `SESSION_SECRET`; production logs a warning at start, and Service setup says the key isn't set. `DATA_ENCRYPTION_KEY_PREVIOUS` alone, or a malformed key, stops startup.

#### Recovery keys

The recovery kit holds the data key, the previous key until pre-rotation backups expire, and `SESSION_SECRET` only while anything is still sealed under the key derived from it. Three things in the app (CB-322) make that kit checkable.

**The legacy-sealed count.** Service setup shows `Legacy-sealed: 3 item(s) (inference credentials 2, files 1) still need SESSION_SECRET; keep it in the recovery kit until this is zero`, and `/healthz` shows `"legacySealed": 3`. It counts every stored value whose seal names the legacy key, in every seal purpose: inference credentials (backends' keys, people's subscription tokens, the environment's seed), data space files and chat attachments, backups, push keys, the GitHub App key, settings secrets (the transcription key, the release feed's token), MCP credentials and workspace secrets ([Secrets for workspace apps and plugins](#secrets-for-workspace-apps-and-plugins), every version, retired and deleted ones too). Backups are only ever sealed under a data key (the off-site copy doesn't run without one), so they never count; Service setup lists only the purposes that have any. Without a data key, everything sealed counts: the legacy key is the one sealing it. Once it reads `none`, `SESSION_SECRET` can leave the recovery kit.

**Re-seal under the data key.** The hourly re-seal above does this on its own; an admin can run it now with **Re-seal under the data key** on Service setup, shown while anything is still under the legacy or the previous key. It's the same run (one at a time: asked while the hourly one runs, it's that one), so it also moves values off `DATA_ENCRYPTION_KEY_PREVIOUS`. It runs in the background store by store, yielding to the event loop between stores and every 25 credentials or 50 files, so requests keep being answered. It's idempotent and resumable: each value moves on its own, so a run cut short leaves the rest for the next one. The workspace audit records who asked and, when it's done, the counts (`done: 8 re-sealed, 0 unreadable, 0 left; 0 legacy-sealed remain`), and Service setup shows `Re-seal: the last one finished at <time>: 8 re-sealed`. Without `DATA_ENCRYPTION_KEY` it's refused (`POST /api/data-key/reseal` answers 409): new seals would be legacy again.

**Key fingerprints.** Service setup shows `Key ids: current 1a2b3c4d5e6f7a8b, previous …`, and `/healthz` shows `"dataKeyId"` and, during a rotation, `"dataKeyPreviousId"`. A key id is the 16 hex characters every seal names its key by, an HMAC of the key: it identifies the key without revealing anything about it. To check a paper or offline copy of the key against the running app, print its id on any machine with the built app, offline:

```sh
node dist/server/server/keys/key-id-cli.js          # type or paste the key; it isn't shown
node dist/server/server/keys/key-id-cli.js < key.txt  # or from a file (the first line that isn't blank)
```

`pnpm run key-id` does the same. The key is read from stdin only, never as an argument (so it stays out of shell history and the process list), parsed as the server parses `DATA_ENCRYPTION_KEY` (64 hex characters or base64), and wiped once hashed. The script reads no environment, writes nothing and makes no network calls. It prints the id, or `Key id failed: … must be 32 random bytes…` without echoing what it was given. The same id as Service setup's means the copy is the key; to prove it also opens the backups, verify it with the restore drill ([Restore drill](#restore-drill)).

### Web reads

Socios with research allowed get `http_get` and `http_json`: GET or HEAD reads of public URLs and JSON APIs. Each socio has a **web identity**, set by admins in the socio's settings: `agent` (the default) sends the declared User-Agent `SocioAgent/1.0 (user-directed agent; +<APP_ORIGIN>/agents)`, using the first `APP_ORIGIN` entry (without one, the `+…/agents` link is left out); `browser` means the socio reads through its computer's browser tools instead, and the two tools say so. Nothing in a request identifies the user: no name, email, account, cookies, Authorization, `From` or `Referer`, and `AGENTS_CONTACT` is never sent. A socio can set only `Accept`, `Accept-Language`, `If-None-Match` and `If-Modified-Since`; any other header is refused.

Reads keep the public-address network rules on every redirect hop (public addresses only, DNS pinned, ports 80 and 443, at most 5 redirects), and are rate-limited per socio and host and for the whole workspace, cached (Cache-Control and ETag are respected), capped in size and time, and audited per socio (host, path with query parameter names but not their values, status, bytes, the user the socio acted for). When a site answers 429 or 403 (or 503 with `Retry-After`), every socio stops reading from it for `Retry-After` or the cooldown, and the socio is told why. `/agents` is a public, static page explaining all of this to site owners.

| Variable                     | Default | Purpose                                                                          |
| ---------------------------- | ------- | -------------------------------------------------------------------------------- |
| `WEB_IDENTITY_DEFAULT`       | `agent` | Identity for socios without their own: `agent` or `browser`                      |
| `AGENTS_CONTACT`             | none    | An http(s) or `mailto:` URL shown on `/agents`; otherwise "the operator"         |
| `WEB_MAX_BYTES`              | 2000000 | Most of a response read (decoded); the rest is cut off and marked incomplete     |
| `WEB_TIMEOUT_MS`             | 15000   | A whole read, redirects included                                                 |
| `WEB_HOST_RATE_PER_MINUTE`   | 30      | Reads per socio and host                                                         |
| `WEB_GLOBAL_RATE_PER_MINUTE` | 300     | Reads for all socios together                                                    |
| `WEB_COOLDOWN_SECONDS`       | 900     | How long a host that refused without `Retry-After` is left alone                 |
| `WEB_CACHE_TTL_SECONDS`      | 60      | Freshness of responses that set none (a response's own max-age is capped at 1 h) |

## Settings and the environment

Nothing an admin does should need a redeploy: a stack update means a short downtime. So a setting an admin may want to tune lives in **Settings**, as a stored value over the environment's: the variable (or the built-in default) stays the starting value, what an admin saves takes its place at once, with no restart, and "Use the server's defaults" goes back to it. Only the environment holds what the app needs before it can start, and secrets.

Every variable the server reads is one of four kinds:

- **Settings:** an admin changes it in the app. The variable is only the starting value; editing it later changes nothing for a value already saved.
- **Tunable, not in Settings yet:** safe to change at runtime, but still a variable, so changing it needs a stack update. Listed with what would make it a control.
- **Secret:** a credential. It stays in the environment or a secret file (`*_FILE`, Docker secrets) and is never stored in Settings, which at most says which one is in use.
- **Boot-time:** where the app listens, where its data lives, how it reaches other services. Changing it means a restart, so it stays in the environment.

### Ceilings: Settings → Access

Who may sign in and how work the other way round (CB-124). The variables stay the **ceiling**, and admins can only narrow them under **Settings → Access**: turn a sign-in method off, take an entry off a list. Nothing there can add a method, an email, a domain or a provider; that still needs a stack update.

| Variable                                                           | What admins can do under Settings → Access |
| ------------------------------------------------------------------ | ------------------------------------------ |
| `AUTH_PASSWORD`, `AUTH_PASSKEY`, `AUTH_OPEN_SIGNUP`                | Turn off, when the variable leaves it on   |
| Telegram sign-in links (on while the bot runs)                     | Turn off                                   |
| `AUTH_OAUTH_PROVIDERS`                                             | Turn a configured provider off             |
| `AUTH_ALLOWED_EMAILS`, `AUTH_ALLOWED_DOMAINS`, `AUTH_ADMIN_EMAILS` | Keep a subset                              |

What is in force is the variable's value intersected with what admins saved, on every request: an entry the variable drops is gone at the next restart whatever was saved, and while a narrowed list is saved, an entry the variable adds later stays out until an operator ticks it (a list with everything ticked follows the variable). Only operators see the page; each change needs their password or a passkey again (step-up), ends the sessions that no longer qualify (those made by a method turned off, and those of people left with no way to sign in), is kept in the page's history (append-only) and is sent to every admin and operator. A change that would leave the operator making it, or every operator, unable to sign in or to confirm a change is refused. If no operator can get in, `pnpm run auth access-policy-reset` on the server clears what was saved (`access-policy` shows it); the boot log says what is narrowed. Socios and connected agents have no tool for any of it. Operators' help: `/docs/operate/access-policy`.

**Who may run code (CB-376)** is no longer a variable: it is the `code:run` permission of Better Auth's organization plugin (dynamic access control, one hidden workspace organization, a `member` row per account). Admins have it; anyone else gets it from a group that gives **Run code**, which admins manage under **Settings → People → Groups**. It is checked on every use, so removing someone from a group, or deleting it, applies at once. The plugin's own `/api/auth/organization/*` endpoints are never served; groups change only through the admin routes (`/api/groups`). `CODE_USERS` (`DISPATCH_CODE_USERS` before CB-325) is deprecated: at the first boot with groups, if it (as narrowed under Settings → Access before) lists anyone, its non-admins are put in a "Code" group, once, and the server logs a deprecation warning while it is set. Remove it from the stack env; a later release stops reading it. With mock auth (local development) there are no groups: admins may run code and nobody else.

## Accounts and sharing

Everyone signs in with their own account. Accounts come from an auth provider behind one interface (`AuthProvider` in `src/server/auth/contract.ts`): **mock** (`AUTH_PROVIDER=mock`, the default, for local development only) or **Better Auth** (`AUTH_PROVIDER=betterauth`, real sign-in inside the app with passkeys, passwords, OAuth/OIDC providers and one-time links by Telegram; see [Sign-in](#sign-in)). Every server other machines reach uses Better Auth.

Roles, highest first:

| Role     | Can                                                                                                                        |
| -------- | -------------------------------------------------------------------------------------------------------------------------- |
| `admin`  | Manage Spaces, socios, permissions, global and platform settings, sign-in (Settings → Access), Learning, issues and people |
| `member` | Their own conversations, tasks and memories; shared Spaces, pages and socios                                               |

One admin is the [workspace owner](#the-workspace-owner). The `operator` role was retired (CB-390): former operators are admins, and wherever this guide still says "operators", read "admins".

With mock auth, the sign-in screen lists the configured users and you pick one. There is no password. The defaults are:

| ID      | Name  | Role   |
| ------- | ----- | ------ |
| `alice` | Alice | admin  |
| `bob`   | Bob   | member |

To use your own team, set `MOCK_USERS` to a JSON array with unique lowercase IDs, roles `admin` or `member`, and at least one admin (a former `operator` entry starts as an admin):

```sh
MOCK_USERS=[{"id":"sam","name":"Sam","role":"admin"},{"id":"rio","name":"Rio","role":"member"}]
```

Keep IDs stable: conversations, tasks and memories are stored against them. Use **Switch user** in the sidebar footer to sign out and pick another account.

Mock auth is for this machine only, because anyone who reaches it can pick any user and nothing stands in front of it (there is no owner token). The server refuses to start with mock auth on a non-loopback `HOST` or with an `APP_ORIGIN` other than `localhost`, `127.0.0.1` or `[::1]`, and it refuses requests from another address or with a proxy's forwarding headers (`X-Forwarded-For`, `Forwarded`, `X-Real-IP`). Mock sign-in sessions are HMAC-signed, HttpOnly, `SameSite=Strict` cookies that last 30 days. Set `SESSION_SECRET` to a random value of at least 24 characters; leaving it empty uses a per-process secret, so everyone is signed out at each restart. Better Auth on a non-loopback `HOST` requires `SESSION_SECRET`.

What is shared and what is private:

| Item                                            | Visible to                     | Changed by                      |
| ----------------------------------------------- | ------------------------------ | ------------------------------- |
| Spaces and pages                                | Everyone                       | Spaces: admins. Pages: everyone |
| Socios, socio permissions, computer permissions | Everyone                       | Admins                          |
| Global settings (pause, research, memory)       | Everyone                       | Admins                          |
| Conversations, including page conversations     | Their owner                    | Their owner                     |
| Scheduled tasks, memories, calls                | Their owner                    | Their owner                     |
| Learning evidence                               | Admins, for review             | Collected from everyone's turns |
| Approved skills                                 | Everyone, through their socios | Admins approve                  |

A socio's turn runs as the owner of the conversation: it uses that person's profile and memories (in a chat with other people, only what they marked for team chats; see [MEMORY.md](MEMORY.md)), and computer actions are audited under their ID. Tools never include management operations, so a member cannot change settings or permissions through a socio. Each person gets their own conversation about a shared page. Another person's conversation, task or call returns "not found".

Upgrading from the single-owner template: on startup, conversations, page conversations, tasks and memories stored under `OWNER_ID` (default `company-brain-owner`) move to the first admin.

## Sign-in

`AUTH_PROVIDER=betterauth` replaces the mock picker with real accounts, run by [Better Auth](https://www.better-auth.com) inside the app: no separate identity service, and its tables (`auth_user`, `auth_session`, `auth_account`, `auth_verification`, `auth_passkey`) live in the app's SQLite database, created by the normal migrations. Mock auth stays the default for local development.

The sign-in screen shows what is configured:

- **Passkeys** (`AUTH_PASSKEY`, default on): sign in with the device's fingerprint, face or PIN. People add a passkey under **Account & security** in the account menu, after their first sign-in with a password or provider. Passkeys are bound to the `APP_ORIGIN` hostname (a new hostname needs new passkeys: [Moving APP_ORIGIN](#moving-app_origin)); browsers allow them only on https (or `localhost`).
- **Email and password** (`AUTH_PASSWORD`, default on): at least 10 characters, stored as scrypt hashes.
- **Sign in with <provider>**: any OpenID Connect provider (Logto, Google, Clerk, …), configured with `AUTH_OAUTH_*` below.
- **Send me a sign-in link**: a one-time link, sent by the Telegram bot as a direct message to the person's linked Telegram account. On whenever the bot runs; see [Sign-in links by Telegram](#sign-in-links-by-telegram).

These variables are ceilings: admins can turn a method off, close sign-up and narrow the lists under **Settings → Access**, never open them further ([Ceilings](#ceilings-settings--access)).

Accounts are **invite-only** by default: an admin adds people (**Account & security → People**, or the `pnpm run auth` command) and passes on a one-time password link. `AUTH_OPEN_SIGNUP=true` lets anyone who reaches the app create an account (with SMTP configured, they must confirm their email first).

### Roles and existing users

Each sign-in account is linked to an app user id, which owns conversations, tasks and memories. New accounts get a new id (`u-` and 12 hex digits). To keep the data of a user from the mock-auth days (say `alice`), link it:

- When adding the person (**People → Existing user to link**, or `pnpm run auth create-user … --link alice`), or
- With `AUTH_LINK_USERS={"alice":"alice@example.com"}`: the first account created with that **verified** email (an admin adding it, or an OAuth sign-in whose provider confirms the address) becomes `alice`.

A linked account starts with the user's existing role. There are two roles, `admin` and `member` (the `operator` role was retired in CB-390: former operators are admins). Admins change roles under **People**, and the app keeps at least one active admin. One admin is the [workspace owner](#the-workspace-owner). Emails in `AUTH_ADMIN_EMAILS` are always admins once verified (admins vouch for the addresses they add; providers confirm theirs; self-service sign-ups are verified only by email confirmation, so without SMTP they never count). An OAuth provider's admin group promotes at sign-in (`AUTH_OAUTH_<ID>_ADMIN_GROUP`), and never demotes. **Deactivate** (People) replaces removing an account: the person can't sign in by any way (password, passkey, provider, sign-in or confirmation link), their sessions end at once, the service account keys they made are revoked, their mini app sessions end, their scheduled tasks and job schedules pause (kept, saying why), their subscription connections are disconnected, and their Telegram link no longer acts for them. Their conversations, files, pages, issues and comments stay theirs and keep their name. **Reactivate** lets them sign in again (not into their old sessions; keys, schedules and subscriptions stay as the deactivation left them). Both are recorded in the workspace audit. Accounts are never deleted from the app.

An OAuth sign-in with a verified email that matches an existing account signs into that account (and links the provider to it). Otherwise it may create an account only if the person matches `AUTH_ADMIN_EMAILS`, `AUTH_ALLOWED_EMAILS`, `AUTH_ALLOWED_DOMAINS`, `AUTH_LINK_USERS`, or the provider's admin or allowed groups (or `AUTH_OPEN_SIGNUP=true`). Everyone else sees "not invited".

### The first admin

Set `AUTH_FIRST_ADMIN_EMAIL` (and `AUTH_FIRST_ADMIN_LINK`, an existing app user id such as `alice`, so that user's conversations, Telegram link and tasks carry over). At each boot under Better Auth, while the workspace has no active admin:

- an existing account with that email becomes an admin, if its email is verified and it isn't deactivated (an unconfirmed self-service sign-up is never promoted; the log says so);
- otherwise the account is created: verified, linked to `AUTH_FIRST_ADMIN_LINK` (unless another account already holds that id; then nothing is created and the log says so), named after that app user, and without a password.

Once an admin exists, the settings do nothing; restarts and later changes to the variables don't create or promote anyone, so they never bring back an account the company's admins demoted or deactivated. The former names, `AUTH_OPERATOR_EMAIL` and `AUTH_OPERATOR_LINK`, are read for two releases with a startup warning; `AUTH_FIRST_ADMIN_*` wins when both are set. The address is only compared and stored, never sent anywhere. The first admin then signs in with **Send me a sign-in link** (their app user's Telegram link) or a password link from `pnpm run auth password-link --email …`, and adds a passkey (the app suggests one in the sidebar after a sign-in without one).

### The workspace owner

Each workspace has one owner (CB-390): an admin with one extra protection, not a third role. The first admin is the owner; on a workspace that had admins before, the upgrade made the earliest-created active admin the owner (a workspace audit line says so).

- Other admins can't demote, deactivate or remove the owner, end the owner's sessions or devices, move what the owner owns, or make the owner a password link. A sign-in change under Settings → Access that would leave the owner without a way to sign in is refused.
- The owner can't demote or deactivate themselves, remove themselves, or leave, while they are the owner. They hand ownership over first: **People** → another active admin → **Make owner** (their name typed, then a step-up). The previous owner stays an admin. The change is audited and every admin is told.
- Only the server's shell can deactivate the owner (`pnpm run auth deactivate --email …`). Ownership then passes to the earliest-created active admin, audited and announced; with no admin left, the next first admin (`AUTH_FIRST_ADMIN_EMAIL`) becomes the owner at boot.

### Sign-in links by Telegram

With Better Auth and a running bot (`TELEGRAM_BOT_TOKEN` and `TELEGRAM_POLLING=true`), the sign-in screen offers **Send me a sign-in link**: the person enters their email, and if an account with that email exists and its app user has a linked Telegram account ([Link accounts](#link-accounts)), the bot sends them a direct message with a one-time link and a one-line note. The message never contains the email.

- The answer is always "If that account can receive links, one is on its way.", whether or not the account exists or can receive links, and it comes before anything is sent, so its timing tells nothing either.
- A link works once, for 15 minutes. It opens `/sign-in-link`, which signs in only when **Continue** is pressed, so a link preview or a scanner that fetches it doesn't use it up (the bot also turns link previews off). Tokens are stored hashed.
- Rate limits: 5 requests per client address and 3 links per account per 15 minutes. Past the account limit the answer stays the same and nothing is sent.
- Admins can send a link from **People** (**Send sign-in link via Telegram**) to anyone with a linked Telegram; they never see the link. For people without one, make a **Password link** and pass it on privately.

Links travel through a `SignInLinkSender` (`src/server/auth/contract.ts`; the link's message is in `packages/foundation/src/auth/sign-in-links.ts`); email delivery through the optional mailer can be added the same way.

### The first admin, and password links

Run the account command on the server, in the container with the stack's environment (it migrates the database first, with a backup):

```sh
pnpm run auth create-user --email you@example.com --name "Your Name" --role admin [--link alice]   # or --role member
# in the container: node dist/server/server/auth/auth-cli.js create-user …
pnpm run auth password-link --email you@example.com
pnpm run auth deactivate --email them@example.com
pnpm run auth reactivate --email them@example.com
pnpm run auth list
pnpm run auth access-policy         # what Settings → Access narrows (CB-124)
pnpm run auth access-policy-reset   # break glass: the environment applies again
```

`create-user` prints a one-time link to `APP_ORIGIN/reset-password?token=…`; open it, choose a password, sign in, then add a passkey under **Account & security**. Links from `create-user` and **People** last three days; with SMTP, they are also emailed. `--password-file <file>` sets the password directly instead (test accounts). Without SMTP there is no "Forgot password?": an admin makes a new link under **People**.

`deactivate` and `reactivate` do what **People → Deactivate** and **Reactivate** do, with the same guards: you can't deactivate the last active admin. From the shell only, `deactivate` may deactivate the workspace owner (at a verified customer contact's request); ownership then passes to the earliest-created active admin. A deactivation signs the person out everywhere. It revokes the API keys they made, ends their mini app sessions, pauses their schedules and disconnects their subscriptions. It prints what ended, and the audit names `cli` as who did it. A running server stops the person's job runs within a second. The CLI can't reach what lives in the server's memory: open mini app connections stay until they close or the server restarts, and a mini app sign-in code made in the last minute still works once. So use **People** while an admin can sign in. `list` marks the workspace owner with `(owner)` and deactivated accounts with `(deactivated)`.

### Sessions and security

Sessions are database-backed, in an HttpOnly, `SameSite=Strict` cookie, valid for 7 days and renewed while in use. With an https `APP_ORIGIN` it is `__Host-cb.session_token` (Secure, `Path=/`, no Domain), and so are Better Auth's other cookies (`__Host-cb.*`): the server renames Better Auth's `__Secure-cb.*` cookies on the way out and reads only `__Host-cb.*` ones on the way in, so a page on a subdomain (a mini app) can't plant a session on the app ([cookie tossing](SECURITY-ARCHITECTURE.md#cookie-tossing)). Over http (local development) it stays `cb.session_token`. **Upgrading to this version signs everyone out once**: sessions in the old `__Secure-cb.session_token` cookie are ignored, and people sign in again (their passkeys, passwords and providers still work). **Account & security** has "Sign out everywhere"; changing or resetting a password signs out other sessions; admins can sign a person out under **People**. Tabs of one browser follow each other: sign out in one and the others show sign-in at once; sign in in one (or come back from a provider or a sign-in link) and the others return to the app without a reload. A signed-out tab doesn't poll the server; it checks again when you come back to it. Sign-in endpoints are rate-limited per client address (email sign-in 30 a minute). With Better Auth, mock sign-in is off. There is no owner token any more: the server warns if `OWNER_TOKEN`, `OWNER_TOKEN_FILE` or `AUTH_MOCK_ALLOW_REMOTE` is still set, and ignores them. See [SECURITY.md](../SECURITY.md).

### Moving APP_ORIGIN

Moving the app to a new hostname (for example from `https://brain.example.test` to `https://brain.example.com`) changes everything bound to the origin:

- **Passkeys stop working.** A passkey is bound to its relying party id, the `APP_ORIGIN` hostname, and browsers won't offer it on another one. After the move people sign in with a [Telegram sign-in link](#sign-in-links-by-telegram), their password or a provider, then add a passkey again under **Account & security** (and may remove the old one). Someone with only a passkey needs a sign-in link or a password link from an admin (**People**, or `pnpm run auth password-link`). Tell people before the move.
- **Everyone is signed out.** Cookies are host-only, so the old host's never reach the new one.
- **OAuth providers.** The redirect URI is `APP_ORIGIN/api/auth/callback/<id>`: register the new one with each provider (Logto, Google, Clerk) before the move.
- **Links already sent** point at the old host: password links (three days), emailed resets and confirmations, Telegram sign-in links (15 minutes), approval links in Telegram (`<APP_ORIGIN>/approvals/<id>`) and the `/apps?promote=` link in an app promotion request. Make new ones; a redirect from the old host to the new one keeps the approval links working.
- **Host and origin checks.** The API answers only on `APP_ORIGIN`'s host (and loopback) and accepts only that `Origin`, and Better Auth trusts only that origin: requests to the old name get "Unrecognized host" unless the proxy redirects them.
- **Mini apps.** `APPS_HOST` defaults to `apps.<APP_ORIGIN host>`, and app addresses follow it. Sessions on the old app hosts are lost (people open the app again); `CB_APP_URL` in an app's `.env` file is rewritten when its token is (after a restart of the app server, or when a day is left), so restart running apps after the move.
- **Web reads.** The declared agent User-Agent links to `<APP_ORIGIN>/agents`; that page must be reachable on the new host.

Not bound to the hostname: data, accounts and roles, password hashes, OAuth links, `SESSION_SECRET` (keep it), data tokens and computer, supervisor and apps runtime tokens (these use the internal network, `DATA_API_URL`, not `APP_ORIGIN`), and Telegram links between accounts.

### OAuth and OpenID Connect providers

Each provider is an OpenID Connect issuer with discovery. Its callback (the redirect URI to register) is `APP_ORIGIN/api/auth/callback/<id>`.

| Variable                                          | Purpose                                                                                             |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `AUTH_OAUTH_<ID>_ISSUER`                          | Issuer URL (https; http only on loopback); discovery is `<issuer>/.well-known/openid-configuration` |
| `AUTH_OAUTH_<ID>_DISCOVERY_URL`                   | Instead of the issuer, the full discovery URL                                                       |
| `AUTH_OAUTH_<ID>_CLIENT_ID`                       | The application's client id                                                                         |
| `AUTH_OAUTH_<ID>_CLIENT_SECRET[_FILE]`            | Its secret (sent with HTTP Basic); leave unset for a public PKCE client                             |
| `AUTH_OAUTH_<ID>_NAME`                            | Button label ("Sign in with Logto"); default the id                                                 |
| `AUTH_OAUTH_<ID>_SCOPES`                          | Default `openid profile email`; must include `openid`                                               |
| `AUTH_OAUTH_<ID>_GROUPS_CLAIM`                    | Claim holding groups or roles (default `groups`)                                                    |
| `AUTH_OAUTH_<ID>_ADMIN_GROUP`, `…_ALLOWED_GROUPS` | Groups that make an admin, or may join as members (comma-separated)                                 |

`<ID>` is the provider id in upper case, dashes as underscores. The flow is the authorization code with PKCE, `state` and an ID-token `nonce`; ID tokens are verified against the issuer's published keys (issuer, audience, expiry, nonce). Claims the ID token lacks (the email, the groups claim) are read from the userinfo endpoint. The app server talks to the issuer itself (discovery, keys, token, userinfo), so it must reach the issuer URL and trust its certificate; for a self-signed proxy certificate, mount the CA and set `NODE_EXTRA_CA_CERTS`. If the issuer is down at startup, a later sign-in retries discovery (at most every 30 s). Signing out of Socio doesn't sign people out of the provider.

### Purge test records

Deactivating, archiving and deleting in the app keep the rows. To remove test people, socios, Spaces, pages, datasets, apps, jobs, rooms and conversations for good, an operator runs `purge` on the server with an explicit id list:

```sh
docker compose --env-file .env -f .docker/compose.yml exec app node dist/server/server/purge/purge-cli.js --list /tmp/purge.json --protect /tmp/protect.txt
docker compose --env-file .env -f .docker/compose.yml exec app node dist/server/server/purge/purge-cli.js --list /tmp/purge.json --protect /tmp/protect.txt --apply
```

`purge.json` lists the ids by kind (`users`, `socios`, `spaces`, `pages`, `datasets`, `apps`, `jobs`, `rooms`, `conversations`) and, optionally, `"cascade": true` or the kinds it may add on its own. `protect.txt` lists ids that must never go, one per line. Without `--apply` it is a dry run: it prints the rows each table would lose, the files and stored objects with their bytes, and the history that stays (comments, board events and audit rows keep naming the removed ids). It refuses unknown or protected ids, active operators and admins (deactivate them first), schedules and coding sessions that name a listed record, rows that belong to a protected record, and records under a listed one (a person's socios, a Space's pages) that the list neither names nor cascades to. `--apply` plans again in its write transaction and stops if anything differs, backs up the database, the data spaces and each object it deletes into `BACKUP_DIR/purge-<time>/`, deletes the rows in one transaction, then the files and objects, and records one audit line as `cli`. Where computers run (`COMPUTER_SUPERVISOR_URL`), the dry run also lists the purged socios' computers, and after the commit the supervisor removes each one's container and its three volumes (`POST /computers/:id/destroy`); with a supervisor older than this route, a purge of any socio refuses before deleting anything (`--keep-computers` leaves the computers instead); `COMPUTER_SUPERVISOR_URL` without its token is an error. Which columns go with which record is in `src/server/purge/references.ts`. Operators can purge one person from the web too (People → Remove permanently, `POST /api/accounts/:id/purge`, CB-360): the same plan, backup, checks and audit line (under their own id, not `cli`), with the server's own `DATABASE_PATH`, `USER_DATA_DIR`, `BACKUP_DIR`, `S3_*` and supervisor settings. It never cascades: it refuses until the person is deactivated and an admin has transferred everything they own (`POST /api/accounts/:id/transfer`; what moves is in `src/server/purge/ownership.ts`), and asks for their name and a step-up before it applies. Each `purge-<time>` backup lives `PURGE_BACKUP_DAYS` (default 30, 1 to 365; an admin changes it in **Settings → General → Backup schedule**, CB-391): the first scheduled backup after that removes it, so the deleted data leaves the backups too. One whose cleanup still waits for `--resume` (`cleanup.json` with `"done": false`), or whose `cleanup.json` can't be read, stays (logged). `pnpm run backup` by hand can't read Settings and leaves them for the next scheduled backup. Purge backups are never sent off-site.

To copy a chosen set of issues, Spaces and pages from one Socio to another (CB-380), an operator exports a **workspace bundle** on the source (`node dist/server/server/bundle/bundle-cli.js export`, from a `VACUUM INTO` snapshot or `--from` an opened backup) and imports it on the target. To import in the running server, put the bundle under the target's `BACKUP_DIR/bundles/` and call `POST /api/operator/bundles/import`. To import offline, use `bundle-cli.js import`. The export requires a deny-list of Spaces it must never read: `--deny-space`, or `BUNDLE_DENY_SPACES` (comma-separated Space ids). The import is a dry run until `apply`, which needs a backup from the last 15 minutes and copies the database to `BACKUP_DIR/import-<time>/` first. See the operator help, Workspace bundles (`content/docs/operate/workspace-bundles.md`).

## Telegram

Your team can talk to a socio from a Telegram group with topics, and by direct message. Every turn is stored like a browser conversation and counts as Learning evidence.

### Create the bot

1. In Telegram, open [@BotFather](https://t.me/BotFather) and send `/newbot`. Choose a display name and a username ending in `bot`. BotFather replies with a token like `123456789:AA…`. Treat it as a password.
2. Optional: send `/setprivacy`, pick the bot and choose **Disable**. This lets the bot see every group message. An admin bot sees them anyway, and it only answers when mentioned or replied to.
3. Once your group is set up, send `/setjoingroups` and choose **Disable** so nobody can add the bot to other groups.

### Set up the group

1. Create a group, open its settings and turn on **Topics**. This makes it a forum supergroup.
2. Add the bot as a member, then promote it to **admin**. It needs no special rights beyond reading and sending messages.
3. Send any message in the group. Then get the chat ID without echoing the token:

    ```sh
    curl -s "https://api.telegram.org/bot$(grep ^TELEGRAM_BOT_TOKEN= .env | cut -d= -f2)/getUpdates" | grep -o '"chat":{"id":-[0-9]*'
    ```

    A supergroup ID starts with `-100`. Run this before starting Socio, which long-polls the same updates.

### Configure Socio

| Variable                    | Purpose                                                                           |
| --------------------------- | --------------------------------------------------------------------------------- |
| `TELEGRAM_BOT_TOKEN`        | The bot token; leave empty to disable Telegram                                    |
| `TELEGRAM_POLLING`          | `true` in the one process that long-polls the bot; otherwise the token is ignored |
| `TELEGRAM_ALLOWED_CHAT_IDS` | Comma-separated group IDs the bot answers in; other groups are ignored            |
| `TELEGRAM_DOT_ID`           | The socio that answers in Telegram; defaults to the first socio                   |

Restart the server. **Settings & setup** and the sidebar status line show Telegram as online, connecting or not connected. They never show the token or chat IDs. Only one process may long-poll a bot, so only one server may set `TELEGRAM_POLLING=true` for a token. A token inherited from your shell is ignored unless that variable is set.

### Link accounts

Each person links their own Telegram account:

1. In the app, select **Telegram** in the sidebar (under Learning), then **Link Telegram**.
2. Open the `t.me/<bot>?start=…` link and press **Start**. The link works once and expires after 10 minutes.

The bot then knows that Telegram account by its numeric ID, never by name or username. An unlinked person gets a reply explaining how to link, and nothing runs. Unlink from the same dialog. Relinking moves the Telegram account to the newest app user who redeemed a code. With Better Auth, a linked Telegram account also receives [sign-in links](#sign-in-links-by-telegram).

### Where conversations appear

- **Direct messages** are a private conversation of the linked user. They appear in that user's sidebar and can be continued in the app.
- **Forum topics** are team conversations, one per topic. They appear, marked _Team_, for every linked user who has spoken in that group outside a topic linked to a room, and are read-only in the app: nobody can rename or delete them there. Each turn runs as the person who sent it, using only the memories and profile they marked for team chats. A topic bound to a room is that room instead (see [Rooms in forum topics](#rooms-in-forum-topics)).
- **Ordinary groups** without topics get one conversation per person. The group reads the replies, so these turns too use only what the person marked for team chats.

In groups the bot answers when mentioned (`@yourbot …`) or replied to. When Socio is paused, the bot says so and does not run. Channel posts and channel direct messages are not supported.

### Direct messages

A direct message is a full client of the person's socio features (CB-145). The bot registers its command menu for direct messages (`setMyCommands` with the `all_private_chats` scope). The menu holds its own commands, then every chat skill with hyphens as underscores. It checks the skills once a minute and registers the menu again when they change. Groups get the chat skills (`all_group_chats`), and their admins `/bind` first (`all_chat_administrators`, CB-214).

- **Commands the bot answers itself:** `/new` (a new conversation with the same socio), `/socio` (choose the socio from buttons, or `/socio Name`; company socios and the person's own), `/stop` (stops the answer in progress), `/memories` (proposed memories with buttons) and `/jobs` (the person's jobs that run until done). They never reach a socio. No chat skill can take these names. `/new` and switching socios start a new app conversation. The earlier one keeps its Telegram link, so an approval decided there still carries on in the direct message. The socio picked last stays the person's socio there; `TELEGRAM_DOT_ID` is only the default.
- **Buttons:** an approval notice has **Approve** and **Deny**. A memory a socio proposed during a direct-message turn is offered after the answer with **Keep** and **Turn down**. A press acts as the linked person who pressed it, checked as the app's routes check the signed-in person, and is answered in Telegram.
- **Reactions:** 👍 and 👎 on a socio's answer are that answer's reactions (CB-133). The bot records which of its messages show which answer (`telegram_replies`).
- **Jobs:** a job that runs until done and was started from a direct message keeps one progress message there, edited at most every 15 seconds and when the job ends. The socio's own report of the end follows, as before.

### Rooms in forum topics

With Rooms on, a forum topic can be bound to a room (CB-214). That is how socios work in a group: in a bound topic, a message from a room member that mentions the bot, replies to it or names it in a command (`/compact@yourbot`) is a room turn, run as that member, and the socio's reply is posted in the topic. Everyone else is not answered: a linked person who isn't in the room, an unlinked account, and anyone while the room is archived or Rooms are off. Their message never reaches the room or another person's turn. The first time each of them addresses the bot there, it replies once saying why, and the room's admins see them in the room's **Telegram topic** dialog.

- **Binding needs one person to prove both sides.** A room admin selects **Telegram topic** in the room's **⋯** menu, confirms who reads the topic, and gets a one-time code (10 minutes). They post `/bind@yourbot <code>` in the topic from their linked Telegram account. The bot asks Telegram (`getChatMember`) whether the sender is an admin of the group, and binds the topic only if they are and the code is theirs. A code works once. A topic maps to one room at a time, and a room to one topic.
- **Legacy topics stay as they were.** A topic nobody bound keeps the behavior above: its readers, its transcript and its turns. Writing in a topic linked to a room doesn't make anyone a reader of the group's team topics; writing anywhere else in the group still does. A person who reads one can select **Make this topic a room…** under its transcript and post the code the same way. That makes a new room with them as its admin and the topic's socio as its lead, and binds the topic. The legacy transcript stays read-only for the people who read it, and the room starts empty. Nobody becomes a member without an invitation they accept. The room's admins see the linked people seen in the group as suggestions to invite.
- **Archiving the room unbinds the topic.** So does **Unlink topic** in the dialog. After that the topic answers no one, and it doesn't fall back to a legacy team topic. A room admin binds it again with a new code, after unarchiving.
- **Messages written in the app stay in the app.** Nothing from the app is posted to the topic. The socio's reply to an approval decided later shows in the room, not in the topic.
- **Storage:** `room_source_bindings` (rooms module) holds the binding. Telegram migration 3 adds `telegram_room_codes` (hashed one-time codes) and `telegram_topic_senders` (who wasn't answered, per room and reason, with an @username at most). Both are expand-only.

The bot needs no further rights to check group admins. In privacy mode it still receives `/bind@yourbot` and mentions.

## Notifications

Socios can notify the person they work for with the `notify_user` tool (CB-114). Typical cases: unattended work finished or needs them, a problem turned up, or a decision only they can make. That person is the one in the chat, or whoever owns the schedule or goal. A socio never notifies anyone else, and its tool takes no recipient: the server decides from the turn.

**Notifications go out only when the person is away.**

- **The signal:** each open tab reports on its 3-second poll whether it is in use, meaning visible and focused with keyboard, pointer, touch or scroll input in the last minute. Hiding or closing a tab reports it away at once. On Telegram, a message from the person in the last two minutes counts as being in that chat.
- **Looking at the chat:** nothing is sent, and the socio says it in its reply.
- **Elsewhere in the brain:** it shows as a pop-up in the app.
- **Otherwise:** it goes to the person's channels.
- **Missing or stale signals** count as away, so a closed laptop never holds a notification back.

**Each person picks their channels** in **Settings → Account → Notifications**.

- Each channel has an on/off switch and a choice between showing the socio's message or keeping it private ("Ada needs you", with no text or image).
- **Push** (Web Push) starts on once a device is added. Use **Turn on for this browser** in each browser or installed app.
    - On iPhone and iPad, push works only in the app added to the Home Screen (iOS 16.4 or later), so add it first, then turn notifications on inside it.
    - Windows, macOS and Android work in the browser or the installed app.
- **Telegram** starts off: bot messages are stored readable on Telegram's servers. It needs a [linked account](#link-accounts).
- **Send a test notification** checks the channels that are on.

**What leaves the server:**

- **Push.** Each push is encrypted for its browser (RFC 8291) and signed with the server's key (VAPID). The push service sees only the ciphertext, the endpoint and the timing: Google for Chrome and Android, Microsoft for Edge on Windows, Apple for Safari, iPhone and iPad, Mozilla for Firefox, and the mobile app's push relay (a Cloudflare Worker) for the Socio app. The production network must reach those services.
    - The key pair is made on first start and sealed with the data key.
    - The VAPID subject is `APP_ORIGIN`, never an email address.
    - Only endpoints on those services, or on the mobile app's push relay, are accepted: `*.googleapis.com`, `*.notify.windows.com`, `*.push.apple.com`, `*.push.services.mozilla.com`, and the relay's exact hosts `push.socio.sh` (production) and `push-staging.socio.sh` (staging). The relay is named host by host, never `*.socio.sh`, which would let any other host on the domain receive pushes. A later host change adds the new host and keeps the old ones until phones have re-registered.
    - `PUSH_ENDPOINT_HOSTS` (comma-separated) replaces that list. A deployment that sets it must include the relay's hosts, or every phone's subscription is refused and deleted at the next send. Staging bench tests against a relay on workers.dev set it explicitly, with that relay's host.
- **Telegram.** The bot sends the text, and an image as an upload.
- **Images.** A socio may add an image: an attachment or Media item, or a public URL. The server downloads a public image once, through the socio's web reads, and checks it is a PNG, JPEG, GIF or WebP of 1 MB at most. Devices load it only from the brain, at a random `/notification-images/…` address that expires after 7 days, so the image's site never sees who opened it. Only some devices show it (Chrome and Edge on Windows and Android); private mode never includes it.

**Limits:**

- **Daily caps:** 20 a day from each socio for a person, and 40 a day for a person from all socios. `NOTIFY_PER_DOT_DAILY` and `NOTIFY_PER_USER_DAILY` set them, and an admin can change them in Settings (0 turns notifications off).
- **Record keeping:** each notification is recorded with the turn that sent it, the presence decision and each delivery, and kept for 90 days.
- **Text-only turns** have no tools, so they don't notify.

## Pages and page conversations

A Space is for the whole workspace or private to its people (CB-181): choose when making it (anyone may make a private one; only admins make or open one for everyone) and under its **Settings** tab. Who may create Spaces at all is the workspace's "create Spaces" permission: **Settings → General → Spaces → Members can create Spaces**, on by default; an admin who turns it off keeps creating Spaces to admins, and members then get a 403 and no **Create Space** control (`spaceCreators` in `PATCH /api/settings`: `everyone` or `admins`). A socio can make one for the person it acts for with `create_space`, only once they approve it on the approval card (always: no bypass or automatic review), private to them unless they are an admin who asked for one for the whole workspace; the socio is given the new Space (CB-271). A Space's editors (workspace admins edit every Space) rename it under its **Settings** tab, or through a socio's `rename_space` for a Space the socio was given (CB-366, `PATCH /api/spaces/:id` with `{ "name": "…" }`): only the name changes, by the same name rule as a new Space, and links keep working because they name the Space's id. Private covers everything in it, and people outside it get a 404 for it, as for a Space that isn't there. See [MEMORY.md](MEMORY.md#private-spaces-cb-181).

Select a Space to open its page library. Search for a document, switch between grid and list views, or create a new page. The visual editor supports formatting, headings, lists, checklists, tables, and slash commands. Use `/` to insert a block and Cmd/Ctrl+S to save immediately. Pages autosave after editing pauses; the save status tells you whether changes reached the server.

Page actions include creating subpages, moving a page within its Space, and editing Markdown source. Existing documents with unsupported visual-editor syntax stay in source mode to preserve their content. Manual editing works without conversation credentials.

**Move to…** in a page's ⋯ menu moves it to another Space, with its subpages; it goes to the top of that Space. Anyone who can edit pages in both Spaces may move it (every person who can see a Space can edit its pages; service account keys can't). The page keeps its id, so its history, conversations and review receipts stay with it, and links to its old address (`/spaces/<old>/pages/<id>`) open it where it is now (`GET /api/pages/:id/location` says where). Your unsaved changes are saved first. A socio does the same with `move_space_page`, only between Spaces it was granted, and only for a person who could move the page themselves. Each move is recorded in the workspace audit (`move` on the page). Its pictures, its link cards' images and its cover are copied into the new Space with it, so that Space's readers see them; images of other Spaces it names are left as they are. Subpages that were deleted before the move stay in the old Space. A dataset view embedded in the page shows its data to others only where its dataset is shared, so share it with the new Space if needed.

Open a page's chat and choose a specialist with access to that Space. Grant access from the socio’s settings in the sidebar. The server creates or reuses a conversation for that page and specialist. The socio receives the current saved page as context and can read, create, and edit pages in its authorized Spaces. The page conversation uses that page’s Space by default; other chats use the socio’s default page destination. Save your manual edits before asking it to revise the document. Revision checks reject stale writes; a conflict keeps your local draft available for recovery. Failed saves stop automatic retries until you retry or resolve the conflict, so a disconnected session does not silently replace newer content.

Use the conversation's save-to-page action to create a document from its saved text history. It uses the conversation's stored history. Pages retain a link to the source conversation, and page links in chat open the document workspace.

Everything (pages, workspace configuration, conversation history and scheduled work) lives in the SQLite file at `DATABASE_PATH`; back up that file (with its `-wal` file, or after a clean shutdown). Realtime collaboration, file uploads and arbitrary interactive embeds are not included.

## Inline charts in chat

Socios can use `format_chart` to format supplied observations as a single-series bar or line chart (CB-242). The reply carries a versioned `socio-chart` JSON fence and an ordinary Markdown summary/data table. Socio renders up to three charts per assistant message with native SVG, readable labels and keyboard point inspection; the table stays readable in clients without rich charts. User messages, reasoning, malformed data and incomplete streaming fences stay ordinary Markdown/code.

Each chart has at most 100 points and 24 KiB of data. Unknown values stay `null` and leave gaps; the tool fetches no data and does not verify its authenticity. Historical charts, including burndowns, need actual dated source data: the formatter does not invent it. Labels are text, and chart data cannot request HTML, scripts or external resources.

## Messages while the socio works

While a socio's turn runs in the web chat, the person can keep writing (CB-151). The composer keeps **Stop** and, once there is text, adds a send button that queues it; Enter does the same. A queued message shows faded at the end of the chat, "Queued · socio reads this after its current step", with **Edit** and **Cancel** until the socio takes it. Attachments wait for the next message once the reply is done. At most 5 messages can wait per chat and person (Settings → General → Socio replies → Queued messages per chat, 1 to 20, over `STEERING_MAX_QUEUED`; CB-170). The server checks it on each new one; with the queue full the chat says so in a quiet note and the text stays in the box. Lowering the limit leaves what already waits.

**When the socio reads it.** Queued messages are kept on the server, per conversation and person (the `chat_steering` table), so a reload or a reconnect still shows them. The running turn takes them at its next safe point: once the tool calls of its current round have all finished and before its next model round. They go into the conversation there as the person's message, after the tool results, and the model reads them in that round and can change course. A tool call is never interrupted, and a call is never separated from its result. Several queued messages go in order, as one message of the person's (consecutive messages are merged, CB-147). When the turn ends before a safe point (its round answered without tools, it hit a limit or its time limit, or failed), the server starts the next turn with them, as the person's own, and the chat follows it as it follows a socio carrying on after an approval. **Stop** never drops them either (CB-170): they stay in the chat, with **Edit** and **Cancel**, until the stopped turn has ended, and then go as the next turn, in order and once; the chat follows that turn even when it reconnected to the stopped one first. A turn that waits for the person (a page review or an approval) leaves them to the turn that carries on; so does a pause, a restart or an operator's force stop, and the server picks them up when it starts again, or when an admin resumes Socio.

**Once, never lost.** A turn takes the queued messages in one statement that removes them, and sends them to the chat at once, so a busy model's retry, a fallback to the shared model (CB-140) or a prompt refitted after compaction (CB-129) sends the same round again with them in it, without taking them again; an edit or a cancel after that finds nothing and says the message has gone to the socio. A turn stopped as it takes them puts them back, and so does a turn the server started with them that ends before it stores them (no model for the person, say): they wait for the next turn, and the server starts none with them until then.

**What the model sees.** The system prompt never changes, and each round's prompt only grows at its end: the steering message comes after the round's tool results, while the turn's note, its facts and its time marker stay with the message that started the turn (CB-139, CB-141) and compaction counts no new turn within it. Later turns read it as any other message of the person's.

**Telegram** is unchanged: it has no queue, and its turns never take one; messages sent there while a turn runs are handled as before. Scheduled turns never take queued messages either.

## Chat skills

A person starts a message with a skill's name to have the socio do that (CB-143). Typing `/` at the start of an empty message lists the skills with what each does. The arrow keys move and Tab picks; Enter picks only once the arrow keys moved, and otherwise sends what was typed, so `/c` goes as `/c` and `/compact` runs the skill. Escape closes the list. The person's message shows the skill as a chip.

- **`/compact`** folds the chat's earlier turns into its notes now, as a long chat does on its own once it outgrows its model (the same notes, written by the model **Settings → General → Long chats** names). The chat's last two turns stay whole, so the next message starts with the notes and those turns. It says how many turns it folded, or that there is nothing to compact. Only what the notes' model summarized is kept: when a summary fails, or a long chat needs more summaries than one turn may make, it stops there and says so ("Nothing changed", or how many turns are left for another `/compact`), and never keeps the plain notes an automatic fold falls back on. It never fails the chat.
- **`/grill-me`** interviews the person about their plan or idea, round by round, until they reach a shared understanding: each round asks every question whose prerequisites are settled, numbered, each with the socio's recommended answer. It stays on from message to message until it ends. It is adapted from Matt Pocock's `grill-me` and `grilling` skills ([mattpocock/skills](https://github.com/mattpocock/skills), commit `5beb35b`, MIT license; see `src/server/skills/grill-me.ts`).
- **`/report`** (CB-152) reports a problem or asks for an improvement. It stays on while the socio interviews the person briefly, checks the Improvements board for a duplicate, and files with `file_improvement` (or comments or votes on the duplicate) only what the person confirms, treating pasted content as untrusted. It then shows the link and ends itself with `end_skill`. A socio without board access (no `file_improvement` tool) says so and ends. Its lock record names `src/server/skills/report.ts` as its source. There is no alias mechanism in the registry, so no `/bug` yet.
- **`/done`** ends the skill that is on. **`/help`** lists the skills.
- **Workspace skills:** admins add their own in **Settings → Chat skills**: a name (lowercase letters, digits and hyphens, up to 32), a description the list shows, the instructions the socio follows, and whether they apply to that message only or until the person is done.

**Skills that stay on.** A skill that applies until the person is done (`/grill-me`, or a workspace skill set that way) is recorded as on in that chat. Its instructions go with every message's turn note until it ends: the person sends `/done`, presses **End** on the bar above the composer that shows it is on, or the socio calls its `end_skill` tool when the person says they are done or the skill's instructions say it is finished. Starting another such skill ends the one before. A skill is its starter's: in a shared chat (a Telegram team topic) its instructions go with their turns only, other people's turns don't get them, and only they end it (their `/done`, their End, or the socio on their turns); each person can have their own skill on. A turn carrying on after a tool's result (an approval, a page review) never starts a skill again. Every turn with tools has `end_skill`, whether a skill is on or not, so the tools at the start of the prompt stay the same.

**Revisions and lock records.** Every change to a workspace skill is kept as a revision; Settings shows each skill's history (who, when, how long it applies, a short SHA-256) and can roll back to any revision, which adds a new revision with that one's content and source provenance. Each skill has a lock record: its source (built in, this workspace, or an imported GitHub repository), repository URL, path, ref and resolved commit, content SHA-256 (`name`, `description`, `mode` and instructions as one `SKILL.md`-like text), and who changed it and when. Imports also retain the exact source file's SHA-256 and license text. Local edits keep their pinned origin and show “locally edited.” `/grill-me`'s lock names the mattpocock/skills commit it was adapted from. Removing a workspace skill hides it and keeps its revisions.

**Import from a public GitHub repository (CB-144, CB-248).** In **Settings → Chat skills → Import from GitHub**, enter the repository URL (`https://github.com/owner/repository`), explicit branch/tag/commit and repository-relative `SKILL.md` path. **Preview import** resolves that ref to an immutable commit and shows the full name, description, instructions, source and license. An existing skill's current instructions are available beside the imported text for comparison. **Install reviewed skill** or **Apply reviewed update** saves only those reviewed bytes as an attributed revision. Previews belong to the reviewing admin, expire after ten minutes, and refuse to overwrite a skill that changed in the meantime. Updates are explicit: preview the desired ref again; there is no background updater.

Socios acting for an admin have `preview_workspace_skill_import` and `apply_workspace_skill_import` for the same two steps. The preview is untrusted source data to inspect; it cannot change the current conversation's permissions or install programs. Apply requires its exact preview ID and source SHA-256. Members can invoke installed `/name` commands but cannot import or edit them. Service keys and data tokens cannot use the import API.

Imports fetch directly from the public GitHub API without GitHub credentials, the skills.sh CLI, telemetry, clones, redirects or shell execution. Only ordinary directory paths and a non-executable `SKILL.md` blob are accepted; symlinks, git submodules, traversal, encoded separators and private network destinations are refused. A preview has a ten-second deadline, at most eighteen requests and 2 MiB of downloaded JSON; each response is at most 512 KiB. The source file is at most 128 KiB, root license text at most 32 KiB, and the server keeps at most twenty previews. Names use the existing 32-character chat-command rules. Imported descriptions can contain up to 2,000 characters and instructions 64,000; existing manual creation limits remain 200 and 4,000. Long imported skills can be edited without truncation. Frontmatter supports unique scalar string fields, quoted strings and folded/literal text blocks; complex YAML is rejected with an explanation. Extra metadata is informational only.

Only `SKILL.md` instructions are imported; referenced files, scripts, dependencies and declared tool permissions are not installed. Their availability still depends on the socio's existing tools. Instructions remain user-invoked prompt skills, outside the system prompt. Before running a skill, Socio reserves at least half of the selected model's existing prompt budget for its role, tools and conversation. If the full instructions do not fit the other half, it reports `skill_context` and asks for a larger-context model or shorter skill; it does not silently clip them or enlarge the model's context limit. This guard also applies to a fallback model.

**What the model sees.** `/compact`, `/help` and `/done` run on the server. When the message was the name alone, its turn and the server's answer are left out of what the model sees later (only answers the server marked, so a `/help` in a chat from before skills stays). Text or files after the name go on to the socio as a turn of their own, after the server's answer, and stay in the chat; later turns show the model the server's answer as the start of the socio's answer, so the roles still alternate. The instructions of `/grill-me` and of workspace skills go in the turn's note, after the part of the prompt that stays the same; never in the system prompt, so a model's prefix cache still holds. A `/word` that names no skill is sent as the text it is; the server also finds a skill's name after the page a page chat puts first. Dispatch runs, whose text is untrusted, never run skills.

On Telegram the same skills are commands, with underscores for hyphens (`/grill_me`); `/help` lists them that way. In a group, send a command with the bot's name (`/compact@yourbot`, as Telegram's command menu writes it) or as a reply to the bot; a command for another bot is ignored. Every other command now reaches the socio as text. The bot doesn't register its command list with Telegram, so Telegram's own command menu doesn't show them.

## Browser tool

Parallel is selected by default (`WEB_SEARCH_PROVIDER=parallel`). Live research needs the model configuration, but no browser worker. An optional server-side `PARALLEL_API_KEY` enables authenticated usage and higher limits. The anonymous MCP endpoint is free for light use. Queries, selected URLs, research objectives and a stable session identifier go to Parallel.

Search goes through a `SearchProvider` interface (`src/server/search/`). Set `WEB_SEARCH_PROVIDER` to choose one:

| Value      | Behavior                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------ |
| `parallel` | Default. Searches and reads pages. Keyless use is free and rate-limited.                                     |
| `searxng`  | Your own SearXNG at `SEARXNG_URL` with its JSON format enabled. Answers from search snippets; no page reads. |
| `disabled` | No web research.                                                                                             |

`brave` and `tavily` are planned. When a provider answers HTTP 429, the socio is told that search is rate-limited and continues without web sources; the result pane shows the same notice.

## Calls

Calls run on one of two backends (CB-265), an admin's choice in **Settings → General → Calls** over `VOICE_BACKEND` (`cloud` when unset). Calls use the browser's microphone, so hosted deployments need HTTPS.

**Cloud** (`cloud`) uses OpenAI's Realtime API at `api.openai.com` over WebRTC. Set `VOICE_API_KEY` to a key with access to that API and `VOICE_MODEL` to a supported Realtime model; `VOICE_NAME` selects the voice. `OPENAI_BASE_URL` changes the compute model endpoint only, not speech. The realtime model speaks for the socio and delegates research to the socio's own turn (`ask_compute`, at most six a call); after the call a receipt turn records it.

**Self-hosted** (`self-hosted`) keeps the audio on your servers, and every turn of the call is a normal turn of the socio:

- **Speech to text:** the transcription server in force (**Settings → General → Transcription**, `VOICE_TRANSCRIBE_*`) through its realtime socket, `{URL}/v1/realtime`, the OpenAI Realtime-style transcription session live dictation uses, with server VAD (socio-voice's `WS /v1/realtime`). It must be `wss` (an https URL), or `ws` to this machine, and not OpenAI's; the same key rules as dictation apply (CB-204: the key goes as `Authorization: Bearer` to that URL only, never across a redirect). Live dictation's own setting (`VOICE_TRANSCRIBE_STREAMING`) doesn't turn calls off.
- **The socio's turn:** when the person stops talking (600 ms of silence), what they said goes through the runner as the chat owner's own message (their sender stamp, the socio's model, tools, permissions, approvals, turn and work-cycle limits), stored in the conversation like a typed message, with a note to the model that it was spoken and that the answer will be read aloud (not stored). What is said while a turn runs goes in the next turn, together. An approval the turn asks for shows in the call as "Approval needed" and waits in the chat.
- **Text to speech:** the speech server, `POST {VOICE_SPEECH_URL}/v1/audio/speech` (OpenAI's API: `model` `VOICE_SPEECH_MODEL`, default `kokoro`; `voice` `VOICE_SPEECH_VOICE`, default `auto`; `input`; `response_format: "pcm"`, 16-bit mono at 24 kHz), streamed back to the browser in pieces of a sentence or two. The reply is spoken without markdown, code or links, at most about 1,200 characters ("The rest is in the chat"). `VOICE_SPEECH_API_KEY` (a `_FILE` secret) goes only to `VOICE_SPEECH_URL`'s origin; a speech URL at the transcription server's origin gets the transcription key in force; any other gets none. A key goes only over https (or to this machine), and redirects are refused. With no speech URL, or when it fails during a call, the browser speaks the reply with its own voice (`speechSynthesis`) and doesn't send the microphone while it does.
- **Down:** when the realtime socket can't be opened (refused, 5xx, a timeout of 10 s), the call ends before it starts with the reason ("The self-hosted voice server isn't answering…", "…refused Socio's key…", "…has no realtime socket…"), the call is saved as failed, and when cloud is set up too the chat offers **Use cloud voice** for that call. Nothing falls back to the cloud by itself.

`GET /api/workspace` says which backend is in force and whether it can take a call (`setup.voice`, `voiceBackend`, `voiceCloud`, `voiceSpeech`). A call lasts at most 15 minutes, one at a time per workspace; the audio is passed on and never stored. The browser streams 16 kHz PCM over `WS /api/voice/call?id=<call>` (signed in, the call's owner only) and plays the reply's 24 kHz PCM; it never sees a key.

socio-voice, a self-hosted voice server (CB-132), is a separate component that isn't published yet; it isn't part of this repository. For reference, a deployment of it serves the realtime socket at `https://voice.example.test`, and its `agent` service serves `POST /v1/audio/speech` (Kokoro-82M, `pcm` streamed, voices `auto` or an English/Spanish Kokoro voice such as `af_heart` or `ef_dora`) at `https://voice-agent.example.test`, a different origin from the transcription server, so the key goes in `VOICE_SPEECH_API_KEY` (or `_FILE`) with `VOICE_SPEECH_URL` set to that URL.

A configured key is not evidence of a successful call. Verify microphone access, audio playback, interruption, hangup, approvals and the conversation's messages (or, for cloud, compute delegation and the saved receipt) with your deployment before relying on voice workflows.

### Dictation

The chat composer's mic turns speech into text in the draft, which the person edits and sends. There are two ways, and each person picks theirs in **Settings → Account → Profile → Dictation** (stored on the server, so it follows them):

- **On this device**: the browser's own speech recognition (Web Speech API). Nothing reaches this server; the browser may use its maker's service (on iPhone, Safari may send the audio to Apple). Needs nothing on the server.
- **On our server**: the browser records (at most 2 minutes, 5 MB) and `POST /api/voice/transcriptions` passes it to the transcription server (below), by default OpenAI's `gpt-4o-mini-transcribe` at `api.openai.com`. The audio is passed through and not stored. Refused while the workspace is paused; it waits at most 60 seconds for the server. Where that server streams, the words show as they are spoken ([Live text](#dictation), below).

Only the ways that work are offered: with one, the mic uses it without asking; with none, there is no mic.

| Variable                     | Default                  | Meaning                                                                                                                                                                                        |
| ---------------------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DICTATION_METHODS`          | `both`                   | `both`, `device` or `server`: the ways to dictate the composer offers.                                                                                                                         |
| `VOICE_TRANSCRIBE_URL`       | `https://api.openai.com` | The transcription server's base URL (http or https); `/v1/audio/transcriptions` is added, and a trailing `/v1` is dropped.                                                                     |
| `VOICE_TRANSCRIBE_MODEL`     | `gpt-4o-mini-transcribe` | The `model` sent with each recording.                                                                                                                                                          |
| `VOICE_TRANSCRIBE_API_KEY`   | unset                    | Its key (a `_FILE` secret), sent only to `VOICE_TRANSCRIBE_URL`'s origin, over https or to this machine. Unset: `VOICE_API_KEY` for OpenAI's URL, and no `Authorization` header for any other. |
| `VOICE_TRANSCRIBE_STREAMING` | `auto`                   | Live text while dictating: `auto`, `on` or `off` (see **Live text** below).                                                                                                                    |

An admin can change the ways in **Settings → General → Dictation**, and the transcription server's URL and model in **Settings → General → Transcription**; what they save there takes the place of the variables ("Use the server's default" goes back to them). The card says which key is sent (the one set there, `VOICE_TRANSCRIBE_API_KEY`, `VOICE_API_KEY` or none), never the key. `VOICE_TRANSCRIBE_API_KEY` goes only to the origin (scheme, host and port) of `VOICE_TRANSCRIBE_URL`, which is OpenAI's when unset: a URL saved in Settings at another origin gets no `Authorization` header, and the card says "No key is sent to this server (the key is set for <host>)."

**A key set in Settings (CB-204).** An admin can also set the server's key on the card (**Set a key**, then **Replace key** or **Clear key**). It is sealed under the data key ([Data encryption key](#data-encryption-key)) in its own table, never in the settings the browser reads: the API and the card say only whether one is set. It takes the place of `VOICE_TRANSCRIBE_API_KEY` for the URL it was set for and goes only there, as `Authorization: Bearer …`: never to another URL, and never to OpenAI unless OpenAI's URL is the one it was set for. Saving a new URL, or going back to the server's default, clears it (rather than asking first), so a key can't be sent to a new host by editing the URL alone; set it again for the new one. The card sends the key with the URL it shows, and the server refuses it ("The transcription URL has changed since this page loaded…") when another URL is in force by then, as from a stale tab or another admin's change.

A key set while the card shows the server's default URL is for that URL. If `VOICE_TRANSCRIBE_URL` then changes, the key stays bound to the old URL and is withheld: the new URL gets no key from it, and the card says "No key is sent to this server (the key is set for <old host>)". Clear it, or set it again for the new URL. Its URL is kept unsealed beside it (it isn't secret), so a key whose data key is gone stops dictation only at that URL, with "can't be opened… An admin replaces or clears it"; a keyless server, or OpenAI's with `VOICE_API_KEY`, still works.

Any key (the one set in Settings or `VOICE_TRANSCRIBE_API_KEY`) is sent only over https, or plain http to this machine (`localhost`, `127.x.x.x`, `[::1]`). There is no opt-in for plain http. The card refuses a key for a plain-http URL to another machine, and when a key is set for one, nothing is sent at all (no key, no audio). With `VOICE_TRANSCRIBE_API_KEY` and a plain-http `VOICE_TRANSCRIBE_URL` to another machine, the server logs a warning at start, and the card and dictation name the fix: "Voice setup required: VOICE_TRANSCRIBE_API_KEY is sent only over https (or to this machine). Set an https VOICE_TRANSCRIBE_URL, or unset VOICE_TRANSCRIBE_API_KEY." When the URL saved in Settings is at that key's plain-http origin, it says to change the URL to https in Settings, or unset `VOICE_TRANSCRIBE_API_KEY`. A server that needs no key may still be plain http. The request never follows a redirect, so the key can't reach another origin that way either: a redirect is refused, and people see "Voice provider redirected the request, which is refused…" (the log says `redirected (refused)`).

**A self-hosted transcription server.** Any server with OpenAI's `POST /v1/audio/transcriptions` works: it gets multipart `file` (`dictation.webm`, `.mp4`, `.ogg`, …), `model` and `response_format=json`, and answers `{ "text": "…" }`. No `language` is sent unless the person dictating picked one under Settings → Account → Profile → **Dictation language** (a bare ISO code such as `fr` or `yue`, also sent as `input_audio_transcription.language` on the realtime socket); with Auto, the default, the server detects it (Spanish or English, say). Loopback, private and tailnet addresses are allowed, over plain http too when the server needs no key; with a key, the URL must be https unless it is this machine. Point `VOICE_TRANSCRIBE_URL` (or the Settings card) at it, set the model name it serves, give it its key if it wants a bearer token (such as `https://voice.example.test`), and leave the key unset if it needs none: then the audio never leaves your network, and `VOICE_API_KEY` is not needed for dictation. Server dictation is offered when a transcription URL is set and either it isn't OpenAI's or a key for it is. Self-hosted calls use the same server's realtime socket ([Calls](#calls)); cloud calls use `VOICE_API_KEY` and OpenAI's Realtime API.

**Live text (CB-222).** Where the transcription server streams, the words show above the text box as people speak, as an unconfirmed preview (up to three lines, the newest in view). When they press Done, the preview stays, marked "Finishing…", while the whole recording is transcribed; that text replaces it in the draft, where they edit and send it as before. Cancel puts nothing in the draft and sends nothing more, but the audio so far has already streamed to the transcription server (passed on, not stored here). The browser captures the microphone as 16 kHz 16-bit mono PCM with an AudioWorklet (`public/dictation-worklet.js`: a windowed-sinc low-pass filter, then resampling from the device's rate; AudioWorklet is in Safari 14.5 and later and in Chrome, and this path is designed for iPhone but not yet checked on a device; MediaRecorder isn't used for it, since iOS records only mp4 with it) and streams it to this server over a WebSocket at `/api/voice/realtime`. That socket is an API request like any other: the same host, origin, cross-site and sign-in checks, a person's session only (no service key or data token), refused while paused. This server relays the audio to the transcription server's realtime socket, an OpenAI Realtime-style transcription session such as socio-voice's (`transcription_session.update` with `pcm16` at 16 kHz, `input_audio_buffer.append`, then `input_audio_buffer.commit`; it reads `conversation.item.input_audio_transcription.delta` and `.completed`), and sends the browser only the text, so the key never reaches it. The audio goes on in appends of 100 ms to 2 s, the rest with Done, and is held in one buffer while the server answers the socket; a frame under 10 ms (320 bytes) is taken only as the last one before Done (a second ends the session as if Done were pressed), and a server that falls more than 1 MB behind ends the session (`fell behind` in the log). Knowing the text is final relies on the transcription server handling a session's messages in the order they come, as socio-voice and OpenAI do: after Done, Socio sends `input_audio_buffer.commit` and then a session update, and takes the update's answer to mean every `...completed` before it has arrived. The realtime URL comes from the transcription URL: the same host, port and path plus `/v1/realtime`, over `wss://` for an https URL and `ws://` for http (`https://voice.example.test` → `wss://voice.example.test/v1/realtime`). Every key rule above holds for the socket: the key goes as `Authorization: Bearer …` only to the realtime URL of the URL it is bound to; the socket is only `wss://`, or `ws://` to this machine, with a key or without one (a plain-http server on another machine gets recordings, never a socket); and a redirect is never followed (the log says `Voice: live text at <host> redirected (refused).`). A session lasts at most the recording's 2 minutes (then it ends as if Done were pressed) and takes at most that much audio; each person has one at a time (a new one ends the older) and starts at most 10 a minute, and 20 run at once in all. A pause, and a server draining for a restart, end the sessions open; their composers send the recordings. While draining, a new socket is refused (409) and the composer records instead. The audio is passed on and never stored.

The browser keeps what it captured meanwhile, and the streamed text is only a preview: on Done it sends that recording (as WAV) once to `/api/voice/transcriptions`, the same as recording and sending, and its text is the final one, as good as recording and sending (the streamed final text, its turns decoded one by one, scored slightly worse: 4.3 % against 4.0 % word errors on 24 test clips). The final text comes about 0.6 s after Done instead of 50 ms, and the audio reaches the transcription server twice: streamed, then as the recording. Only when that request fails, or takes over 15 seconds while a streamed final text has come, does the streamed text count; without one, Done waits for the recording's text as long as that takes, as when recording and sending. When neither gives any text, the recording's error shows, as today, and a browser that lacks something this needs (an older Safari) shows an error rather than waiting for ever. When the socket can't open, the server has no realtime socket, or the stream drops, there is no preview, and Done sends the recording all the same, once. An admin picks the behavior in **Settings → General → Transcription → Live text**, over `VOICE_TRANSCRIBE_STREAMING`: **Automatic** (`auto`, the default) streams to any server but OpenAI's (its batch API has no such socket here); a server that answers that it has no such socket (HTTP 404, 405 or 426), or doesn't answer the first session update within 3 seconds without having said `transcription_session.created` (it speaks another dialect; one that said it is only slow, and is tried again), records, then sends, for 10 minutes, or until an admin changes the transcription URL, key or this setting. A refused key (401, or socio-voice's 403), a redirect, or a server that is down (502, 503) isn't remembered: the next dictation tries again. **On** tries it every time; **Off** always records, then sends; **The server's default** goes back to `VOICE_TRANSCRIBE_STREAMING`. The composer captures PCM and opens the socket only when `setup.transcriptionStreaming` says so (a transcription server works here, live text would be tried there, and it isn't remembered as recordings-only); otherwise it records and sends as before.

When the server fails, people see "Voice provider returned HTTP 502…", "Voice provider did not answer…" or "Voice provider took longer than 60 seconds…"; the server log names the host (`Voice: transcription at stt.example.test:8000 (whisper-1) returned HTTP 502.`).

## Containers

Set `SESSION_SECRET` to a random secret of at least 24 characters in `.env`, then run, from the repository root (the Compose files are in `.docker/`; `--env-file .env` makes Compose read the repository's `.env` rather than look for one in `.docker/`):

```sh
docker compose --env-file .env -f .docker/compose.yml up --build -d
docker compose --env-file .env -f .docker/compose.yml exec app node dist/server/server/auth/auth-cli.js create-user --email you@example.com --name "Your Name" --role admin
```

Open the printed link to set a password, then http://localhost:4310. The container uses Better Auth (`APP_ORIGIN` defaults to `http://localhost:4310`), because mock auth runs only on a loopback `HOST` and the container binds `0.0.0.0`. The app port binds to loopback. Application metadata lives in the `company-brain-data` volume.

```sh
# Stop services while retaining saved data.
docker compose --env-file .env -f .docker/compose.yml down
```

For remote hosting, configure an HTTPS reverse proxy and the matching `APP_ORIGIN`. See [Security](../SECURITY.md) for the deployment boundary. A self-hosting guide with the swarm stacks is coming.

## Development environments

`APP_ENV=development` marks a deployment as a development one (brain.example.test); the default is `production`, and an unknown value stops the server at boot. Operators then see a **Development** badge on Settings → Platform and a **Stop all running work** button, which lists what is running and, after a confirmation, stops it at once (`POST /api/operator/force-stop`, operators only): running turns end with "Stopped by an operator for a deploy.", job runs end as interrupted, and computer actions in progress are aborted (the computers keep running). By default new work is then held until the restart, as while draining, so a deploy can follow at once; `scripts/wait-idle.mjs --force` does the same from the command line. Each force stop is logged with who, when and the counts. In production the endpoint answers 404 and SIGTERM always drains.

With `SHUTDOWN_FORCE=true` (development only) SIGTERM skips the drain too and stops running work the same way, except worker runs, which keep running as on any restart. It is off by default.

## Production checklist

Before the team uses a deployment:

1. **Reverse proxy.** Put it behind a proxy host such as Nginx Proxy Manager. Prefer HTTPS: set `APP_ORIGIN` to the exact `https://` origin, which also makes session cookies `Secure` and `__Host-` prefixed. With plain HTTP (a trusted LAN only), set `APP_ORIGIN` to the `http://` origin. The app gzips its own responses (JSON, pages and text from 1 kB; build files from their build-time `.gz` copies), so the proxy needs no `gzip` settings. Don't add `text/event-stream` to the proxy's `gzip_types`: chat turns would wait in the compressor.
2. **Secrets.** Generate `SESSION_SECRET`, `COMPUTER_SUPERVISOR_TOKEN` and `COMPUTER_TOKEN` with a CSPRNG (24+ characters each) and `DATA_ENCRYPTION_KEY` (`openssl rand -hex 32`, [Data encryption key](#data-encryption-key)), and keep the bot token and OAuth client secrets private. In a swarm, provide them as secrets through `<NAME>_FILE` variables; never put them in stack env or compose files. Rotating `SESSION_SECRET` signs everyone out. Keep a copy of the data key apart from the backups.
3. **Access.** Use [Better Auth](#sign-in) (`AUTH_PROVIDER=betterauth`, one `APP_ORIGIN`, `AUTH_TRUST_PROXY=true` behind the proxy with the app port reachable only through it). Mock auth refuses to run anywhere but loopback.
4. **Users.** Set `AUTH_FIRST_ADMIN_EMAIL` (and `AUTH_FIRST_ADMIN_LINK`) for the first admin, or create it (`pnpm run auth create-user`); invite the team under **People**, and link existing ids. On first start, data from the single-owner template moves to the first admin.
5. **Model.** Point `OPENAI_BASE_URL` at your model server before the first start (it seeds the first backend; later changes go through Settings → Platform) and confirm `/healthz` reports `"model": true`.
6. **Telegram** (optional). Set the bot token and `TELEGRAM_ALLOWED_CHAT_IDS`; run only one deployment per bot.
7. **Backups.** The app backs up every `BACKUP_INTERVAL_HOURS` (24) on its own; put `BACKUP_DIR` on its own volume, set up the [off-site copy](#off-site-copy) (or copy backups off the host another way), check the last backup on Service setup, and test a restore.
8. **Mini apps** (optional). For Apps to open, add the wildcard DNS entry and proxy host for `*.<APPS_HOST>` with a wildcard certificate ([Mini apps](#mini-apps)), or set `APPS_HOST=off`. Promoted apps need the `apps` and `apps-egress` services and the `company_brain_apps_token` secret ([Promoted apps](#promoted-apps)).
9. **Exit test.** Create the test accounts ([Test sign-in](#test-sign-in-for-the-scripts)) and run `pnpm run exit-test --base <url> --admin-email … --member-email … --password-file …` against the deployment. It signs in only as those two, never as the team, and deletes the conversations and scheduled task it created when it ends.

Upgrades:

1. Read the release notes.
2. Take a backup.
3. Deploy the new image. The schema migrates itself on start; there is no downgrade path, so restore the backup to roll back.
4. Run the exit test.

## Automatic Learning

Socios get better from the team's finished conversations, on this server and with your own model. Nothing is published without an admin's approval.

### How evidence is chosen

1. An admin opens **Learning → Manage scopes**, chooses a socio, and assigns a new or existing **Scope ID**, e.g. `research`. Several socios can share a scope (also called a container). The same setting is available as **Learning container ID** in a socio's settings. Leave it blank to stop collecting evidence from new conversations; **Use this scope’s published skills** controls skill delivery separately.
2. Each new conversation with that socio is assigned to the container when it is created; changing the setting later does not move existing conversations. Telegram conversations count too.
3. A conversation becomes evidence when its latest run finishes. A run that failed or was stopped makes it ineligible until the next finished run. Each conversation counts once per analysis.

### Analysis

An analysis reads the container's new evidence: up to 60 conversations, the last 4,000 characters of each, in batches. It asks the configured model to call a `propose_skill` tool for each procedure that repeats across conversations. It runs:

- when 15 new conversations have finished since the last analysis;
- daily after 02:00, server time, for any container with new evidence (catching up after downtime or when the model becomes available, without repeating that day's scheduled analysis after a restart);
- when an admin presses **Analyze now**, only while the feature flag `learning-analyze-now` is on (Settings → Features; off by default, because it doesn't work yet). Off, the button isn't shown and its route answers 404.

Only one analysis runs per container at a time, and it can be canceled. Canceled or failed runs leave the evidence for the next run.

Learning uses the enabled default shared backend under **Settings → Inference**, not a person's chat subscription. The Learning page explains when that model is missing or there are no new finished conversations. **Analyze now**, when its flag is on, becomes available once both are ready.

### What reviewers already decided

Each analysis also tells the model what admins decided in this container before:

- The rejected proposals and the revoked skills, as "already rejected; don't propose these or close variants".
- The published skills (the ones the latest revision delivers), as "already published". The model may propose one again only as a clear improvement, under the same name, and say in the rationale what changed.

Each list gives the name and the description on one line (cut at 160 characters), most recently decided first, at most 25 entries and 2,500 characters. A name is listed once. A skill that is published now is listed as published, even if an earlier proposal under its name was rejected. Only the container's own decisions are listed; another container's never reach this one's request. Entries that fail the privacy check below are left out.

After the model answers:

- A proposal named like a rejected proposal or a revoked skill of this container is dropped. Names match when they have the same words, ignoring case, word order and a plural "s" (`weekly-reports` matches `weekly-report`).
- A proposal named like a published skill is kept as a revision of it, under the published name, so the review page compares the two. It is dropped as "already published" when its `SKILL.md` is the published one again (frontmatter, whitespace and case ignored), and as "already rejected" when it repeats a rejected proposal under that name.
- Revoking a skill moves its name to the rejected list. Publishing it again moves it back.

Each run counts its dropped proposals by reason, and the Learning page shows them, e.g. "3 dropped (2 already rejected, 1 malformed)".

### Privacy

Skills apply to everyone who uses the socio, so proposals must be generic:

- Before transcripts reach the model, email addresses, phone numbers and secret-like strings are replaced with placeholders.
- The analysis instructions forbid names, contact details, credentials, customer and confidential data, and quotes from the conversations.
- Proposals that still contain contact details or secrets, cite conversations outside the batch, or are malformed are dropped and counted in the run's status.
- The rejected and published lists get the same check before they are sent: an entry with contact details or secrets is left out.
- Evidence comes from everyone's private conversations. Only admins see proposals and their evidence; members see only published skills.

### Review and publishing

Open **Learning** in the sidebar (admins). For each container you see new evidence, the last run, proposals, published skills and the delivered revision.

Proposals are listed newest first, 25 at a time. **Load more** shows the next 25. The list refreshes every 3 seconds and keeps every page you loaded.

- Open a proposal to read its evidence, edit its name, description and `SKILL.md`, and compare it with the published version of that skill.
- **Approve and publish** saves an immutable revision and publishes it. **Reject** marks the proposal rejected. It stays in the list with its status, and the next analyzes of this container are told not to propose it again. Proposals can't be deleted.
- **Revoke** stops delivering a skill; its revisions stay in history. The next analyzes of this container treat it as rejected.
- **Deliver** pins the container to an earlier revision, e.g. to roll back. Choose the latest to unpin.

Each publish or revoke creates a new container revision. A socio with **Use published skills** on gets the delivered revision's skill list in every turn, through CopilotKit's skill-delivery tools (`copilotkit_load_skill`, `copilotkit_read_skill_file`), and loads a skill when it is relevant. Members can see what is published under **Skills**.

## Socio requests

When a user needs something no tool can do, a socio can ask the team for it with `request_capability` (a short capability name, why, an example). The request lands in **Issues** as kind **Socio request**, label `dot-request`, in triage, filed by the socio; the **Socio requests** button on the board and the list shows only those. Requests are merged on a normalized key (lowercase, punctuation and filler words dropped, simple stems and synonyms, word order ignored: "Send emails" and "email sending" are one request): while an issue for the key is open, a new asker is added to it as an agent comment and the demand count (each socio and user pair once) goes up. The issue text names the socio, never the user; who asked is listed in the issue's side panel (Socio and user names, visible to everyone signed in, like authors). When the issue moves to **Done** or **Won't fix**, each user who asked sees a notice on their next visit and, if they linked Telegram and the bot is online, a direct message with the capability, the issue key and the resolution (no emails); the socio is told on its next turn for that user.

| Variable                      | Default | Meaning                                                              |
| ----------------------------- | ------- | -------------------------------------------------------------------- |
| `DOT_REQUESTS_PER_DOT_DAILY`  | `50`    | Requests one socio can make in 24 hours, for all its users. `0` off. |
| `DOT_REQUESTS_PER_USER_DAILY` | `50`    | Requests made for one user in 24 hours, by all their socios.         |

An admin can change both in **Settings → General → Socio filing limits**; what they save there takes the place of these variables, which stay the starting values. The same limits apply to a socio's board items, comments and votes, each counted on its own.

A socio allowed to file to the Improvements board can attach what the person shared in the conversation: `file_improvement` and `comment_on_improvement` take `attachments`, a list of attachment ids (each image and file is labeled with its id for the socio, and `attachments_list` lists them), at most 10. Each file's bytes are copied onto the new item or the comment, uploaded by the person the socio acts for, with the board's usual checks: PNG, JPEG, GIF or WebP images, PDFs and plain text files, up to 5 MB each and 10 per item. Only files a message of that conversation carried, and that the person can read, count; anything else (another conversation's, someone else's, a deleted one, a type the board refuses, one past the cap) is left out on its own while the rest is filed, and the result says which were attached and why the others were not. `read_improvement` lists an item's attachments and each comment's by name, type and size, with the item's link.

When the person asks, a socio allowed to file to the Improvements board can also change one item's status with `set_improvement_status` (CB-520): an item key and one of the board's statuses. It goes through the same permission check and write as the board's own status change, as the person: an admin may move any item, a member none, so a member's request comes back `forbidden`. The status history row is the person's, with the socio recorded beside it. Setting the status the item already has returns `unchanged` and records nothing. The result gives the status read back after the change and the item's link. There is no bulk change.

## Automatic triage

When an admin turns on **Settings → General → Automatic triage**, each new issue that lands in triage (filed in the app, by a socio or by a connected agent; not imports or socio capability requests) is sent once, in a background job, to the default shared backend, the model socios use. The request has no tools, a 30-second timeout and a cap of 1,024 output tokens, and the issue's title and description go in as data between fixed markers. The model must answer with a JSON object of a kind, area, priority, labels (all from the existing lists; not `request` or `dot-request`) and a one-line reason; anything else is dropped and recorded as a failure. A valid answer is posted as a comment from "Automatic triage", and the issue shows a **Triage proposal** card that an admin applies (kind, area and priority are set, labels are added to the issue's own, each as a history row by the admin) or ignores. Nothing is applied automatically, and a failed or invalid answer is never retried. One issue is asked at a time, and at most "Most a day" issues are asked in 24 hours, failures included.

| Variable            | Default | Meaning                                              |
| ------------------- | ------- | ---------------------------------------------------- |
| `AUTO_TRIAGE`       | `false` | `true` turns automatic triage on to start with.      |
| `AUTO_TRIAGE_DAILY` | `100`   | Issues asked about in 24 hours. `0` asks about none. |

What an admin saves in Settings takes the place of these variables, which stay the starting values.

## Rooms

Rooms are conversations several people share with a company socio. They are still being built: this release has their storage and the switch, **Settings → General → Rooms**, off by default (`ROOMS_ENABLED=true` turns it on to start with; an admin's choice takes its place). Turning it on changes nothing in chats yet. Before they do, admins see there how many chats there are and that every one is private; private chats keep exactly their readers, history and links. ## GitHub App

Coding sessions ([docs/CODING.md](CODING.md)) push their branches and open draft pull requests through a GitHub App, in the app's own process: the coding gateway's Git proxy and pull requests mint a short-lived installation token for one repository with no more than contents and pull requests, use it, and revoke it. Repositories are listed in Settings → Coding → Repositories; the App must be installed on each one's owner.

Dispatch (issues sent to coding agents in a `dispatch` worker) was removed in CB-325; this connection is what stays of it.

**Connecting (one time, no tokens to copy).** In **Settings → General → GitHub App**, check the repository (`owner/name`; `GITHUB_REPO` is the starting value, `erden-sh/socio` in the stack), whose owner the App is made for, then select **Connect GitHub**. It uses GitHub's [App manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest):

1. The app sends you to GitHub's new-App page for the repository's owner (the organization's, or your account's) with a manifest: a private GitHub App named "Socio …" with **Contents: read and write**, **Pull requests: read and write** and **Metadata: read**, no webhook and no events, which returns to `APP_ORIGIN/settings/workspace`. Select **Create GitHub App** (you may rename it first).
2. GitHub sends you back with a one-time code. The server exchanges it with GitHub (`POST /app-manifests/<code>/conversions`) for the App's id and private key and stores them sealed under the data key, like the inference backends' keys. The key never reaches a page, a log, a socio or a coding agent. You are sent on to the App's install page.
3. Choose the repositories and select **Install**. GitHub sends you back again; the server checks the installation is this App's, on the repository's owner, and records it.

You need to be an owner of the organization (or the account) to create and install the App. Each step carries a one-time state tied to you and valid for an hour; only admins can take any step, and a step that doesn't match is refused ("select Connect GitHub again"). **Connect again** makes a new App; **Disconnect** forgets the App here (delete it on GitHub too: the owner's Developer settings → GitHub Apps). If the App is installed from GitHub itself, without the return trip, its installation is found from each repository. An App made outside Settings can be used instead with `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY` (or `_FILE`; a PEM, `\n` escapes allowed) and optionally `GITHUB_INSTALLATION_ID`; one connected in Settings takes their place. Before CB-325 these were `DISPATCH_GITHUB_APP_ID`, `DISPATCH_GITHUB_APP_PRIVATE_KEY`, `DISPATCH_GITHUB_INSTALLATION_ID` and `DISPATCH_GITHUB_REPO`: for one release the old names are still read when the new ones are unset, with a one-line deprecation warning at start.

**Never give the App the `workflows` permission** (or administration, actions, secrets, or anything else) on GitHub. Each token asks for contents and pull requests only, and a token GitHub grants more for is revoked unused; but the App's key could mint tokens with whatever the App holds, so the App must hold no more than that. If it was given `workflows` and the installation accepted it, remove it in the App's settings (the owner's Developer settings → GitHub Apps → the App → Permissions & events).

**When it fails.** If the App saved here can't be decrypted (the data key it was sealed with is gone), Settings says so and offers **Disconnect**; connecting again is refused until then. A redirect from GitHub is reported as a renamed or moved repository (it is never followed, so the token never goes elsewhere). An installation on another account than the repository's owner is refused.

**CI.** `.github/workflows/ci.yml` treats every branch as untrusted, people's included; see [SECURITY-ARCHITECTURE.md](SECURITY-ARCHITECTURE.md#ci-runs-untrusted-code). Its token can only read, checkout doesn't keep it, no job has secrets, nothing in it uses `pull_request_target` (only the CLA check does, and it runs no branch code), and its actions (`actions/checkout`, `actions/cache/restore` and `actions/cache/save`) are pinned by commit SHA. The runner runs nothing from the branch: it copies the checkout (without `.git`) to `$RUNNER_TEMP/src`, and only containers ever use that copy. `pnpm install --frozen-lockfile --ignore-scripts --ignore-pnpmfile` runs in a container on an internal Docker network whose only exit is a small proxy (`.github/ci/egress-proxy.mjs`) allowing `registry.npmjs.org:443`; install scripts, format, lint, typecheck, tests and the build then run in containers with `--network none` (`.github/ci/Dockerfile`: the app's Node, pinned by digest, git, pnpm from corepack at package.json's `packageManager`, and the proxy). Only on GitHub-hosted runners: never point this workflow at a self-hosted runner (see SECURITY.md). CI keeps no pnpm store, so installs download everything each run.

## Data spaces

Each user has a data space where their socios keep what outlasts a conversation: datasets (one SQLite file each, never the app's database) and files (encrypted at rest under the [data encryption key](#data-encryption-key), like inference credentials). It lives in `USER_DATA_DIR`, by default `userdata/` next to `DATABASE_PATH` (`/data/userdata` in the image), one directory per user; files can live in S3-compatible object storage instead (below). Each socio gets a scratch dataset per user, created when it first needs one; anything else needs the user's grant, and new datasets, writes to datasets shared with a Space and access requests need their approval (Approvals in the app; manual by default, bypass per socio and capability). Users browse, query, export (CSV, SQLite), delete, set retention and grant access under Data; operators see everyone's usage, never their data.

Deleting keeps the data (CB-64). A deleted dataset, file, folder or attachment is gone for users and socios, and doesn't count toward the user's quota, but its row stays in the database and its bytes stay where they were: the dataset's file in `USER_DATA_DIR/<user>/datasets/`, the file's encrypted object in its store, under the same key. Retention and the collection of unsent attachments delete the same way. Saving over a file keeps its previous contents the same way, as a deleted earlier version of it (saving the same contents again keeps nothing), so a socio or job that rewrites a large file often grows the disk by that file each time. Backups include all of it, and so does the move to S3. Everyone's usage on the Data page shows operators how much each person deleted and the app keeps; plan disk and bucket space for it. A later admin view is to restore or purge it; until then, nothing removes it.

Limits, enforced for every socio (bypass or not): `DATA_DATASET_MAX_MB` (100), `DATA_USER_MAX_MB` (1024), `DATA_FILE_MAX_MB` (25), `DATA_MAX_DATASETS` (50, besides the scratch datasets), `DATA_QUERY_TIMEOUT_MS` (5000), `DATA_QUERY_MAX_ROWS` (500), `DATA_QUERY_MAX_BYTES` (262144) and `DATA_STATEMENTS_PER_MINUTE` (120 data operations a minute per user and socio). An admin can change the file, dataset, per-person and dataset-count limits in **Settings → General → Data space**; what they save takes the place of the variables, and lowering a limit deletes nothing.

Code in a socio's computer reaches the data space through `/api/data` with a short-lived token scoped to that socio and user. Set `DATA_API_URL` to the app as the computers reach it (with the compose overlay, `http://app:4310` on the computers network); unset, computers get no token. Each command gets a token of its own (CB-224), exported as `CB_DATA_TOKEN` and `CB_DATA_URL` (`curl -H "Authorization: Bearer $CB_DATA_TOKEN" "$CB_DATA_URL/datasets"`). The app writes it to a file of the command's own under `.socio/run/`, which the command deletes before anything else runs. The token lives in the app's memory only and is revoked when the command returns (at the latest `DATA_TOKEN_TTL_MINUTES`, 60, after it started), so a process the command leaves running loses it; use a job or a mini app for work that lasts. It is also revoked when the computer stops. On a personal socio the token reaches the socio's scratch dataset, its folder and what its owner granted it. A company socio's computer is shared by everyone who uses that socio, and a command running at the same time can read another's token, so there it reaches only the socio's shared area, which is no person's: a shared dataset (`scratch`) and a shared folder, both visible to everyone who uses the socio through its computer. It can also read, not write, datasets shared with a Space that the acting person granted the socio. A person's own data (their scratch dataset, folder, private datasets and granted folders) answers 404, as if it didn't exist; a write to a dataset shared with a Space, or a path in another socio's folder, answers 403. For a person's own data, use the data tools in the chat, or a personal socio (CB-227). To hand a file to a company socio's computer, the socio copies it with `files_copy` to `shared/<name>`. The computer file tools refuse token files under `.socio/` and leave them out of listings, and data tokens are redacted from what a computer sends back. See [SECURITY-ARCHITECTURE.md](SECURITY-ARCHITECTURE.md#computers) for what is and isn't isolated.

### Indexes on datasets

A dataset's tables can carry secondary indexes (CB-355), so queries that filter, join or sort on other columns than the key don't scan a whole table and run into `DATA_QUERY_TIMEOUT_MS`. An index is declared, never written as SQL: a name (letters, digits and `_`, unique in the dataset, not one of the engine's own prefixes), the table's columns in order (up to 8), and whether it is unique. The engine checks the name and the columns against the dataset's schema and writes the statement itself; `data_query` stays read-only and the write guard still refuses any other DDL. Each table holds at most 10, and an index's pages count toward the dataset's quota.

- Socios use `data_create_index` and `data_drop_index`; `data_describe` lists each table's `indexes` (`name`, `columns`, `unique`), as does `GET /api/data/datasets/:id`.
- The data API: `POST /api/data/datasets/:id/tables/:table/indexes` with `{ "name", "columns": [...], "unique"?, "ifNotExists"? }`, and `DELETE /api/data/datasets/:id/tables/:table/indexes/:name`. A socio's, job's or app's token may call them where it may write (the `createIndex` and `dropIndex` operations, tier `write`), and so may the dataset's owner signed in to the app. On a dataset shared with a Space, a socio's index change waits for the owner's approval like any other write.
- A unique index refuses duplicate values (creating one over rows that already repeat fails), and `data_upsert` or a write with `key` may key on its columns.
- `ANALYZE` refreshes the planner's statistics, for the whole dataset or one table: the `data_analyze` tool, or `POST /api/data/datasets/:id/analyze` and `POST /api/data/datasets/:id/tables/:table/analyze` with a JSON body (`{}`), the `analyze` operation, tier `write`. The engine names each dataset table itself (never its row history tables), under its own write-guard mode. A socio's, job's or app's call counts toward `DATA_STATEMENTS_PER_MINUTE` (the owner's own, in the app, doesn't, like their other changes) and needs no approval on a Space-shared dataset, since it changes no rows. Run it after a large load or a new index on a big table.
- The Data page shows each table's indexes (name, columns, unique), read-only.
- Indexes live in the dataset's file, so backups, the off-site copy, a mini app's promotion (the tables it moves keep theirs) and a transfer to another person carry them. Deleting a table drops its indexes.

### Batches

`POST /api/data/datasets/:id/batch` runs up to 32 statements in one SQLite transaction: all of them or none. It is how a sync loads raw rows, derives facts from them and rebuilds a mart without anyone reading half of it.

```json
{
    "statements": [
        {
            "op": "upsert",
            "table": "raw_charges",
            "key": ["id"],
            "rows": [{ "id": "ch_1", "payload": { "amount": 1200 } }]
        },
        { "sql": "DELETE FROM facts" },
        {
            "sql": "INSERT INTO facts (id, amount) SELECT id, json_extract(payload, '$.amount') FROM raw_charges WHERE json_extract(payload, '$.amount') >= ?",
            "params": [0]
        }
    ]
}
```

It answers as a single write does, with each statement's changed rows and outcome: `{ "status": "done", "dataset": "stripe", "result": { "statements": 3, "changes": [1, 2, 1], "totalChanges": 4, "results": [{ "changes": 1, "lastInsertRowid": 1 }, …] } }`. A statement with a `RETURNING` clause has its `columns` and `rows` in its outcome, all of them or a `413` that keeps nothing; one with `"expectChanges": n` that changes another number of rows rolls the batch back with a `409` naming it (`code: "expect_changes"`, its `index` from 0). See [PLUGINS.md, A D1-style driver](PLUGINS.md#datasets). A failure names the statement (`"Statement 3: …. Nothing in the batch was kept."`) and keeps nothing; the one exception is a batch stopped at its time limit, below.

- A statement is SQL with bound `params` (one statement, at most 20,000 characters and 100 params), or `{ "op": "insert" | "upsert", "table", "rows", "key"? }` as the rows route takes them (at most `insertMaxRows`, 1,000, rows each).
- SQL changes rows only: `INSERT` (with `SELECT`, `json_extract` and the other JSON functions), `REPLACE`, `UPDATE` and `WITH … INSERT`. `DELETE` is allowed only in the datasets a service plugin writes, and in company datasets a data API token with `data:write` reaches. The same write guard as single writes applies to every statement: no DDL (tables, columns and indexes have their own routes), `PRAGMA`, `ATTACH`, transactions or savepoints, recursive CTEs, the engine's own tables (row history, `_writes`, `_writer`, deleted tables), or the file, extension and allocation functions. A refusal is `403`.
- Each statement counts against `DATA_STATEMENTS_PER_MINUTE` (a plugin's token: its own budget, `DATA_PLUGIN_STATEMENTS_PER_MINUTE`; a data API token: its own, set when it was made), and the batch against the dataset's quota (`413` keeps nothing). It runs in the query runner's process, not the app's, and stops after `DATA_BATCH_TIMEOUT_MS` (30 s). A stopped batch is rolled back and answers `504` with "nothing it did was kept", unless it committed in the moment it was stopped: then the `504` says its changes were kept, or, if Socio couldn't tell, that whether it committed is not known. In those two cases check the data before you send the batch again, or make it safe to repeat (an upsert, or `DELETE` then `INSERT … SELECT`). Rows it replaces or deletes go to row history, as the writer's.
- `POST /api/data/datasets/:id/read-batch` is the read side (CB-474): up to 32 SELECTs, each checked and capped as a query is, read from one snapshot and counted as one operation. Anyone who may query the dataset may send one.
- A socio's, job's, app's or plugin's token may send one where it may write (operation `batch`, tier `write`). A dataset shared with a Space is refused (`409`) unless the token is a promoted app's, a plugin's own or a data API token, since each change there otherwise needs the owner's approval. A signed-in person can't send one.

### Row history

Every dataset table keeps the rows its writes replace or delete, with who and when (row history), in the dataset's own file. History has its own room outside the quota. Three controls keep it from growing without end (CB-369):

- **Tables without history.** `POST /api/data/datasets/:id/tables` takes `"history": false`: the table keeps nothing its writes replace. Meant for derived tables (marts, caches) rebuilt from other tables. A plugin's manifest may declare it for its tables (see [PLUGINS.md](PLUGINS.md#datasets)). An existing table is switched with `PATCH /api/data/datasets/:id/tables/:table` and `{ "history": false }` (or `true`): by the dataset's owner in the app (an admin, for a plugin's dataset; the **Turn row history off** button on the Data page), or by a plugin with its own token on its own dataset (the `tableHistory` operation, tier `write`). A socio's, job's or app's token is refused (`403`). Off drops the table's history triggers, and what it kept so far is deleted at the next nightly prune. On again keeps changes from that moment. `GET /api/data/datasets/:id` says `history` for each table.
- **Keep row history for N days.** A dataset's owner (an admin, for a plugin's) sets **Row history** on its Data page, or `historyDays` (1 to 3,650, or `null` to keep all of it) with `PATCH /api/data/datasets/:id`. The default keeps everything, as before: nothing is pruned until someone sets a limit.
- **Compact file.** Pruned rows free pages that later history and rows reuse, so the file stops growing but doesn't shrink. Free pages never count toward the quota. **Compact file** on the Data page (`POST /api/data/datasets/:id/compact`, `{ "cancel": true }` takes it back) rewrites the file without its free pages (SQLite `VACUUM`) at the next nightly run, in the query runner's process. Writes to that dataset wait (or fail with "database is locked") while it runs; it stops after 10 minutes and leaves the file as it was.

The nightly run is on the runtime that leads, once a night between 02:00 and 06:00 the server's local time. It deletes kept rows in transactions of 5,000, then the `_writes` records nothing names any more, and audits each dataset it changed as `history_prune` (actor `system`, with counts) and each compaction as `compact`. Deleted tables' history is pruned by age only. Older backups keep what a prune deleted until they are pruned themselves (`BACKUP_KEEP`).

### Row stamps and changes

Every dataset table with a primary key also keeps a stamp per row (CB-451), whatever its history setting: the write that last changed the row, as `<generation>.<value>`. `value` comes from the file's own sequence, which every write takes once and nothing lowers (history prunes don't touch it); `generation` is a random id the file gets with its first stamp and replaces when its history is rewound or forked. A backup's dataset copies keep no generation, so each restore of one takes a new one the first time Socio opens the file, and a copy of a dataset (moving tables into a new one) takes its own. A deleted row leaves a tombstone, kept for **Remember deleted rows for** in Settings → General → Data space (`DATA_STAMP_TOMBSTONE_DAYS`, 30 days) and deleted by the nightly row-history run. Stamps live in the engine's own `_stamp*` tables in the dataset file (table names starting with `_stamp` are reserved), count with history outside the quota, and are left out of exports. Files from before them get them on their next write, every existing row with the sequence's first value; no step at start opens every file.

`GET /api/data/datasets/:id/tables/:table/changes?since=<token>` answers a reader of the dataset with the rows changed after the token (all their fields, blobs as `{ "$blob": true }`) and the keys deleted since, in stamp order, at most 1,000 an answer: with `next`, ask again with `&cursor=<next>`. `token` is the next `since`. A token of another generation (after a restore), or older than the tombstones kept, answers `reconcile: true` with no rows and the current token; a client with no token yet starts that way. A table without a primary key, or an analytical one, answers `resync: true`. An unchanged answer is a `304` (`If-None-Match`).

### Analytical tables

A dataset may also hold analytical tables (CB-369): append-only history kept as Parquet files beside the dataset's file and queried with DuckDB, for data like a daily occupancy log that only grows. In this release they are in **service plugins' own datasets only**: the plugin declares, appends and queries them with its own token, and admins read them on the Data page. Socios, apps and personal datasets don't reach them yet.

- **Declare.** `POST /api/data/datasets/:id/tables` with `"kind": "analytical"`, the columns (`TEXT`, `INTEGER`, `REAL`, `DECIMAL(p,s)`, `BOOLEAN`, `DATE`, `TIMESTAMP` in UTC, `JSON`; no keys, uniques or defaults) and `"partitionBy": { "column", "grain": "day" | "month" }`, on a `NOT NULL` `DATE` or `TIMESTAMP` column. `ifNotExists` with the same declaration does nothing; with another it is refused, naming the difference. `POST …/tables/:table/columns` adds a nullable column; older files read it as null. `"retainDays"` (1 to 36,500) keeps partitions that many days (see Retention below). A plugin may declare them in its manifest instead ([PLUGINS.md](PLUGINS.md#datasets)).
- **Append.** `POST …/tables/:table/append` with NDJSON (`application/x-ndjson`, a row per line) or `application/json` (`{ "rows": [...] }`), up to `DATA_ANALYTICS_APPEND_MAX_ROWS` (200,000) rows and `DATA_ANALYTICS_APPEND_MAX_MB` (64) per call. The body is streamed to disk, every row is checked against the declaration (a bad row refuses the whole append), and one zstd Parquet file is written per partition touched (at most 400). Send `x-cb-append-id`: an id the table has committed already adds nothing and answers its first counts with `"duplicate": true`, so a retry never doubles rows. The answer: `{ "status": "done", "table", "rows", "parts", "bytes" }`.
- **Values.** A cell is stored exactly or the append is refused, naming the row and column; nothing is rounded or rolled over. `INTEGER` takes 64-bit whole numbers. JSON numbers are read from their digits, as sent: past 2^53, or with more digits than a double holds, they keep them wherever the type does. `REAL` takes finite numbers, as doubles. `DECIMAL(p,s)` takes a number or numeric string with at most `s` fraction digits and `p − s` whole digits. `BOOLEAN` takes `true`, `false`, `0` or `1`. `DATE` takes a real `YYYY-MM-DD`; `TIMESTAMP` takes epoch milliseconds or ISO 8601 with a real date and time, years 1 to 9999, kept to the millisecond. `JSON` takes any JSON value; a string is taken as JSON text and must parse. `TEXT` takes text, numbers and booleans, written as text. NaN, Infinity and bytes are refused. In a query, a transactional column of numbers reads as `BIGINT` (all whole) or `DOUBLE`, one of bytes as `BLOB`, and one mixing text, numbers or bytes as text; one mixing integers past 2^53 with fractions is refused.
- **Copy a table across.** `POST …/tables/:table/append-from` with `{ "from": "<transactional table>", "where"?: { "column", "from"?, "to"? } }` copies its rows (in chunks of 10,000, each its own short read) into the analytical table; the source stays. Its append id is `from:` and a SHA-256 of the source table and its `where`, unless `x-cb-append-id` says otherwise, so the same copy twice adds nothing.
- **Query.** `POST …/analytics/query` with `{ "sql", "params"?, "maxRows"? }`: exactly one DuckDB `SELECT` (or `WITH … SELECT`), checked by DuckDB's own parser, over every table of the dataset, both kinds, in one consistent snapshot. Transactional tables it names are loaded into DuckDB, up to `DATA_ANALYTICS_JOIN_MAX_ROWS` (200,000) rows and `DATA_ANALYTICS_JOIN_MAX_MB` (64) together. It answers like `POST …/query` (`columns`, `rows`, `truncated`, `ms`; dates and timestamps as ISO strings, decimals as exact text, nested values as JSON text), within `DATA_ANALYTICS_QUERY_TIMEOUT_SECONDS` (30), `DATA_ANALYTICS_QUERY_MAX_ROWS` (10,000) and `DATA_ANALYTICS_QUERY_MAX_MB` (8). `POST …/query` stays SQLite and refuses an analytical table's name with a pointer here. `query_table('t')` (or a list of names) and `query('SELECT …')` work with constant strings, and read the tables they name like any other; the SQL inside `query()` is held to one `SELECT` too, nested at most three deep (CB-387). One dataset per query.
- **Limits.** Each counts as one operation against the plugin token's budget (`DATA_PLUGIN_STATEMENTS_PER_MINUTE`, CB-473; anyone else's, `DATA_STATEMENTS_PER_MINUTE`). Analytical bytes have a budget of their own per owner (a person, a socio's area or a plugin), `DATA_ANALYTICS_MAX_MB` (1,024), apart from `DATA_USER_MAX_MB`; an append past it is refused (`413`). Queries run `DATA_ANALYTICS_QUERY_CONCURRENCY` (2) at a time, 16 more wait, then `429`; each gets `DATA_ANALYTICS_QUERY_MEMORY_MB` (512), `DATA_ANALYTICS_THREADS` (2) and `DATA_ANALYTICS_QUERY_TEMP_MB` (2,048) of spill. An admin changes the budget, query time, rows, append rows, memory, concurrency and the default retention in **Settings → General → Analytical tables**.
- **The process.** `DATA_ANALYTICS_MODE`: `child` (the default) forks the analytics process the first time an analytical table is used and stops it after 5 idle minutes; it has an empty environment, opens only the dataset file the app authorized (read-only) and the Parquet files its catalog lists, with DuckDB's extensions and file access off. `off` refuses analytical tables (`503`); existing ones stay on disk and in backups.
- **Storage and backups.** Parts live in `USER_DATA_DIR/<owner>/datasets/<id>.parts/`, read-only, listed in the dataset file's own hidden catalog. They are in every daily backup, copied once into `BACKUP_DIR/parts/` and hard-linked into each run, and the off-site copy sends each once, sealed under the data key, to `parts/<dataset>/<part>.parquet.sealed`. Restoring a run's `userdata-…/` brings them back; from off-site, restore the snapshot's dataset file first, then for each row of its catalog (`SELECT id, table_id, partition FROM _olap_parts WHERE retired_at IS NULL`) open `parts/<dataset>/<id>.parquet.sealed` with `backup-cli open` into `USER_DATA_DIR/<owner>/datasets/<dataset>.parts/<table_id>/<partition>/<id>.parquet`, and make it read-only (`chmod 0444`). Health names any part a catalog lists that is missing on disk. The recovery point is the daily backup; a plugin re-appends since its last good day (appends are idempotent). The SQLite export of a dataset leaves analytical tables out.
- **Retention** (CB-387). A table with `retainDays` loses old partitions at the nightly run (with the row-history run, on the runtime that leads, 02:00 to 06:00): every partition that ended before that many days ago is retired, audited as `retention_drop_partition` (actor `system`, with partitions, rows and bytes), and leaves queries, the Data page and the analytical budget at once. Its files stay on disk and in the catalog for 48 hours, so the next backups still hold them, and then the hourly sweep deletes them. Older backups keep them until they are pruned (`BACKUP_KEEP`). Which retention applies, first match wins: an admin's override on the table; else the plugin's value (the installed manifest's `retainDays` for a table it declares, so an update that fails never changes it, or the table's own `retainDays`); else the workspace default, `DATA_ANALYTICS_RETAIN_DAYS` (0, the default, keeps everything), which an admin changes in **Settings → General → Analytical tables**. An admin overrides a table's retention on the Data page (`PUT /api/data/datasets/:id/tables/:table/retention` with `{ "days": N }`, or `null` to keep everything). The override is stored apart from the manifest's value and wins over plugin updates that declare another value until the admin clears it (`DELETE …/retention`). `GET …/retention/preview?days=N` says what that retention would drop if the run happened now (partitions, parts, rows, bytes, first and last partition); the page shows it and asks before it saves a value that drops anything. Each table's `analytical.retention` gives the days in force, their `source` (`override`, `manifest` or `default`), the override, the plugin's value and the workspace default. Overrides are audited as `table_retention_override`, and changes to the default as `analytics_retention_default`.
- **During a deploy** a new analytical table or append waits (`409`, try again in a few minutes) until the previous release, which doesn't know them, has stopped.

### Service plugins' datasets

A service plugin declares the datasets it needs (its manifest's `datasets`, with `read` or `write` access; see [PLUGINS.md](PLUGINS.md#datasets)), and an admin binds each need to a workspace dataset at install (CB-451). Bound datasets are owned by `ws:workspace`, like a company socio's area is by `socio:<id>`: the company's, outside every person's data space, so a transfer (CB-360) or a person's purge never touches them and they count against no person's quota. Each has at most one plugin that writes it. The plugin reaches them with a data token it exchanges its identity for (`POST /api/workload/data-token`), purpose `plugin`, which reaches only the datasets bound to it, each with its binding's access (a `read` binding: queries only), never files, jobs or another owner's data, and writes as the plugin (`plugin` in the audit and in row history) with no `x-cb-obo`. Uninstalling ends its bindings and keeps the datasets. Datasets owned by `plugin:<id>` before this release are bound to their plugins at start and move to the workspace once no runtime of the previous release runs, so a start-first deploy has no gap.

Admins see them on the Data page with a **Plugin** badge and manage them as an owner does: browse, export, share with a Space, set retention, grant a socio access, and delete. Members read one only when an admin shares it with a Space they read. A socio reaches one through a grant an admin gives it (or approves, when the socio asks with `data_request_access`; that approval is never automatic): a company socio's grant serves everyone who uses that socio, a personal socio's only while its owner is an admin. A plugin's dataset keeps the name its manifest declares.

Each has its own limits, which an admin may raise in **Settings → General → Plugin datasets**: its size (`DATA_PLUGIN_DATASET_MAX_MB`, 100) and the rows one query returns (`DATA_PLUGIN_QUERY_MAX_ROWS`, 500; its byte cap grows with it, up to 8 MB). A plugin's token has its own budget of data operations a minute (`DATA_PLUGIN_STATEMENTS_PER_MINUTE`, 600, apart from socios' `DATA_STATEMENTS_PER_MINUTE`), which an admin changes there for every plugin and on a plugin's page for that plugin (CB-473).

### Data API tokens

A workspace admin's own script (an import from another tool, such as Notion) uses the data API with a **data API token**, made in **Settings → Data API** (workspace settings; admins only, `GET`, `POST` and `DELETE /api/data/api-tokens/:id` with a session). It is shown once, as `cbdt_api_` and 43 characters; the app keeps its SHA-256 only. Each one has:

- a name and scopes: `data:read` (list and describe datasets, query, read batches, read field settings), `data:write` (insert, upsert, batches, `DELETE` in a batch, `ANALYZE`) and `data:admin` (create datasets, declare tables and columns, indexes, change a dataset's name, description, retention and place in a Space, read and save field settings with `GET …/tables/:table/fields` and `PUT …/tables/:table/fields/:field`). A scope gives only its own routes (`data:admin` writes no rows): give an import all three;
- an expiry: 7 days unless the admin picks another, 30 at most;
- a budget of data operations a minute, its own: 600 unless the admin sets another, up to the plugin budget's ceiling (100,000). A request is one operation (a read batch too); a write batch is one per statement. Past it, `429`.

It reaches only the workspace's own datasets (owner `ws:workspace`) that no plugin is bound to: never a person's dataset (its maker's included), a socio's scratch or shared area, a plugin's, files, jobs, deletes, exports or grants. A dataset it makes with `POST /api/data/datasets` is the company's: it counts against no person's quota (its size limit is a plugin dataset's), the workspace may hold at most `DATA_MAX_DATASETS` of them, and backups include its file like every dataset's. Placing one in a Space (`sharedSpaceId`, `spaceParentId`, `spacePosition`) needs its maker to be able to edit that Space; writes to a Space-shared company dataset need no approval. Writes are recorded as the token (`token:<id>` in row history, field settings and the data audit, with its maker in the audit's `byUserId`). The workspace audit has each token's making, a summary of its use (at its first request, then at most every 15 minutes, and at its revoke) and its revoke. Writes answer as a socio's do, `{ "status": "done", "dataset", "result" }`, with a batch's per-statement outcomes under `result` ([Batches](#batches)). Requests over the API's 1 MB body limit are refused, so split large imports into several batches. Revoking it, its expiry, or its maker no longer being an active admin stops it at the next request. Its maker's demotion or deactivation revokes every token they made for good, at once, as it revokes their service keys (the auth CLI's deactivation at the token's next request), so a reactivation or a later promotion doesn't bring them back (an admin entitlement taken away under Settings → Access, or from the admin list at a restart, too); the check uses the sign-in provider's effective role. Send it as a bearer token:

```sh
curl -s -H "Authorization: Bearer $SOCIO_DATA_TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"Roadmap"}' https://socio.example.com/api/data/datasets
```

### Object storage

With `S3_ENDPOINT` set (CB-54), files go to an S3-compatible object store instead of the local disk; datasets stay in `USER_DATA_DIR`. The contract is plain S3 with SigV4: AWS S3, MinIO, Cloudflare R2, Backblaze B2 or SeaweedFS all work. The stack bundles SeaweedFS (`http://company-brain-s3:8333`), but that is a deployment choice, not a requirement. The app encrypts each file before it leaves (as on disk), and stores it under `tenants/<TENANT_ID>/users/<user>/files/<file id>`: the bucket sees sizes and opaque ids, never names, types or contents. Settings: `STORAGE_DRIVER` (`local` or `s3`; `s3` when `S3_ENDPOINT` is set), `S3_BUCKET` (`company-brain`, created at start when missing, in `S3_REGION`), `S3_REGION` (`us-east-1`), `S3_FORCE_PATH_STYLE` (`true`: `<endpoint>/<bucket>/<key>`; `false`: virtual-hosted, `<bucket>.<endpoint host>/<key>`, as AWS prefers), `S3_CREDENTIALS` or `S3_CREDENTIALS_FILE` (JSON: `{"accessKeyId": "…", "secretAccessKey": "…"}`; SeaweedFS's own identity file is accepted too, from which the app takes the first key pair of the identity named `S3_IDENTITY`, `company-brain`) and `TENANT_ID` (`main`). `s3` without an endpoint or credentials stops startup.

Once S3 is set, files already on the local disk move there in the background, once: each is uploaded, checked by size, marked as moved and only then deleted locally; a crash midway is picked up at the next start, and the app retries hourly while any are left. It logs counts only. While the bucket doesn't answer, file reads and writes fail with 503 ("File storage is unavailable; try again."), and `/healthz` and setup say `"storage": "s3_unreachable"` until a request succeeds again.

### Chat attachments

People attach files in both chat composers (CB-54): the paperclip, a paste (a screenshot) or a drop. Each file is uploaded at once into the user's data space, under `attachments/<date>/`, as it was sent (images are not shrunk or re-encoded), within `DATA_FILE_MAX_MB` and the user's quota, at most 10 per message. Messages carry references, never the bytes, so a conversation's history stays small; an attachment that is never sent is deleted (hidden and kept, as above) after a day, and one in a deleted conversation stays in the user's files.

When a turn runs, the newest images of the conversation go to the model as images (up to the model's image limit, 4 by default, each at most `MEDIA_IMAGE_MODEL_MAX_MB`, 10, and 32 MB a turn), on both the self-hosted and the ChatGPT paths; a model without vision, older images and larger ones get a note instead. Text and other files are announced to the socio by name, type, size and path, and the socio reads them with `files_get` (100 KB at a time) when it needs to. A socio may read what was attached in its own conversation without a grant; anything else in the data space needs a folder grant, as before (a read grant on `attachments/` covers every attachment). Telegram photos and documents are stored the same way, as the sender's attachments.

Screenshots a socio takes with its computer (CB-157) are attachments of the chat too, `source` `tool`, in the files of the person the socio acts for, bound to the chat at once; the tool's result names the image (`image`: its id, type, size and dimensions), so history never holds the bytes. Each round's prompt shows the newest images of the chat (screenshots and the person's photos together, up to the model's limit and the byte limits above) as images, a screenshot in a message from Socio right after its result, since a tool result is text on the Chat Completions path. An older or larger one gets a short note after its result, with its id. Past the limit, each newer image turns the oldest one shown into a note, which changes the request from that image onward, so a model's prompt cache (CB-139) holds only up to it; the note stays the same after that. A model without vision gets the note with the image's size and is pointed to `computer_snapshot` and `computer_read`; after a switch to the shared model (CB-140) the shared model's limits apply. `attachments_view` shows a socio one of the chat's images again. Screenshots stored as base64 text by older versions become a short note in the prompt and in `recall`; stored history is not rewritten. The image's bytes come from `/api/media/attachments/<id>/content`, for the person and anyone who can read the chat, never anyone else (404).

**Media** in the sidebar (`/media`) is where people manage these files: everything in their data space, by folder (Chat attachments under `attachments/`, each socio's own folder by the socio's name, and their own folders). Images show as thumbnails of the original, other files with an icon for their type; a list view says which conversation an attachment came from (or that the conversation was deleted) and which socio saved a file. A preview shows an image at full size or the first 256 KB of a text file, with Download, Move or rename, and Delete (a deleted attachment shows as removed in its chat). Upload with the button, a drop anywhere on the page or a paste, into the open folder. Folders can be created empty, renamed or moved with everything in them (a socio's own folder can't), and deleted with their files. A folder's **Socio access** lists and changes its folder grants, the same grants as on the Data page; renaming or moving a folder takes its grants and those of its subfolders along, and deleting a folder ends them (both show in the data audit). Media is a view over the data space: the Data page's Files tab now points there.

### Space uploads

A socio can upload images and PDFs into a Space's media with `space_media_upload` (CB-524), for example the assets of a Markdown or ZIP import, so the Space's readers open them without the socio's computer or its private files. It is the media model page covers and pictures use: each upload is a copy in the files of the person the socio acts for (`space-media/<Space>/`, counted against their quota), recorded as an embed of the Space, served at `/api/media/embeds/<id>/content` (the URL the tool returns) to whoever may read the Space at that moment, and nobody else (404). Removing someone from the Space stops their access at once.

- **Who may upload.** The socio reads its sources as `files_get` does: its own folder, a folder granted to it, or a file attached in the chat (a computer's file is first saved to the socio's folder, `PUT $CB_DATA_URL/files`). Being able to read a file is not leave to share it: the socio must have the Space in that chat, the person must edit the Space, and new content waits on the person's approval (capability `media.space_upload`, under their manual, auto or bypass policy), bound to the exact files and their bytes and used once.
- **What it takes.** PNG, JPEG, GIF and WebP images up to 5 MB and PDFs up to 25 MB, never more than `DATA_FILE_MAX_MB`, at most 20 files a call, recognized by their bytes only (an SVG, HTML, or a file whose name or declared type says image or PDF but whose bytes don't, is refused). Images are served inline with their type, PDFs as downloads, both with `nosniff` and a sandboxing policy.
- **Retries and results.** The same bytes for the same Space and page return the existing asset (`reused`), without a second copy or a second approval, while its stored copy still holds those bytes. Every file gets its own result, so a partial import lists what is missing.
- **Lifecycle.** A page names an upload by its image block or by a link to its URL; moving the page copies them into the new Space, as pictures. The hourly clean-up removes an upload no page names (live or deleted, in its text, a kept revision or as its cover) after 7 days without being uploaded again, and deletes its copy (restorable from the person's deleted files) only when no other embed names that file. Deleting a page never removes an upload another page, or a restorable page, still names. Deleting the copy from the person's Media page takes it off the Space, as for covers.

## Mini apps

A socio can build a small web app, run it in its computer with Bun and publish it. People open it from **Apps** in the sidebar; the platform serves it on its own origin, `<APPS_LABEL_PREFIX><app>--<dot>.<APPS_HOST>` (for example `tracker--dot-ab12cd.apps.brain.example.test`, or `app-tracker--dot-ab12cd.brain.example.test`), signs them in and proxies to the app's port in the socio's computer. Mini apps are ephemeral: an app runs only while its socio's computer runs it, until it is promoted into a workspace app ([Promoted apps](#promoted-apps)).

- **`APPS_HOST`.** The apps' parent host. Unset, it is `apps.<APP_ORIGIN's host>` (`apps.brain.example.test`, or `apps.localhost` locally); `off` turns mini apps off, and so does an unset `APP_ORIGIN`. It may be the app's own host (`APPS_HOST=brain.example.test` with `APP_ORIGIN=https://brain.example.test`), so one wildcard certificate for `*.brain.example.test` covers the apps; use https then, which makes the app's cookies `__Host-` ([Sessions and security](#sessions-and-security)). The apps share `APP_ORIGIN`'s scheme and port. Every request whose Host is under `APPS_HOST` is answered by the proxy alone and never reaches the app's own routes or client; the app's own host is never treated as an app's.
- **`APPS_LABEL_PREFIX`.** Empty by default. Set (for example `app-`: up to 20 letters, digits and single dashes), every app's host label starts with it (`app-tracker--dot-ab12cd`) and only labels with the prefix are routed to an app; other names under `APPS_HOST` (`www.brain.example.test`) get the proxy's 404 and never reach an app. Labels stay within 63 characters: with a prefix, the socio's name in the label is shortened as needed. App ids don't include the prefix, so apps registered before it was set keep their ids and move to the prefixed address (one whose label would then pass 63 characters has to be registered again). Recommended whenever `APPS_HOST` is the app's own host.
- **DNS and proxy host.** Live use needs a wildcard DNS entry `*.apps.brain.example.test` pointing at the same host as `brain.example.test`, and a reverse-proxy host for `*.apps.brain.example.test` with the same upstream as the app (`node-1:4310`, or `company-brain_app:4310` on the `proxy` network), **Websockets Support** on, the Host header passed through unchanged (Nginx Proxy Manager does by default) and a certificate for `*.apps.brain.example.test` (one wildcard covers every app: there is only one label under `APPS_HOST`). `/etc/hosts` can't hold a wildcard, so the entry goes in a DNS server the users' machines ask (dnsmasq: `address=/apps.brain.example.test/10.0.0.10`). Browsers must trust the certificate (a self-signed one is accepted per host; a local CA the machines trust works for all). Until these exist the apps' addresses don't resolve and Open fails in the browser; nothing else is affected.
- **Computers.** The proxy reaches an app at `<the computer's host on the computers network>:<port>` (the supervisor's computer URL, with the app's port), so the app must run with computers in Compose or the stack (the computers network). A computer on the host's loopback publishes only its API port; its apps show as unreachable.
- **Sign-in.** Owner only by default; the owner can share an app with a Space under Apps. Open (or any visit to an app's address without a session there) goes through `/apps/<id>/open` on the app's own origin, which hands the browser a one-time code (60 s, single use, bound to that app and person) for `<app origin>/__cb/auth`. That sets a host-only cookie for that app's address alone (`__Host-cb_app` over https: Secure, HttpOnly, SameSite=Lax), valid `APPS_SESSION_HOURS` (12). Unregistering, unsharing (for others) and losing access end sessions at once. Public apps aren't available yet.
- **Data.** Registering writes `.socio/apps/<slug>.env` into the socio's computer with `PORT`, `CB_APP_ID`, `CB_APP_URL`, `CB_DATA_URL` and `CB_DATA_TOKEN`: a data token for the datasets the socio named and its scratch dataset, valid 7 days and replaced in that file when a day is left or after the app restarts (tokens live in memory), checked every 10 minutes and on use. The app sources the file before starting and reads it again on a 401. It needs `DATA_API_URL` (above).
- **Starting.** The socio starts its server itself with exec (`set -a; . ./.socio/apps/<slug>.env; set +a; (setsid nohup bun run server.ts > ~/.socio/apps/<slug>.log 2>&1 < /dev/null &)`), bound to `0.0.0.0` on a port from 3000 to 3999, or gives `app_register` a start command that the platform runs after registering and when the owner presses Start on the "This app's computer is stopped" page.
- **Limits.** `APPS_MAX_REQUEST_MB` (10), `APPS_MAX_RESPONSE_MB` (100), `APPS_TIMEOUT_SECONDS` (30, until the app answers with headers) and `APPS_IDLE_SECONDS` (300, for streams and WebSockets).
- **Approval.** Registering is the `app.register` capability: manual by default, bypass per socio under Approvals.

### Promoted apps

Promotion moves a mini app out of its socio's computer into the **workspace app runtime**, the `apps` service of the stack, at the same address. It is the user's statement that the app and its data should outlive the socio's computer, and it follows this handoff protocol:

1. **Package.** `app_package({ app, dir, files?, manifest })` collects the app's source and `bun.lock` from the socio's computer (by exec: a file list, a ustar archive, read back in base64 chunks with a checksum) into a versioned bundle, sealed in the owner's data space under `apps/<app id>/bundles/v<n>.cbapp`. `node_modules`, `.git`, `.socio/`, `.env*`, `.npmrc` and key files are never packaged. The manifest is `{ name, description, entry, runtime: 'bun', routes?, datasets: [{ id, access: 'read'|'write', tables? }], egress: ['host:port'], env?: { NAME: description }, secrets?: [{ name, required, description? }] }` (`secrets`: see [Secrets for workspace apps and plugins](#secrets-for-workspace-apps-and-plugins)); egress entries are public host names only (no addresses, `localhost`, `.local`). Caps: `APPS_BUNDLE_MAX_FILES` (400), `APPS_BUNDLE_MAX_FILE_MB` (2), `APPS_BUNDLE_MAX_MB` (8, uncompressed), and the data space's file limit for the bundle itself. Files sit in the bundle in plain byte order of their paths, not the server's locale, so the same source gives the same bytes and checksum on any server. Bundles packaged before 2026-10-11 used the locale's order: stored ones still open as they are, but packaging the same source again gives new bytes and a new checksum once.
2. **Data handoff.** The owner promotes from **Apps** (Promote… on a packaged app: a wizard with the manifest and files, then a choice for each dataset, then the review), or the socio proposes it with `app_promote`, an `app.promote` approval whose card lists every choice and links to the wizard (`/apps?promote=<id>`). Per dataset: **move** (the socio's scratch tables, all or the manifest's `tables`, go into a new dataset of the user's; the socio keeps read access unless the user unticks it), **share** (with a Space; scratch data is moved first) or **keep** (it stays where it is). Nothing moves without a choice. The app's own grants (`app_grants`) then point at the result; its token sees those datasets only, under the names its manifest used (`scratch` stays `scratch` for the app after a move), and no files.
3. **Review.** The wizard's Promote is the owner's own approval; `app_promote` and `app_update` follow the approval policy (manual by default, bypass or `auto` per socio).
4. **Run.** The app deploys the bundle to the runtime and starts it. The runtime runs each app as its own process, under its own uid (`APPS_RUNTIME_UID_BASE`), with `prlimit` limits and a memory watchdog, in a directory of its own that is emptied on every restart, listening on a unix socket (`$CB_SOCKET`) that only the runtime can open. Its environment holds `CB_SOCKET`, `CB_APP_ID`, `CB_APP_URL`, `CB_DATA_URL`, `CB_DATA_TOKEN` (also in the file `$CB_DATA_TOKEN_FILE`, rewritten in place when the token is renewed: read it again on a 401), the owner's values for the manifest's `env`, and, when the manifest lists egress, `HTTPS_PROXY` for the apps' egress proxy. The apps proxy serves it as before (sign-in, sharing, headers); promoted apps the user may open appear in the launcher, the sidebar and the ⌘K palette.
5. **Updates.** The socio packages a new version and proposes it with `app_update` (an `app.update` approval with what changed in files, manifest and data, and a choice for each new dataset). Approved, it rolls out; the previous version is kept and **Roll back** returns to it. A version that doesn't start leaves the live one running.
6. **Retirement.** **Unpublish** stops it (its address answers "unpublished", nobody can open it, the data and versions stay; **Publish** brings it back). **Delete…** asks whether its data goes too: "delete" deletes the datasets its promotion created (kept, like any delete of data); datasets it only used, and the socio's scratch dataset, stay.

**Build and start logs (CB-146).** Each build of a version in the runtime (unpacking it, installing its locked dependencies) and each start (a crash restart too) is an **attempt** with its own output and how it ended: `exit` (its exit code), `signal`, `oom` (above `APPS_RUNTIME_MEMORY_MB`), `health_check` (it never opened `$CB_SOCKET` within `APPS_RUNTIME_START_SECONDS`), `spawn` (its command couldn't run), `build` (the bundle was refused or installing failed) or `stopped`. The runtime keeps the last 10 attempts per app in memory, and always the one running however old, each to its last 400 lines and 32 KB; a line is cleaned of terminal colors and control characters and cut to 1,000 characters (a line that was cut also loses its last characters, at least 64 and as many as the longest secret, where part of a secret or key may sit). A flood can't hold up the runtime, which every app shares: of one write only the last 399 lines are read (a line in their place says how many were dropped), and an attempt takes at most 500 lines a second; past that the newest 50 wait for the next second, stderr's first and stdout's in the room left, after a line saying how many were dropped, and come out in the order they came. Output is always read at once, never paused: a Node app waiting on a full pipe slows to a crawl, and one that crashes then loses its stack trace. Once a process exits or is stopped, its late lines are held the same way, and the line saying it exited comes after its output has ended (up to 2 s). The app copies them into `app_attempts` (apps migration 4) after every deploy and start, when the runtime's newest attempt changes (the minute tick) and before anyone reads them, so they outlive a runtime restart. A running attempt the runtime no longer lists is marked `lost` (it restarted, or dropped it as old); while the runtime doesn't have the app at all, nothing stored changes. It keeps the newest 5 per version and 50 per app. Output is redacted in the runtime, with lines joined across writes first, and again in the app before anyone reads it: the data token, the egress credentials, the owner's **secret** settings (a name ending in KEY, TOKEN, SECRET, PASSWORD, PASS, PWD, CREDENTIAL(S), DSN, SALT, WEBHOOK or WEBHOOK_URL, such as `PRIVATE_KEY`, `SIGNING_KEY` or `AUTH_TOKEN`, but not `AUTH_PROVIDER`, `AUTH_MODE` or `PRIMARY_KEY`, a description that says it is a secret, password, token, API key or credential, or a URL with credentials or a key in its query; ordinary settings such as a mode, a host or a time zone stay readable), each as it is, URL-encoded, JSON-escaped, base64 (also inside a longer blob, as in `user:secret`) and hex in either case, and bearer and basic credentials, JWTs, credentials in URLs, keys of a known shape and `password=`-style values. Values shorter than 6 characters are never redacted (they would blank ordinary words), so a secret setting should be longer. A runtime from before attempts (the app deployed ahead of it) keeps one log for every version: **Logs** and `app_logs` then show its last lines with a note. The owner reads them under **Logs** on the app's card on **Apps**, which also says when the newest attempt failed. The socio that built the app reads them for its owner with `app_logs({ app, version?, attempt?, lines? })`: the newest attempt by default, or the newest of a version, or one by its number, with the exit reason, times and last lines, or a note saying there is none yet. Nobody else can: not the members of a Space it is shared with, not the owner's other socios. `app_list` gives a promoted app no `logFile`: that file in the computer only has the output of the ephemeral copy.

`app_combine({ apps, name })` copies the packaged source of several of the user's apps into the socio's computer (`combined/<name>/<app>/…` with a `COMBINE.md` of their manifests) as the start of a new app, which then goes through register, package and promote like any other.

The app's settings: `APPS_RUNTIME_URL` (the runtime's API, `http://company-brain-apps:4330` in the stack; unset, apps can be packaged but not promoted), `APPS_RUNTIME_TOKEN` or `APPS_RUNTIME_TOKEN_FILE` (24+ characters, shared with the runtime and its egress proxy), `APPS_LOG_DAYS` (14) and `APPS_LOG_ATTEMPTS` (50, from 10 to 500) are the starting values for how long each promoted app's build and start logs are kept: an attempt stays for that many days or while it is one of the app's last attempts, whichever keeps more (an admin changes them under Settings, Mini app logs). `APPS_RUNTIME_INGRESS_PORT` (4331, on the runtime's host) and `APPS_RUNTIME_DATA_URL` (the data API as the runtime's apps reach it; `DATA_API_URL` by default). Every minute the app checks its promoted apps: after the runtime restarts (it keeps nothing) it deploys and starts their live versions again; after the app restarts (tokens live in memory) it gives them new tokens. A start that fails there is tried again after 1 minute, then twice as long each time (at most 30 minutes); after 6 failures the app waits until it changes (an update or a rollback) or its owner presses Start.

The runtime's settings (`pnpm run apps-runtime` locally, the `apps-runtime` image target in the stack): `APPS_RUNTIME_TOKEN`/`_FILE`, `APPS_RUNTIME_HOST`/`APPS_RUNTIME_PORT` (4330), `APPS_RUNTIME_INGRESS_PORT` (4331), `APPS_RUNTIME_DIR` (`/srv/apps`), `APPS_RUNTIME_COMMAND` (`bun`: `bun run` can't read the app's parent directories, so an old `bun run` is read as `bun`), `APPS_RUNTIME_UID_BASE` (unset: apps run as the runtime's user; 20000 in the image) with `APPS_RUNTIME_UID_COUNT` and `APPS_RUNTIME_GID`, `APPS_RUNTIME_PRLIMIT=on`, `APPS_RUNTIME_MEMORY_MB` (256), `APPS_RUNTIME_MAX_APPS` (20), `APPS_RUNTIME_START_SECONDS` (30, to open the socket), `APPS_RUNTIME_EGRESS_PROXY` (`http://company-brain-apps-egress:3128`; unset, apps reach nothing outside), `APPS_RUNTIME_REGISTRY` (`registry.npmjs.org:443`, where `bun install --frozen-lockfile --production --ignore-scripts` fetches locked dependencies; `off` refuses bundles with dependencies), `APPS_RUNTIME_INSTALL`, `APPS_RUNTIME_INSTALL_SECONDS` (180), `APPS_RUNTIME_PROXY_WAIT_SECONDS` (60, how long an install waits for the egress proxy to take connections: a new one only does once it is healthy), `APPS_RUNTIME_LOG_LINES` (500) and the `APPS_BUNDLE_*` caps (keep them equal to the app's). The apps' egress proxy (`dist/server/apps-runtime/egress-main.js`) takes `APPS_RUNTIME_TOKEN`/`_FILE`, `EGRESS_HOST` (`127.0.0.1`), `EGRESS_PORT` (3128) and `EGRESS_PUBLIC_ONLY` (on unless `false`: apps reach public addresses only; `false` lets them reach private addresses too). Load the telemetry opt-out (`DO_NOT_TRACK=1`, `COPILOTKIT_TELEMETRY_DISABLED=true`) for both, as for the app; the runtime passes `DO_NOT_TRACK=1` to every app it starts.

### Secrets for workspace apps and plugins

Socio Secrets: a promoted app (phase 1) or an installed service plugin (phase 2) gets the third-party keys it needs (a payment provider's key, a webhook URL) from Socio at runtime, instead of from its code, its `env` settings or a hand-made Docker secret. There is no setting to turn on and nothing to create by hand.

- **Declaring.** The app's manifest lists them: `"secrets": [{ "name": "STRIPE_API_KEY", "required": true, "description": "Charges cards" }]`. Names are `UPPER_CASE` (letters, digits, `_`); `required` is true unless set to false; a name can't also be an `env` setting. A name the manifest of the version the app runs doesn't declare can't be granted or read.
- **Managing.** Workspace admins, in **Settings → Secrets**. A secret is either the **workspace**'s, readable only by the apps an admin grants it to, or one app's **own**, readable by that app alone and deleted when the app is. Values are write-only: they're never shown again, in the UI or in any API answer. **Replace** makes a new version; the old one stays readable for a window the admin picks (an hour by default, up to a week, or none) so a rotation doesn't break a running app. **Delete** is a soft delete: apps can't read it any more, its grants end at once, and its sealed versions are kept for the record (nothing purges them yet). An app whose required secrets aren't all set shows **Needs setup** on its card on **Apps** and on Settings → Secrets; it still starts.
- **Reading.** The app calls `GET /api/workload/secrets/<NAME>` (or `?names=A,B` for several, all or nothing) with its data token, `Authorization: Bearer $CB_DATA_TOKEN`: the answer is `{ value, version, expiresAt }` with `Cache-Control: no-store`; `?version=<n>` reads the previous version during its window. The SDK's `secrets.get`, `secrets.require` and `secrets.onRotate` do this with an in-memory cache ([packages/app-sdk/README.md](../packages/app-sdk/README.md#secrets-secrets)). A name that isn't declared, set or granted gets 403. Reads are limited to 120 a minute per app or plugin (429 past that). Only promoted apps' tokens and plugins' identity tokens are accepted: a development app on a socio's computer can't read secrets yet, and socios get none.
- **Plugins (phase 2).** A service plugin declares `secrets` at the top level of its manifest, the same shape ([PLUGINS.md](PLUGINS.md#manifest)); it is listed under **Plugins** on Settings → Secrets with the same needs-setup, grant and set-its-own actions, and its own secrets are deleted (softly) when it is uninstalled. It reads with its own **identity token**, the file `SOCIO_IDENTITY_FILE` names, plus its proof (`x-cb-plugin-proof`, from `CB_PLUGIN_PROOF`); `socio.secrets` in `@socio/app-sdk` does this for it unchanged. Socio mints that token per plugin, stores it hashed and rotates it on every provision; the apps runtime delivers it (on Swarm, a secret `<PLUGIN_NAME_PREFIX>-wl-<id>-v<n>` created through the socket proxy and mounted at `/run/secrets/socio_identity`; in development, `APPS_RUNTIME_IDENTITY_DELIVERY=local` and `APPS_RUNTIME_IDENTITY_DIR` write a 0400 file instead, refused behind the proxy). Audit lines name the plugin as `plugin:<id>`. Details: [PLUGINS.md, Calling back into Socio](PLUGINS.md#calling-back-into-socio).
- **Retired: `PLUGIN_SERVICE_TOKEN` and `service.secrets`.** The shared plugin token is read for one more release, with a warning at boot (`PLUGIN_SERVICE_TOKEN is deprecated: …`, like a renamed setting's) and one per plugin that still calls with it; it never reads secrets. Socio gives every enabled plugin installed before phase 2 its own identity at start (retried every 10 minutes), so the warning should stop on its own. `PLUGIN_SERVICE_TOKEN_SECRET` is no longer read (a warning if set). A plugin manifest's `service.secrets` (Swarm secrets) still mounts for one release with a warning at catalog load. **Migration:** nothing to do for the bundled planner. For a `file:` catalog plugin, move each `service.secrets` entry to a declared `secrets` name, set or grant it on Settings → Secrets, and read it with `socio.secrets`; read the identity from `SOCIO_IDENTITY_FILE` instead of `SOCIO_API_TOKEN_FILE`. After the next release, remove `PLUGIN_SERVICE_TOKEN(_FILE)` and its secret from the deployment.
- **Records.** Every change (create, replace, delete, grant, revoke) and every read and refused read is a line in the workspace audit (`workspace_audit`, target `workspace_secret`), with the secret's name, the version and the app or plugin, never the value. Settings → Secrets shows when each version was set and by whom, and when the secret was last read and by which app or plugin.
- **History (phase 4).** **History** on a secret opens what the audit lines say about it, deleted secrets included (`GET /api/workspace-secrets/<id>/history`, admins only): its versions (set when, by whom, current, previous or retired), each app's or plugin's reads (first read, last read, how many, and refused attempts), and its events newest first, 50 a page (**Show older**, `?before=<id>&limit=` up to 100): created, replaced, description changed, deleted, granted, revoked, and **First read by a new workload**, once per app or plugin. Names and versions only, never a value.
- **Read flags (phase 4).** Every 5 minutes, on the leader, Socio runs three conservative rules over the audit lines and flags what they find under **Unusual reads** on Settings → Secrets, telling every active admin once per new finding (a Socio notice, `workspace_secret_flag`, linking to Settings → Secrets). Each flag says why, with its numbers, never a value:
    - **Unusual read rate:** an app or plugin read its secrets at least 100 times in the last hour and at least 10× its own hourly average over the week before (it needs a read more than a day older than that hour, so a new one isn't flagged).
    - **Reads after a revoke:** at least 5 refused attempts to read a secret, counted from 5 minutes after an admin revoked its grant (when a value read before has left the SDK's cache), within the last 24 hours, and not granted again since.
    - **Stale plugin identity:** a plugin read, or tried to, with an identity version older than its current one more than 10 minutes after the new one was issued (its rolling update should be over), within 24 hours. Plugin reads' audit lines now carry `identity v<n>`, and `stale (current v<m>)` when that applies; a retired identity used with the plugin's proof is refused and audited too (`identity no longer accepted`, at most once a minute per version).

    One finding is one open flag: later runs refresh it, they don't repeat it or its notice. **Dismiss** keeps the flag as the record; only evidence newer than the dismissal flags it again. The thresholds are named constants in `packages/shared/src/workspace-secrets.ts`.

- **Rotate identity (phase 4).** Each enabled plugin service is listed under **Plugins** on Settings → Secrets, even one that declares no secrets, with **Rotate identity**: after a confirmation it calls `POST /api/plugins/<id>/identity`, which mints a new token and updates the service; the old token is accepted for 15 minutes while old tasks drain.
- **Storage and recovery.** Values are sealed with the data key under their own purpose, `workspace-secrets`, in the app database (`workspace_secrets`, `workspace_secret_versions`, `workspace_secret_grants`, workspace-secrets migration 1; read flags in `workspace_secret_flags`, migration 2), so the database backup and the recovery kit cover them. The legacy-sealed count, the re-seal and the recovery key check include them ([Recovery keys](#recovery-keys)).
- **Redaction.** The values an app may read (and has read) are redacted from its build and start logs and from its socio's computer output, like its data token.

Workspace plugins are the same runtime's other workload: one Docker service per installed plugin, reached through the apps proxy. They are off until an admin installs one from this instance's catalog. See [PLUGINS.md](PLUGINS.md) for the manifest, the service spec, replicas, and how to offer the social planner on one instance only.

## Domains

Operators set up the app's host names from the **Platform** page (Settings → Platform, the **Domains** card). The workspace provisions them on demand through the existing Nginx Proxy Manager (NPM) and Cloudflare DNS:

- **Set up domains** (later **Repair**) makes the base: A records for `DOMAINS_BASE` and `*.DOMAINS_BASE` pointing at `DOMAINS_TARGET_IP` (DNS only, never proxied, TTL automatic), one Let's Encrypt certificate for both names by DNS-01 through Cloudflare, and a proxy host for each name with that certificate, forwarding to `DOMAINS_UPSTREAM` (Websockets Support, HTTP/2, Force SSL, HSTS and Block Common Exploits on; NPM passes the Host header through unchanged). It reuses what exists, found by domain, and fixes drift: a record with another address or proxied, extra A records for the same name, a missing proxy host, or one whose upstream, certificate or switches changed. Running it again changes nothing. With the defaults, the app is `brain.example.test` and mini apps are `app-<…>.brain.example.test`, all under the one wildcard certificate.
- **Provision** takes a host name under `DOMAINS_ZONE` that the wildcard doesn't cover (for example a custom app domain `x.example.test`, or a deeper name like `a.b.brain.example.test`) and gives it an A record, its own certificate and a proxy host. It refuses names outside the zone, the base, and names one label under the base (the wildcard covers them). It never changes an A record it didn't create that points elsewhere (the operation fails and says so); one that already points at the target is used as it is.
- **Remove** (on a provisioned name) deletes only what the module created: its proxy host, its certificate (unless another proxy host uses it) and its A record (one it found already there stays). The base isn't removed this way.
- **Status** shows the base (ready or needs repair), the provisioned names with their certificates' expiry, and the recent operations. NPM is read live; the A records as of the last operation (Cloudflare is called only by operations).

Operations run one at a time in the background (a certificate can take a few minutes while certbot waits for DNS); the card polls until it ends. Each is audited in `domain_ops` (who, what, every step, the error), with secrets redacted. Admins only: members get 403 from `/api/domains`.

Settings (the module is off, and the card says which are missing, until every one but the ACME address is set; a secret whose value is `none` counts as unset). The values are examples from one self-hosted setup, with Nginx Proxy Manager running as `ingress_proxy` on a `proxy` overlay network and the app's host at `10.0.0.10` on the LAN; use your own proxy's names and addresses:

| Setting                                                                                | Example value                                                                                                                |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `DOMAINS_ZONE`                                                                         | `example.test`, the Cloudflare zone                                                                                          |
| `DOMAINS_BASE`                                                                         | `brain.example.test`, under the zone                                                                                         |
| `DOMAINS_TARGET_IP`                                                                    | `10.0.0.10`: where the A records point (a LAN address, so the records must stay DNS only)                                    |
| `DOMAINS_UPSTREAM`                                                                     | `http://company-brain_app:4310`: what the proxy hosts forward to, over the `proxy` network                                   |

**The ACME address.** NPM 2.14 takes no address with a certificate request: certbot registers the email address of the NPM user that asks. So the module's NPM user's email is the Let's Encrypt account address, and before requesting a certificate the module checks that it is `DOMAINS_ACME_EMAIL` (`GET /api/users/me`) and refuses otherwise. Use a role address you control (for example `certs@example.com`), never a person's. Let's Encrypt uses it only for account notices.

**The NPM user.** The workspace uses an NPM user of its own that sees and changes only the items it created. An NPM administrator creates it once, signed in to NPM (in the example setup `http://ingress_proxy:81`, or the admin UI's published address) with the admin login:

1. **Users → Add User.** Full name `Socio`, nickname `brain`, email: the `DOMAINS_ACME_EMAIL` address. Leave **Administrator** off and **Disabled** off. Save.
2. On the new user's menu, **Permissions**: Item visibility **Created items only**; Proxy hosts **Manage**; SSL certificates **Manage**; Redirection hosts, 404 hosts, Streams and Access lists **Hidden**. Save.
3. On its menu, **Change password**: a long random password (e.g. `openssl rand -base64 32`). Don't turn on two-factor authentication for this user (the module can't answer a challenge).
4. Put the login straight into the secret, without it passing through stack env, chat or shell history: Portainer's **Secrets → Add secret** form as `company_brain_npm_credentials` with `{"email": "<DOMAINS_ACME_EMAIL>", "password": "<the password>"}`, or a mode-0600 file base64'd into the `Data` of `POST /api/endpoints/1/docker/secrets/create`, then deleted.

The same with NPM's API and an admin token (`POST /api/tokens {identity, secret}`): `POST /api/users {"name": "Socio", "nickname": "brain", "email": "<address>", "roles": [], "is_disabled": false}`, then `PUT /api/users/<id>/auth {"type": "password", "secret": "<password>"}` and `PUT /api/users/<id>/permissions {"visibility": "user", "proxy_hosts": "manage", "certificates": "manage", "redirection_hosts": "hidden", "dead_hosts": "hidden", "streams": "hidden", "access_lists": "hidden"}`.

Proxy hosts made earlier with another NPM login (say, `brain.example.test` by the admin) are invisible to this user, and NPM refuses a second proxy host for a name already in use: delete them before **Set up domains**, or the operation fails with NPM's "already in use".

**The Cloudflare token.** In Cloudflare, **My Profile → API Tokens → Create Token → Custom token**: permission **Zone → DNS → Edit**; zone resources **Include → Specific zone → example.test**; nothing else (optionally a client IP filter for the host's public address and an expiry). Put it straight into the secret `company_brain_cloudflare_dns_token`, as above. The module looks the zone up by name (`GET /zones?name=`); if the token can't list it, set `CLOUDFLARE_ZONE_ID`. The same token goes to NPM with each certificate request, as certbot's DNS-01 credentials (`dns_cloudflare_api_token = …`); NPM keeps it in its database and its `letsencrypt` credentials file to renew. To rotate it, create a new token, a new secret (`…_v2`), point `CLOUDFLARE_DNS_TOKEN_SECRET` at it, redeploy, run **Repair** (existing certificates keep the old token for renewals until they are requested again; delete and set up the base again if you revoke the old one) and revoke the old token.

Until both secrets exist, create them with the value `none` (the stack names them): the module stays off and the card names the missing settings. Point `NPM_CREDENTIALS_SECRET` and `CLOUDFLARE_DNS_TOKEN_SECRET` at the real secrets when they exist and redeploy.

**For apps, later.** A promoted app that wants a custom domain will call `platform.domains.provision(hostname, { actor: 'app:<id>' })` (server side; it throws a `DomainsError` for a refused name or while another operation runs, and otherwise resolves with the audited op and the host's state). There is no UI or socio tool for that yet.

## Schedules and jobs

Socios can propose recurring work: a **schedule** runs either a turn of the socio with a fixed prompt, in a conversation of its own, as its owner and on the owner's inference, or a **job**: code the socio saved (Bun `main.ts` or bash `main.sh`) that runs in the socio's computer without the model. New schedules and each job version need the owner's approval (Approvals; bypass per socio and capability), and the owner pauses, resumes, cancels, runs and inspects them under Schedules & jobs. Cadences are phrases (`every day at 09:00`, `every 6 hours`, `every monday at 08:30`) or five-field cron, in the time zone the socio passes, else UTC. Schedules are claimed by the same scheduler as the tasks people make in a conversation, which needs research allowed in Settings.

A job run wakes the socio's computer through the supervisor (up to `JOB_WAKE_SECONDS`, 90, counted in the job's timeout), copies the job's files (stored encrypted in the owner's data space) into a fresh directory, and runs them under `timeout` with a data token for that run only (the job's datasets and the socio's scratch dataset; `CB_DATA_URL` and `CB_DATA_TOKEN` in the environment, so `DATA_API_URL` must be set), then keeps the exit code and the end of its output (tokens redacted) and revokes the token. Every run is kept; the newest 50 of each job keep their output, and older ones show "Output not kept for older runs." with their times, status and exit code. Jobs need a computer service and the socio's shell permission. A deploy's drain waits for job runs like turns; longer ones are stopped at `SHUTDOWN_DRAIN_MS`, and an operator's force stop stops them too.

Limits, for every socio: `SCHEDULE_MIN_INTERVAL_MINUTES` (15) between runs, `SCHEDULES_PER_USER` (20) active schedules, `JOB_MAX_TIMEOUT_SECONDS` (900), `JOB_CONCURRENCY` (2) runs at once in the workspace, `JOBS_PER_USER` (50), and for jobs that run until done (below) `JOB_ITEM_ATTEMPTS` (3), `JOB_BATCH_RETRIES` (5) and `JOB_MAX_BATCHES` (200). An admin can change all eight in **Settings → General → Schedules and jobs**; what they save takes the place of the variables, which stay the starting values. Each user sees only their own schedules and jobs; operators also see the workspace's counts.

### Jobs that run until done

How a job run ends without this (CB-122): the server drives each run from outside the computer. It wakes the computer, starts `run.sh` detached (`setsid`) when the timeout is over 45 s, and polls for `exit.code` every 2 s; `timeout` kills the job at its own timeout (at most `JOB_MAX_TIMEOUT_SECONDS`, so a collection job budgets about 840 s of its 900). Its data token lives only in the server's memory. So a deploy drained the server for up to `SHUTDOWN_DRAIN_MS` (the turn limit plus 20 s), then stopped the run (`interrupted`, process killed); a restart without a drain marked every open run `interrupted` ("The server restarted during this run") and its token died with the process; a computer that stopped (idle, recycled, stopped by its owner) left the run polling until its deadline, then `timed_out` or "ended without an exit code". Nothing ran it again except the next scheduled run, which started from scratch, and a run that exited 0 was "succeeded" whatever was left.

A job saved with `untilDone` (`job_save`, shown as "runs until done" under Schedules & jobs) runs as a **long run** the server owns, in the database (`job_long_runs`, `job_items`; schedules migration 8), not the computer:

- Starting it (Run now, `job_run`, a schedule) opens its long run, or answers with the one already open. The server starts **batches**: ordinary job runs within the job's timeout, through the same queue and `JOB_CONCURRENCY`. After a batch that made progress the next starts at once; it ends only when the job's own completion condition holds: it declared its whole list of items and none is left, or it said it is complete. A batch exiting 0 is never the end.
- **Resuming.** A batch stopped from outside (a deploy, a restart, the computer stopping, a pause, a force stop, the owner deactivated) costs nothing: the items it held go back and the next batch starts from the checkpoint, at once if the stopped batch made progress, else after 30 s. A restart finds open long runs in the database and resumes them; a batch still running in the computer from before (its token died with the server) is stopped first. A deploy's drain doesn't wait for batches. The computer stopping now ends any run at once (`interrupted`, "The computer stopped during this run.") instead of at its deadline.
- **Each item once.** A batch claims items; only the batch that holds an item may mark it done or failed, and a done item is never handed out again. Writing an item's rows with an upsert key (`/done` with `write` does the write and the mark in one call) makes doing it again after a stop overwrite instead of duplicating.
- **Retries and the dead-letter list.** A failed item is retried after a wait that doubles from 30 s; after `JOB_ITEM_ATTEMPTS` tries (or `retry: false`) it is set aside with its error and the rest go on. A batch that crashes or times out is charged one try on the item it was on, not on the items it never reached, and that item waits as a failed one does. `JOB_BATCH_RETRIES` batches in a row that fail, make no progress or are refused end the long run as failed; each such retry waits twice as long (30 s, 1 min, 2 min…, at most 6 h). A batch that crashed or timed out while on an item made progress only if it got items done: neither the item it was charged for nor its checkpoint counts, even one that changes every batch, so a job that crashes every batch ends after its retries. One that crashed holding no item (say, while listing) still counts a moved checkpoint, and saving the same checkpoint again is never progress. A retry never starts before the next item is due, and a 403 or 429 wait holds even when the batch is then stopped or the server restarts. `JOB_MAX_BATCHES` caps one long run.
- **Refusals.** On a 403 or 429 the job calls `/fail` with the status (or `/pause`) and exits: the item's try doesn't count, nothing more is handed out, and the long run waits `retryAfterSeconds` if the source said, else 5 minutes (15 for a 403), doubling with each refusal in a row, then resumes.
- **Status.** Under Schedules & jobs the job shows "412 of 726 done"; its details show Progress: items done, left, in progress and failed, batches, the last checkpoint, the retry count and what it waits for, the items set aside with their errors, the outcome, and **Stop**. The socio's `job_status` tool answers the same, so it can say how it is going without reading logs.
- **The end.** Getting through every item is not success by itself: a long run ends `done` only if no more of its items were set aside than done ("is done, but not all of it" when some were), else `failed`. A long run started from a chat is reported there: a turn of the socio runs once the chat is free, from a hidden note with the outcome (as after an approval), its reply posted in Telegram too. Otherwise (a schedule, Run now, a chat it can't use) the owner gets a notification ("Job done", "Job done, with failures", "Job failed" or "Job stopped"), within the daily notification limits. An end the server didn't get to report before a restart is reported at the next start.

The checkpoint API is `$CB_JOB_API` (`$CB_DATA_URL/job`), with the batch's own data token, JSON in and out; a session can't use it, and a token of a job that runs once gets 409:

| Call                                                                     | Does                                                                                                             |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `GET /`                                                                  | the long run's counts, the batch number and the checkpoint                                                       |
| `POST /items {"keys": [...], "complete": true}`                          | declares items (keys up to 200 characters, 1,000 a call; again is harmless); `complete` says that is all of them |
| `POST /claim {"limit": 10}`                                              | up to 200 items for this batch; none, with `stop`, when it should exit                                           |
| `POST /done {"key", "write"?}`                                           | marks the item done, once; `write` (`dataset`, `table`, `rows`, `key` columns) upserts its rows first            |
| `POST /fail {"key", "error", "retry"?, "status"?, "retryAfterSeconds"?}` | the item failed; a 403 or 429 `status` pauses the long run instead of charging the item                          |
| `POST /checkpoint {"value"}`                                             | keeps up to 16 KB of JSON (a cursor) to resume from                                                              |
| `POST /pause {"reason", "status"?, "retryAfterSeconds"?}`                | a source refused: wait, then resume                                                                              |
| `POST /complete {"summary"?}`                                            | the job's own completion check holds (every item must be done or failed)                                         |

## Feature flags

Features can ship dark, be tried early, or be part of some plans only (CB-169, CB-182, CB-503). It is all in the app: no outside flag service, no telemetry.

- **Declared in code.** Every flag is an entry in `packages/shared/src/flags.ts`: its key, title, description, stage (`dev`, `early-access` or `ga`), safe default, owning area, removal date (`removeBy`, reported in the log once it passes), its board item, and the socio tools that exist only while it is on. Today there are six: `web-reads` (released, on), which turns `http_get` and `http_json` off for whoever it is off for; three in development and off, for socios using apps and coding gateways for a person (CB-232, CB-239, CB-267): `socio-actor-access`, `coding-sessions` and `repo-extraction`; and two in early access and off: `learning-analyze-now`, which hides Learning's **Analyze now** until it is fixed, and `datasets-in-spaces` (CB-451), which shows datasets in their Spaces and the **Private** group in the web app. Turning one off for a person, or for everyone, ends those people's socio access grants within a minute and stops their use within 5 seconds.
- **Deployment kind: `SOCIO_DEPLOYMENT_KIND`.** `internal` marks a deployment for the team that builds Socio. Any other value, or unset, is a customer deployment, the default. In a customer deployment a `dev` flag is never listed and never on, whatever `FEATURE_FLAGS`, a stored rule or a plan says: the evaluator checks it first, its routes answer 404, `/api/workspace` never has it on, its socio tools are off, and a `FEATURE_FLAGS` entry naming one is logged once at start and ignored. In an internal deployment `dev` flags layer like the others, and admins switch them on Settings → In development.
- **Evaluated on the server, per request.** `Platform.flags` decides each flag for one person from these layers, each replacing the one before: the code's default, `FEATURE_FLAGS` (this server's default, `flag=on,flag=off`), a stored rule for the server, the workspace's plan, and an admin's rule for the workspace. A rule is on for everyone, off, or on for some roles and people only. A locked server rule, and a plan that leaves a flag out, end it there. Nothing a person stores takes part: there is no personal opt-in. Nothing is cached: a change applies to the next request and the next socio turn.
- **Who sets what.** Admins set the workspace's rule on **Settings → Optional features** (`ga`), **Settings → Early access** (`early-access`, marked experimental) and, in an internal deployment, **Settings → In development** (`dev`), except for flags a locked server rule or the plan decides. Those pages show what this server's configuration decides (`FEATURE_FLAGS`, a stored server rule, the plan) read-only, and name no role above admin; the app has no editor for server rules or plans (the routes under `/api/flags/:key/instance` and `/api/flags/tiers` remain, for out-of-band tooling). Every change is a `workspace_audit` line (`feature_flag`, `flag_tier`), listed under Recent changes.
- **No personal opt-in (CB-503).** No route takes a person's own choice (`/api/flags/early-access` and `/api/flags/:key/choice` answer 404), a rule with `optIn` is refused (400), and `/api/workspace`'s `flags` carries only `on` (plus `internal` on an internal deployment). Flags migration 2 sets every stored rule's `optIn` to 0 and deletes every row of `flag_choices`; its triggers keep `optIn` at 0 and `flag_choices` empty while a previous release still writes them during a start-first deploy. The column and the table stay until a later contract migration drops them; each earlier choice remains in `workspace_audit`.
- **The client only shows.** Routes check flags themselves (`requireFlag`, a 404 when off), and each turn's tools leave out those of flags that are off for the person (`DotExtensions.toolsOff`), so the prompt never mentions them either.
- **Releases.** A release highlight whose board item is an early-access flag's shows an **Early access** badge in What's new; for admins, the What's new list links to Settings → Early access.
- **One workspace per server today.** The workspace's rules and plan are kept under its `TENANT_ID`, so more workspaces per server can come later without a migration. A central plane that pushes rules to many servers (a signed bundle from the operator's own plane) is not built.

To add a flag: add its entry, check it where the feature is served (`platform.flags.enabled(key, userId)` or `requireFlag`), list its tools, show it in the client with `useFlag` (and `EarlyAccessBadge`), and remove it by its date.

## Tracing

Every socio turn keeps a trace with its run (CB-128), in the runs table's `trace` column: each model round (its number, start and end, time to first output, tokens in, out and reasoning when the model reports them, and why it stopped: `stop`, `tool_calls`, `length`, `content_filter`, `error` or `cancelled`), each tool call (its name, start, duration, outcome, `ok`, `error`, `refused` or `timeout`, and a short error class such as `TimeoutError` or `rate_limited`), the waits for an approval or for the person, each time a round's prompt was fitted to the model's context (CB-129: its estimated tokens before and after, the window, how many tool results were cut or set aside, how many turns are in the chat's notes, and the retry, if the model had refused it as too long), and why the turn's loop ended: `completed`, `round_cap`, `time_limit`, `output_limit`, `error`, `model_unavailable` (no model could carry on, busy or out of reach), `stopped` or `interrupted`. The socio's own loop-end event gives the reason; without one it is worked out from how the turn ended. Rounds are timed at the model adapter, so this works the same on the shared models, a person's own ChatGPT plan and any OpenAI-compatible server. Each request to the model is traced, so a round the model refused as too long shows its retry (`retry: 1`, the same round), and the requests that write the chat's notes show as `summary`; neither counts as a round.

**Runs** shows a turn's trace as a timeline under its row (**Trace**): admins see every turn, members only their own conversations'. Each time an admin opens the trace of a turn from someone else's conversation, here or from a failure in Operations → Reliability, it is written to Operations → Access log (CB-188), and a trace that can't be written there isn't shown; a turn from before traces, and one's own, aren't written. The `Turn: finished` log line gains `reason=`, `rounds=` and, when the model reported them, `tokens_in=` and `tokens_out=`. A trace holds names, times, counts and codes: never prompts, answers, tool arguments or results.

### Sending traces to a collector

Off unless the operator sets an endpoint. With `OTEL_EXPORTER_OTLP_ENDPOINT` set, each finished turn goes to `<endpoint>/v1/traces` over OTLP/HTTP with a JSON body (`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, when set, is used as given). gRPC is not supported: use the collector's HTTP port (4318). `OTEL_EXPORTER_OTLP_HEADERS` (`key=value,…`, values URL-encoded; a secret, so `OTEL_EXPORTER_OTLP_HEADERS_FILE` works too) goes with every request and is never logged; `OTEL_SERVICE_NAME` names the service (`company-brain`); `OTEL_SDK_DISABLED=true` turns export off again. For example:

- **OpenTelemetry Collector** (the simplest front door; it batches, retries and fans out to the rest): `OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318`, with an `otlp` receiver that has `http` enabled.
- **Grafana Tempo:** its OTLP HTTP receiver, `OTEL_EXPORTER_OTLP_ENDPOINT=http://tempo:4318`.
- **Langfuse:** `OTEL_EXPORTER_OTLP_ENDPOINT=https://<langfuse host>/api/public/otel` and `OTEL_EXPORTER_OTLP_HEADERS=Authorization=Basic%20<base64 of public-key:secret-key>`.
- **Phoenix:** `OTEL_EXPORTER_OTLP_ENDPOINT=http://phoenix:6006`. A version that takes only protobuf goes behind the Collector, which converts.

What a trace carries, by the OpenTelemetry GenAI conventions: a turn span (`invoke_agent <socio>`: the socio's id and name, the conversation id, the model, the run's id, status and source, the loop's end reason, rounds and cap, and the tokens added up), with a child span per model round (`chat <model>`: `gen_ai.request.model`, `gen_ai.usage.input_tokens` and `output_tokens`, `gen_ai.response.finish_reasons`, the time to first output) and per tool call (`execute_tool <tool>`: `gen_ai.tool.name`, its call id, outcome and `error.type`), and the waits, context compactions (`company_brain.context_compaction`, with which pinned facts went with the round) and updates of a long chat's notes (`company_brain.context_notes`: whose model wrote them, turns, tokens, and a plain summary kept) as the turn's events; a retried round's span has `company_brain.round.retry`, a notes request's `company_brain.round.purpose=context_notes`. Never: people's names, emails or ids, the system prompt, memories, secrets or headers. Prompts and answers are left out unless an admin turns on **Settings → General → Tracing → Include content in traces** (off; `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true` is its starting value). Then the turn span carries what the person sent and the socio's answer (`gen_ai.input.messages`, `gen_ai.output.messages`) and each tool span its arguments and result, each cut to 4,000 characters; whoever can read the collector can read them.

Export never holds up or fails a turn: spans are built after the turn is stored and queued (at most 2,048; more are dropped and counted), sent every 2 seconds, one request at a time with a 10-second limit, and a failed request is logged at most once a minute (`Trace export: …`) and not retried. It goes only to the endpoint set here, never to a vendor (see `packages/foundation/src/no-vendor-telemetry.ts`).

## Backups

All data (pages, Spaces, socios, users, conversations and their runs, tasks, memories, Telegram links and Learning) lives in the one SQLite file at `DATABASE_PATH`, except the users' data spaces (below), which live in `USER_DATA_DIR`.

The server backs them up on its own every `BACKUP_INTERVAL_HOURS` (default 24, counted from the last attempt, so restarts don't reset it; a failed one is retried within the hour; `0` turns it off). An admin can change it in **Settings → General → Backup schedule**; what they save there takes the place of the variable, which stays the starting value, from the server's next check (within 5 minutes, no restart). By hand, the same backup:

```sh
pnpm run backup
```

Each backup copies the database with SQLite's backup API, off the main thread and in one read transaction, so the server keeps answering and writing meanwhile, checks its integrity, and keeps the newest `BACKUP_KEEP` (default 14) files in `BACKUP_DIR` (default `data/backups`; `/backups`, its own volume, in the stack), named `company-brain-YYYYMMDD-HHMMSS.sqlite` (UTC). In a container, `docker exec <container> node dist/server/server/backup/backup-cli.js`. One backup runs at a time (`BACKUP_DIR/.backup-running`, which a running backup touches every minute; one cut off by a crash or a redeploy is taken over after 15 minutes, and the next run removes the `.partial` copies it left). A run that fails (S3 unreachable, a full disk) removes its own copies, so it never counts against `BACKUP_KEEP` or pushes a good backup out; old backups are pruned only after a run completes. The result (last success, size, last error, the off-site copy) is in `BACKUP_DIR/backup-status.json`, which admins see on the Settings dialog's Service setup; the server logs counts and sizes only. Put `BACKUP_DIR` on another volume than the data, and keep a copy off the host: the [off-site copy](#off-site-copy) does that.

Each scheduled backup also takes a snapshot of every enabled service plugin that declares `service.backup` (CB-458; docs/PLUGINS.md, Volumes and backups), into `BACKUP_DIR/plugins/<id>/`: chunks stored once by hash and every record sealed under the data key, so they need `DATA_ENCRYPTION_KEY`. A plugin's failure never fails the run; it shows under **Plugin data** on Service setup and notifies admins. What happened to each plugin is in `BACKUP_DIR/plugin-snapshots.json`. One plugin's snapshot holds at most `PLUGIN_BACKUP_MAX_GB` (20 by default), which an admin changes in **Settings → General → Plugin backups**. `pnpm run backup` takes none (it can't reach plugins), but prunes the store with its run and sends what it keeps off-site.

To restore:

1. Stop the server (or scale the service to 0).
2. Move the current `DATABASE_PATH` file aside, together with its `-wal` and `-shm` files.
3. Copy the backup to `DATABASE_PATH`.
4. Start the server. Runs that were streaming when the backup was taken are closed as interrupted and keep their partial output.

A backup also copies the data spaces into `BACKUP_DIR/userdata-YYYYMMDD-HHMMSS/`: each dataset with the backup API, each file as stored (still encrypted, so restoring needs the [data key](#data-encryption-key), and `SESSION_SECRET` for anything not yet re-sealed). Their metadata (datasets, grants, audit) is in the database backup, so restore the two from the same run: put the `userdata-…` directory's contents back as `USER_DATA_DIR`.

With object storage, the tenant's objects are mirrored into `BACKUP_DIR/objects/`, still encrypted, incrementally: an object is fetched only when its size and ETag (or LastModified) changed since the last backup, and objects gone from the bucket are removed from the mirror (`BACKUP_DIR/objects.json` remembers what it has; an interrupted mirror resumes). Each backup then gets the mirror as of that run in `userdata-…/objects/`, as hard links, so unchanged objects take no extra space and an object deleted later stays in the older backups until they are pruned. Each file's path there is its key: restore them into the bucket under the same keys (leave `objects/` out of `USER_DATA_DIR`).

### Off-site copy

With `BACKUP_S3_ENDPOINT` set, each backup is also copied to any S3-compatible store (AWS S3, Backblaze B2, Cloudflare R2, MinIO, another SeaweedFS, …); it is off otherwise. Settings, like the data space's: `BACKUP_S3_BUCKET` (required, created when missing), `BACKUP_S3_REGION` (`us-east-1`), `BACKUP_S3_FORCE_PATH_STYLE` (`true`), `BACKUP_S3_PREFIX` (empty; `company-brain/` in the stack) and `BACKUP_S3_CREDENTIALS` or `_FILE` (`{"accessKeyId": "…", "secretAccessKey": "…"}`). It needs `DATA_ENCRYPTION_KEY`: the database and datasets are plaintext on the backup volume, so they are sealed under the data key before they leave (`….sqlite.sealed`); files and objects already are. Under the prefix:

- `snapshots/<YYYYMMDD-HHMMSS>/company-brain.sqlite.sealed` and `snapshots/<…>/userdata/…`: the newest `BACKUP_KEEP` complete backups. `snapshots/<…>/complete` is written last; a snapshot without it is from a copy that failed midway, doesn't count, and is removed by the next copy that succeeds;
- `snapshots/<…>/plugins/<id>/<snapshotId>.json.sealed` (CB-458): that run's plugin snapshots, sent before `complete`; `plugin-snapshots/<id>/<stamp>-<snapshotId>/snapshot.json.sealed`: those the backup volume keeps outside a kept run (Back up now, a plugin's request, a plugin's newest good one past its run), removed off-site once the backup volume no longer keeps them; and `plugin-chunks/<id>/<name>.sealed`: each chunk they list, once, named by an HMAC of its SHA-256 under a key derived from the data key, sent again when it was sealed under another key, and removed once no kept snapshot can need it. All of them are sealed on the backup volume already (`BACKUP_DIR/plugins/<id>/`) and go as stored. `BACKUP_DIR/offsite-plugins.json` records what was sent;
- `objects/<key>`: the object mirror, sent incrementally (only what changed). An object gone from the bucket stays until every kept snapshot is newer than the first one without it, so each kept snapshot's objects are there. It holds each object's latest version: a file replaced since a snapshot comes back as it is now.

Only sealed bytes leave: a file that isn't sealed (the database and datasets are sealed here, files and objects must already be) stops the copy with `the off-site copy failed: A file for the off-site copy isn’t sealed…`.

A failed copy keeps the local backup and is shown on Service setup (`the off-site copy failed: …`); the next backup tries again. To restore from it, download a snapshot and open the sealed files with the data key: `node dist/server/server/backup/backup-cli.js open company-brain.sqlite.sealed company-brain.sqlite` (with `DATA_ENCRYPTION_KEY`, or the old key as `DATA_ENCRYPTION_KEY_PREVIOUS`), then restore as above.

With the [continuous copy](#continuous-copy) set up too (`LITESTREAM_REPLICA_DIR`), its files go off-site between the daily backups as well: see [Continuous copy off-site](#continuous-copy-off-site).

### Continuous copy

The stack also runs [Litestream](https://litestream.io) 0.5.17 as its own service, `litestream` (CB-109). It copies each write to `DATABASE_PATH` into a file replica on the backup volume, `/backups/litestream/company-brain`, within about a second. It keeps 14 days of history (`snapshot.retention: 336h`, a fresh snapshot every 6 hours), so the database can be restored to any point in them: to the second for the last few minutes, and to the hour further back. The daily backups stay a second copy, apart from it. Litestream 0.5 can't encrypt its copy, so Litestream itself never sends it anywhere; the app seals its files and sends them off-site ([below](#continuous-copy-off-site)). The datasets stay out (they keep `journal_mode=DELETE`); the daily backups have them.

The service's config is written in its command, in the stack file. It runs as the app's user (uid 1000) with one replica, `stop-first`, so there is only ever one Litestream writing the replica. It adds two tables of its own to the database, `_litestream_seq` and `_litestream_lock`, and keeps its state next to it in `.socio.sqlite-litestream/`. It turns unhealthy when the database's WAL changed over 2 minutes after the newest copy. With `LITESTREAM_REPLICA_DIR` set on the app (`/backups/litestream/company-brain` in the stack), Service setup shows `Continuous copy: …` and the Operator page a card: the newest copy and the last write, and `behind` when a write is over 5 minutes newer than the newest copy.

Run the commands below in the `litestream` service's container, `docker exec -it <container> sh`. Its config is `/tmp/litestream.yml`.

To see the restore points: `litestream ltx -config /tmp/litestream.yml -level all /data/company-brain.sqlite`.

To restore a copy, the live database untouched (a drill, or to look something up):

```sh
mkdir -p /backups/restore
litestream restore -config /tmp/litestream.yml -timestamp 2026-10-19T14:04:31Z \
  -o /backups/restore/company-brain.sqlite /data/company-brain.sqlite
```

Leave out `-timestamp` for the latest. The file at the timestamp itself isn't included. `-o` must not exist yet. Check it with `PRAGMA integrity_check` (from the app's container: `node -e` with `node:sqlite`, read-only), and delete `/backups/restore` afterwards.

To put the database back to a point in time:

1. Restore a copy as above, and check it.
2. Stop the app and the `litestream` service (scale both to 0 in the stack).
3. Move the current `DATABASE_PATH` aside, with its `-wal` and `-shm` files, and remove `/data/.socio.sqlite-litestream/`.
4. Copy the restored file to `DATABASE_PATH`.
5. Start `litestream`, then the app. Litestream logs `detected database behind replica` and goes on from there: later restores follow the restored database, and the points before it are still there to go back to.

Restoring one of the daily backups works the same way while Litestream runs: stop both and remove `.socio.sqlite-litestream/` too (steps 2, 3 and 5).

#### Continuous copy alerts

With Litestream on, the app leaves checkpoints to it, so while it is down nothing is copied and the database's write-ahead log (`DATABASE_PATH-wal`) only grows. Every minute the app compares the newest copy in the replica with the last write (the lag: with a write newer than the newest copy, the time since that copy, so it keeps growing after writes stop; 0 when the copy covers the last write, so an idle database is never behind; with no copy at all, since the server started) and reads the log's size. Either past its threshold makes the copy `warning` or `critical`: 5 and 30 minutes of lag, 256 MB and 1 GB of log by default (`LITESTREAM_LAG_WARN_MINUTES`, `LITESTREAM_LAG_CRITICAL_MINUTES`, `LITESTREAM_WAL_WARN_MB`, `LITESTREAM_WAL_CRITICAL_MB`), which an admin can change in **Settings → General → Continuous copy alerts**.

- **Where it shows.** Operations → Health (Continuous copy: the level, the lag and the log's size), Service setup and the Operator page. `/healthz` gives the level only, `litestream: off | ok | warning | critical` (`off` without `LITESTREAM_REPLICA_DIR`), with no paths, sizes or times.
- **Who hears.** Every admin gets a notification, as for a failed restore drill, when the level changes, a reminder at most hourly while it stays critical, and `Continuous copy recovered` once it is back to ok. The log says `Continuous copy: …` each time. The state is kept in memory: a server that restarts while the copy is behind tells admins again.
- **The safety valve.** Once the log is past its critical size while the copy has been critically behind, the app runs `PRAGMA wal_checkpoint(PASSIVE)` from a connection of its own, at most every 10 minutes, logs it and tells admins once (and again if a reader holds it short of the log's end, when the log can still grow). PASSIVE never waits on or interrupts anyone and never truncates the log: it copies committed pages into the database up to the oldest reader. While Litestream runs it holds a read transaction for exactly this reason, so the checkpoint can't pass a frame it hasn't copied and changes nothing. Only with Litestream gone does it reach the end of the log; the next write then starts the log over instead of growing it, so the disk stops filling (the file keeps its size until Litestream truncates it). The frames reused were never copied: when Litestream is back it finds its position gone and starts from a fresh snapshot. No data is lost (it is all in the database), only the points in time inside the outage, which a full disk would cost anyway.

### Continuous copy off-site

With the [off-site copy](#off-site-copy) (`BACKUP_S3_ENDPOINT`) and `LITESTREAM_REPLICA_DIR` both set, the app also sends the continuous copy off-site (CB-112), so losing the host loses minutes of work, not up to a day. Every `BACKUP_LTX_INTERVAL_SECONDS` (default 60; `0` turns it off; otherwise 10 to 86400) it seals each new file of the replica (`ltx/<level>/<min txid>-<max txid>.ltx`) under the data key, exactly like the database of a daily backup, and sends it to `litestream/<lineage>/ltx/<level>/<name>.ltx.sealed` under `BACKUP_S3_PREFIX`. An admin can change the interval in **Settings → General → Backup schedule**, over the variable; the server reads it every 10 seconds, no restart.

The first send uploads the whole replica, and the target then holds what the replica holds: with the stack's Litestream settings, about 56 full copies of the database (a snapshot every 6 hours, kept 14 days) plus the changes between them, 4 more copies a day. Count on that much storage at the target, and on one listing of the lineage per send (once a minute by default). Each file is read and sealed in memory, so the largest takes about twice its size in RAM while it goes.

- **Incremental.** `BACKUP_DIR/offsite-ltx.json` remembers each file sent (name, size, time, SHA-256, the key that sealed it and the sealed size). A file goes when the target lacks it, it changed (size, then hash; a file only touched isn't sent) or it was sealed under an older data key. A restart sends nothing twice.
- **Whole files only.** Litestream writes each file as `<name>.tmp` and renames it once synced; the app reads only `.ltx` names, checks the file is an LTX file (`LTX1`, its header and trailer) and that it didn't change while it was read. One that fails a check waits for the next send; while one waits nothing off-site is removed, and one that keeps failing it (not an LTX file) shows on Service setup as `N file(s) waiting; nothing off-site is removed until they go`, in red once it has waited over the interval and 5 minutes.
- **The highest level first.** Each send goes from the snapshots (level 9) down to level 0, each level from its oldest file. Litestream writes a compacted file into the higher level before it removes the files it replaces, so a send cut short at any point (a failure, a restart, the host lost) leaves the lineage restorable, to the same transaction as before it or a later one: after an outage longer than Litestream keeps level 0, the level 1 file holding the transactions in between goes before the newer level 0 files. A file that went before it was read, or waits, and isn't off-site yet holds back the rest of its level and the levels below it until the next send, so they can't leave a gap a restore stops at.
- **Compaction and retention, mirrored.** Litestream compacts level 0 into higher levels and drops files older than its retention (14 days). Once every file the replica has is off-site, the app removes a file Litestream removed only when it sent that file itself (`offsite-ltx.json` records each file before it goes, so a send cut short still knows it) and another file it sent, off-site as sent, holds the same transactions: the level it was compacted into, or a newer snapshot. So the lineage holds what the replica holds, and a file nothing replaced stays. It removes nothing while a file waits (it may be the one that replaces them), when the replica has no files (an unmounted volume), when a directory of it can't be read (the send fails with `Some of the continuous copy's files can't be read (EACCES); …`, after sending what it could read), or when a send failed midway. The daily snapshots (`snapshots/`, `objects/`) are apart from it.
- **Lineages.** The app only adds to, overwrites or removes files in its own lineage, `litestream/<lineage>/`, named after when it started (`20261020T090000Z-a1b2c3`) and recorded in `offsite-ltx.json`. It starts a new one when that file is missing (a new host, or the backup volume lost), when Litestream started over (its newest transaction is below the newest one sent, as after a restore; only told by a listing of every level, so a level that can't be read doesn't start one), or when the lineage off-site has a file that `offsite-ltx.json` doesn't record as sent, or a transaction newer than the replica's: `/backups` put back from an older copy, or a second host sending with a copy of it. It leaves the older ones as they were, logging `Continuous copy off-site: sending a new lineage, …; the N older one(s) stay off-site until removed by hand.` So a new host that starts before the restore can't remove or overwrite the copy you are about to restore. Two hosts sending at once each move to a lineage of their own as soon as one sees the other's files; within the same send they can still overwrite a file of the same name, so stop the old host's app (or set its `BACKUP_LTX_INTERVAL_SECONDS=0`) before a new one sends. Remove an older lineage (`litestream/<lineage>/` under the prefix) with the target's own tools once you no longer need it; the app never does.
- **Failures** are retried later each time (twice the interval per failure in a row, up to 30 minutes), logged once per streak (`Continuous copy off-site failed: …`, and `… sending again after a failure.` when it works again), and shown on Service setup: `Continuous copy off-site: every 60 seconds; everything up to <time> is off-site`, in red with `the last send failed at <time> (3 in a row): …` or `behind: the newest copy has waited 7 min` once a copy has waited over the interval and 5 minutes.

To restore from it (the host is gone, or for a drill), on any machine with Node, the app's build and Litestream 0.5:

> **On a new host, restore before the app sends.** Do the steps below before you start the stack on the new host if you can. If it has to start first, set `BACKUP_LTX_INTERVAL_SECONDS=0` and `BACKUP_INTERVAL_HOURS=0` in its stack env until the restored database is in place: nothing the old host sent is removed either way, but this keeps the new host from sending an empty database's lineage, and daily snapshots of it that push out the older ones.

1. Fetch the replica, with the `BACKUP_S3_*` settings and `DATA_ENCRYPTION_KEY` (or the old key as `DATA_ENCRYPTION_KEY_PREVIOUS`) in the environment:

    ```sh
    node dist/server/server/backup/backup-cli.js fetch-ltx /restore/replica
    ```

    (`pnpm run backup fetch-ltx /restore/replica` from a checkout.) With one lineage off-site it takes that one. With more, it lists them, the newest first, with their files and newest transaction, and asks for one: `fetch-ltx /restore/replica <lineage>` (after a disaster, the lineage from before the disaster, by its date, not the new host's). It downloads and opens each file of the lineage into `/restore/replica/ltx/<level>/<name>`, dated by its header as Litestream dates its own, and lists again until nothing new shows, so files the app sent meanwhile are there too. The directory must be new or empty. Or by hand: download the lineage's `.ltx.sealed` files, open each with `backup-cli.js open <name>.ltx.sealed <name>.ltx`, and lay them out the same way.

2. Restore from it as a file replica (`-timestamp` works as above; `-o` must not exist yet):

    ```sh
    litestream restore -o /restore/company-brain.sqlite file:///restore/replica
    ```

3. Check it with `PRAGMA integrity_check`, then put it in place as in steps 2 to 5 above (with no host left, at the new host's `DATABASE_PATH` before the app first starts). The data spaces and objects come from the newest daily snapshot.

### Restore drill

A backup is only proven once a restore from it works, so the app tries one on a schedule (CB-111): every `RESTORE_DRILL_INTERVAL_DAYS` (default 30; `0`: only by hand; up to 365) since the last one, as `BACKUP_DIR/restore-drill.json` records it, and again after a day when one failed. An admin changes the interval in **Settings → General → Backup schedule**, and runs one at once with **Run drill now** on Service setup. It needs `LITESTREAM_REPLICA_DIR`, and waits for the replica's first copy. One drill:

1. Restores the latest point, and a random point of the last 14 days (from the replica's oldest snapshot on), from the local replica into scratch files in `BACKUP_DIR/.restore-drill/`.
2. With the off-site copy set up, fetches its newest lineage there as `fetch-ltx` does, and restores its latest point.
3. Checks each with `PRAGMA integrity_check`, in a worker thread, deleting each file once checked.
4. Counts every table's rows in the latest local restore and in the live database, before and after the restore. A table may hold anything between the two live counts (writes since the last replicated transaction); a difference beyond them is reported, and fails the drill only for a missing table or a gross mismatch (over 100 rows and 10% of the table). The off-site restore must have every table too; it may be further behind, so its rows aren't compared.
5. Removes `BACKUP_DIR/.restore-drill/`, failed or not (and at start, after a crash).

Service setup shows `Restore drill: every 30 day(s); the last one passed at <time> in 14 s (latest 3 s, as of <time> 4 s, off-site 7 s); rows match live`, or in red `the last one failed at <time>: …`, which names each step that failed. A failure is logged (`Restore drill failed in 9 s: …`) and every admin is notified, as socios notify people (in the app while they use it, else on the channels they turned on).

**Verify a recovery key (CB-322).** The drill above proves the backups restore with the server's own keys; this proves the escrowed key opens them. On Service setup, an admin pastes the data key from the recovery kit into **Verify a recovery key** (a password field, cleared as it's sent) and selects **Verify**. In the background, the server:

1. Restores the latest point of the local replica into `BACKUP_DIR/.restore-drill-key/` and checks it with `PRAGMA integrity_check`.
2. Picks, per seal purpose, up to 5 seals under the supplied key's id: credentials and secrets from the restored copy's tables; files from its `data_files` rows, their objects read from file storage (the local disk or S3, which the database backup doesn't hold); backups from the off-site copy's newest lineage, when there is one.
3. Opens each with the supplied key alone (never the server's), and counts seals under the legacy key or another data key apart: no data key opens those.
4. Removes the scratch directory and wipes the key from memory (the bytes, and the keys derived from them) as far as JavaScript allows; the request's text is dropped, never stored, logged or echoed.

Service setup then shows `Recovery key check: key 1a2b3c4d5e6f7a8b (the server's current key) passed at <time>: inference credentials 2 of 2 opened, files 5 of 5 opened, backups 5 of 5 opened, …`, a purpose with nothing under that key as `nothing to try`, and in red when a seal didn't open (`failed`) or the restore failed. It passes when at least one purpose opened and none failed. It also says whether the key is the server's current key, its previous key, or neither (an old key whose backups have expired, or the wrong copy). The result is kept in memory until restart, logged (`Recovery key check: key 1a2b3c4d5e6f7a8b (current) passed; opened 14 of 14 sampled seal(s).`) and audited, by key id only. One check runs at a time (`POST /api/backups/verify-key`, admins only), apart from the scheduled drill, whose schedule and `restore-drill.json` it leaves alone. It needs `LITESTREAM_REPLICA_DIR`.

From the command line, inside the app service, `node dist/server/server/backup/backup-cli.js verify-key` (or `pnpm run backup verify-key`) runs the same check with the key from stdin (typed and not shown, or piped), never as an argument. It prints the key's id, a line per purpose (`data-files: 5 of 5 opened`, `push-keys: nothing under this key to try (1 legacy)`) and `Passed.` or `Failed.`, exiting 1 unless it passed. It uses its own scratch directory, `BACKUP_DIR/.restore-drill-key-cli/`, so it doesn't collide with a check the app is running, and it is neither audited nor shown on Service setup.

The drill runs `litestream restore` from the app's own image, which carries the litestream service's release (`COPY --from=litestream/litestream:0.5.17`; a test keeps the Dockerfile's tag and the stack's in step), with nothing of the app's environment but `PATH`. It never runs `replicate`, so the litestream service stays the replica's one writer, and needs no change. `LITESTREAM_BIN` points it at another binary (outside the image, say).

### Schema migrations

The server migrates the database at start, before it opens anything else, and records each step in `schema_migrations` (module, version, name, time, checksum). When anything is pending on a database that already has tables, it first writes a backup to `BACKUP_DIR` as above and logs its path. A database from before migrations were tracked is adopted: each module's baseline whose tables, columns and indexes already exist is marked applied without running. A database migrated by a newer build (a version or module this build doesn't know) stops the server with an error; run the newer build or restore a backup taken before it.

A migration a release shipped never changes: its checksum is in `src/server/modules/released-migrations.json`, and the build fails when the server build gives another (`scripts/released-migrations.mjs`; `pnpm release` records each release's). A schema change is a new migration. A change in form only (formatting) restores the old source or lists the checksum databases recorded in the migration's `formerChecksums`; without one, every start logs "Migration … changed after it was applied", which changes nothing else.

To see what the next start would do, without writing, run `node dist/server/server/modules/migrate-cli.js [file]` (default `DATABASE_PATH`) inside the app service, or `node --import tsx src/server/modules/migrate-cli.ts <copy.sqlite>` on a copy of a backup. Next to it, `node dist/server/server/keys/key-id-cli.js` prints a data key's id from stdin, offline ([Recovery keys](#recovery-keys)).

## Updates

Admins see on **Settings → Platform → Updates** which releases are newer than the running build (CB-259): the version and commit running (`/healthz` and `/api/releases` say the same), each newer release's notes and its `### Upgrading` steps, and the last check. Nobody else sees the card, the feed or its answers: `/api/updates` answers 403 for members, and the settings are kept out of `/api/state`.

**The release feed.** `UPDATES_FEED` (or the card) is `github:<owner>/<repo>` for a repository's GitHub releases, whose body is the release's section of docs/RELEASE-NOTES.md (drafts, pre-releases and tags other than `vX.Y.Z` are left out), or `ghcr:<owner>/<image>` for an image's tags on GHCR, which have no notes, so every release there counts as having steps to read. A private feed needs a read-only token: an operator enters it on the card, where it is sealed under the [data encryption key](#data-encryption-key) for that one feed (changing the feed removes it) and never shown again; `UPDATES_FEED_TOKEN` (`UPDATES_FEED_TOKEN_FILE`, a swarm secret, never stack env text) is used only for the environment's own feed. The token goes only to `api.github.com` or `ghcr.io`, as the Authorization header, and the requests follow no redirects. The app checks every `UPDATES_CHECK_HOURS` (24, an operator can change it on the card; `0` checks only on **Check now**), a failed check again within the hour. A check sends one request to GitHub (two to GHCR) with the User-Agent `update-check/1.0` and nothing about the workspace, its people or the host. Each new newest release notifies the operators once.

**Applying one.** Without `UPDATER_URL` this is notify-only: apply releases through your deployment. With the opt-in updater sidecar (`UPDATER_URL` and `UPDATER_TOKEN`, shared with it) an operator clicks **Update to vX.Y.Z**, confirms the Upgrading steps of every release up to it when there are any (or the feed has none), and then:

1. The app takes a backup through its [backup service](#backups), as configured: `BACKUP_DIR`, and the off-site copy when `BACKUP_S3_ENDPOINT` is set. A failed backup, or a failed off-site copy when one is configured, stops the update with nothing changed.
2. The app hands the updater the tag, the running version and the backup's file names over the internal network, with the shared token. The updater refuses a stale backup, a downgrade and a second update.
3. The updater updates the stack through the Portainer stack API only, keeping its file and every env key and changing only the image tag keys (`UPDATER_TAG_KEYS`, `IMAGE_TAG` by default), after checking the images are on the node.
4. It waits for `/healthz` to report the new version healthy several times in a row, and otherwise puts the previous file and env back and waits for the previous version. It judges the version rather than the tasks, so it works with stop-first and start-first rollouts alike. A rollback that doesn't come back healthy (typically: the new version migrated the database, which the previous image refuses) is reported with the backup to restore.

**The updater's platform.** The updater deploys through a platform port (CB-323): deploy a tag, wait until healthy, roll back. `UPDATER_PLATFORM` on the updater picks the adapter. It is `portainer` by default, and that's the only value so far: anything else stops the updater at start with a message naming the values it accepts. The updater supports Docker Swarm only for now: Portainer today, other platforms later. The `portainer` adapter is steps 3 and 4 above, and its settings are today's: `UPDATER_PORTAINER_URL`, `UPDATER_PORTAINER_TOKEN` (`UPDATER_PORTAINER_TOKEN_FILE`, the adapter's own credential, a Portainer API key), `UPDATER_ENDPOINT_ID`, `UPDATER_PORTAINER_TIMEOUT_SECONDS`, `UPDATER_STACK`, `UPDATER_TAG_KEYS` and `UPDATER_PULL_IMAGE`. The health gate and the job kept in `UPDATER_STATE_DIR` (`/state`) work the same for every platform. The gate polls `UPDATER_HEALTH_URL` (the app's `/healthz` as the updater reaches it, `http://company-brain_app:4310/healthz` by default) every `UPDATER_HEALTH_INTERVAL_SECONDS` (10), needs `UPDATER_HEALTH_STABLE_CHECKS` (3) healthy answers in a row, and gives up after `UPDATER_HEALTH_TIMEOUT_SECONDS` (900). An existing updater needs no change.

**Staleness warning.** When this server falls behind, the card warns and operators get one notice (CB-323). It is only a warning: nothing is applied because of it (`UPDATES_AUTO_APPLY` is the opt-in for that).

- **Behind** means the newest release's date minus the running release's date, in whole days. The dates are the ones the release data already carries: the feed's (a GitHub release's publish date) and, for the running release when the feed doesn't list it, the date in the build's own release notes. A `ghcr:` feed has no dates, so it gets no age warning.
- The warning comes when that's more than `UPDATES_STALE_DAYS` (90). Operators can change it on the card, under **Warn when behind by (days)**, like the other update settings, and **Use the environment's** puts it back. `0` turns the warning off, security releases included.
- A newer release **marked security** warns right away, whatever its date. The marker is `(security)` in the release's summary or highlights, the text before its first `### ` section in docs/RELEASE-NOTES.md (or in its GitHub release title). Being free text, it needs no new section, and the release tooling accepts it as it is. The card shows a **Security** badge on that release.
- **Notices:** each new newest release still notifies operators once. While the server is stale, that notice is the warning (`update_stale`) instead of "available", again once per newer release. If a lower window makes a release already announced stale, the warning comes once on the next check. A new feed starts the notices over.

`UPDATES_AUTO_APPLY` (off; the card's switch) applies, after a check, the newest release reachable through releases whose notes list no Upgrading steps, never past one with steps or without notes, and never a release whose update failed before.

## Development checks

```sh
pnpm run check   # check-format (oxfmt), lint (oxlint) and typecheck (tsc), in parallel
pnpm test
pnpm run build
```

The toolchain is oxc's (CB-311): `oxfmt` formats (`.oxfmtrc.json`; `pnpm run format` writes), `oxlint` lints (`.oxlintrc.json`, with the project's own rules in `scripts/lint/socio-rules.mjs`), and TypeScript 7 (the native compiler) typechecks and emits the server build. Disable a lint rule for one line with `// oxlint-disable-next-line <rule> -- why`. The React Compiler rules are off: only the native app (`apps/mobile`) uses the compiler, and a test guards it there.

Automated tests use service fixtures and fail on any non-loopback network connection. To audit a live run, start the server with `node --import ./scripts/egress-log.mjs --import tsx src/server/index.ts`; every outbound connection is logged to stderr as `[egress] host:port`.
