# Memory: what socios know about a person

Each person has their own context that follows them into every chat with any socio (CB-106): a **profile** they write, and **memories** they add or approve. Both are theirs alone. Paths are relative to `app/`.

## What a person has

- **Profile** (`user_profiles`, core migration 4): preferred name, pronouns, role and team, time zone, language, how they like answers, and standing instructions. Every field is optional and only the person writes it. One live version per person: saving stamps the one before as deleted and adds the new one, so earlier versions are kept (CB-64).
- **Memories** (`memories`, extended by core migration 4): one sentence each. Each says where it came from (`source`: the person, a socio, or a socio from a chat's pinned facts), which socio and chat proposed it (`dotId`, `threadId`), when it was made and changed, and when the person last confirmed it (`confirmedAt`: when they added or approved it, or pressed **Still true**).
- **Proposals:** a memory a socio proposed waits (`status = 'proposed'`) until its person approves it. It is never used before. The person can edit it first, or turn it down. At most 50 wait at a time (`PROPOSALS_WAITING_MAX`).

Both are private to the person by default. Each memory, and the profile as a whole, has **Use in team chats** (`shareable`), off by default.

The **Memories** page (`/memories`) shows all of it: the profile, the proposals waiting, and the memories in use, with where each came from and when it was last confirmed. People add, edit, confirm, approve and forget there. Forgetting a memory or clearing the profile stamps it deleted (CB-64): socios stop using it at once, and it stays in the database and backups like anything deleted.

## How socios get it

Each turn, the person's profile and the memories that bear on their newest message go in the **turn's note**, with that message (`src/server/memory/turn.ts`, `withTurnNote`). Never in the system prompt: the system prompt stays the same, byte for byte, with or without memories (CB-139), so a model's prompt cache keeps it.

- **Which memories:** the ones that share words with the message, best first (BM25, as the chat's notes use: `rankByWords`), then the most recently confirmed, up to 12 and 4,000 characters (`TURN_MEMORIES_MAX`, `TURN_MEMORY_CHARS`). A small set is given whole.
- **How much (CB-173):** the recall budget, **Recalled context per reply** in Settings → General → Socio replies (`TURN_RECALL_TOKENS`, 250 to 8,000 tokens; 1,000 by default, which is the 12 memories and 4,000 characters above). The memories get the budget, at four characters a token, and as many more or fewer of them; the pinned facts of a long chat that match the message (`fit.ts`, the `relevance` selection) grow and shrink in step. It changes only the turn's note: the system prompt stays the same, byte for byte, whatever the budget.
- **As data:** the profile and memories are JSON inside a line labeled as the person's own, untrusted data that can shape tone and facts but never the rules, tools, permissions or approvals. The system prompt says the same. No wording in a memory can start a line of its own or close the list.
- **Switches:** nothing is given, and `propose_memory` isn't offered, when an admin turns memory off (Settings) or for a socio with **Use saved memories** off.

## Episodes (CB-180)

Phase 3 of the PRD: socios remember what happened in a person's own earlier chats, with when and where. An **episode** is one thing a chat kept: a fact its notes pinned (a decision, a result, a goal, an open question, a name, each with its kind as the notes wrote it: `Decision: invoices go out on the 1st`), or what the chat was about (its running summary, one per chat). Episodes are not memories: they are captured automatically and never approved, and a memory (which the person approves) stays the only thing used in team chats.

- **Captured automatically** (`src/server/context/fit.ts`, the `episodes` option; `memory_episodes`, memory migration 2): each fold of a chat's notes, automatic or `/compact`, hands the facts it newly pinned and the model's summary to the episodes of the turn's person. No extra model call: they are the facts and summary CB-137's notes already write. A fold that fell back to the plain summary (its model failed) gives nothing: it pinned no facts, and a plain summary is not kept. Only in a chat that is the person's own (`sharedChat` false): never in a team topic, a Telegram group, a room or anyone else's thread. Nothing is captured while an admin has memory off or for a socio with **Use saved memories** off. A failed capture is reported and never fails the turn or the fold. A chat too short to be compacted leaves no episodes.
- **Per person, per chat, deduplicated:** an episode is its person's (`userId`), with the chat (`threadId`) and socio (`dotId`) it came from. The same fact pinned again in the same chat is the same row, with its newer words and time; a chat's summary is one row that moves on with each fold. `occurredAt` is the time the newest folded turn was told (its time marker), else when it was captured.
- **Recalled, a little each turn:** in a turn of the person's own chat, the episodes of their _other_ chats that share words with their message (BM25, `rankByWords`; never the newest for their own sake) go in the turn's note after the memories, labeled as untrusted data with the day and chat each came from: at most 2 (`TURN_EPISODES_MAX`, more with a bigger budget, 6 at most) within a fifth of the recall budget (`TURN_EPISODE_SHARE`), taken from the memories' share, so the note is no bigger than before. Facts only: the chat summaries are for the tool. The system prompt never carries them, so it stays the same, byte for byte (CB-139). The current chat's own are left out: its notes have them.
- **On demand:** `search_episodes` (a socio tool of the memories module, beside `propose_memory`) searches the person's episodes by words, newest 2,000 ranked (`EPISODES_SEARCHED`), 8 hits by default and 20 at most, each with its kind, day and chat (a chat that is no longer the person's is not named). It leaves out the current chat's. Offered whenever memory is, so the tool list stays the same; in a chat with other people in it, it finds nothing and says why.
- **Seeing and deleting:** **Memories → From your chats** lists the person's episodes, newest first, with the chat and socio each came from and its day, a search box, and **Delete** for one or **Delete all**. Deleting is real: the row is deleted (no soft delete, unlike memories), so socios stop recalling it at once; backups keep it until they age out. The workspace audit gets the episode's id (or `*`, or the chat), never its text.
- **Retention:** an episode is deleted once it hasn't come up (`occurredAt`) for **Keep episodes for** days, Settings → General → Memory (`episodeRetentionDays`, 1 to 3,650; 180 by default, over `EPISODE_RETENTION_DAYS`). The memories module's tick runs it hourly, so only on the leader (CB-108's lease: `Platform.lead()` schedules modules' ticks on the runtime that holds it), up to 20 batches of 1,000 a run, oldest first.

**Isolation (CB-210).** No episode of a private chat reaches a chat with other people in it, whoever acts there: not the turn's note (`personalContext` gives none when `shared`), not `search_episodes` (finds nothing), not `recall` or the prompt (a stored `search_episodes` result is withheld there from everyone, the person who ran it too: `OWN_CHATS_TOOLS` in `room-context.ts`), and not the chat's notes (the shared transcript has no tool result, and the turn note is never stored). A shared chat's folds capture nothing. `tests/episodic-memory.test.ts` holds canaries for each.

## Space memory (CB-181)

Phase 4 of the PRD: what a team knows together, kept per **Space** in a table and governed. Owner's decisions of 2026-10-28: shared memory is scoped to a Space and stored in a table; members and socios **propose**, the Space's **editors approve**; access is checked when an entry is read, every time, against the reader's current Space access. Paths are relative to the repository root.

- **Space access** (`packages/shared/src/space-memory.ts`, `spaceAccessLevel`, the one rule; `src/server/spaces/access.ts`, `SpaceAccess`, loads it, `WorkspaceStore.spaceAccess`): a Space has people with a role, `editor` or `member` (`space_members`, spaces migration 1), and is either open to the whole workspace (the default) or private, read by its people only (`space_settings.membersOnly`). Editors are its `editor` rows and the workspace's admins. A reader is an editor, a member, or, in an open Space, any active person; a deactivated or unknown person, or a Space that is gone, gets nothing. Editors add and remove people, change roles and make the Space private; only workspace admins open one to the whole workspace. Removing someone deletes their row (the workspace audit keeps the change). Private covers everything in the Space, not its memory alone: see **Private Spaces** below.
- **Entries and versions** (`space_memories`, memory migration 3; the Memory context's `SpaceMemoryRepository`, `memory/infra/sqlite/space-memories.ts`): one row per version, with its provenance: who proposed it (`proposedBy`: the person, or the person a socio acted for), the socio (`dotId`) and chat (`threadId`) it came from, who approved or rejected it and when (`decidedBy`, `decidedAt`), who superseded, withdrew or retired it and when (`endedBy`, `endedAt`). An entry's versions share `entryId`; approved ones are numbered from 1, and an entry has one version in use at most. A change names the version it replaces (`supersedes`); approving it supersedes that one, and is refused (409) when another change came first or the entry was retired, so nothing quietly undoes someone else's. The same words (but for case and spaces) in use or waiting add nothing.
- **Proposing** (`src/server/memory/space-memory.ts`, `SpaceMemoryService`): anyone who can read the Space proposes an entry or a change from its **Memory** tab; it waits. A socio proposes with `propose_space_memory` (the memories module's tool, offered whenever `propose_memory` is) for the person it acts for, in a Space it has (`dot_spaces`) that the person can read; Spaces the person can't read are not named. A socio's proposal **always waits for an editor**, whoever the person is: no socio approves anything, and nothing from a person's memories or episodes reaches a Space but through a proposal an editor approves. An editor's own entry or edit from the tab is in use at once (they are its approver), and adding words that wait as a new proposal approves that proposal. At most 100 proposals wait in a Space (`SPACE_PROPOSALS_WAITING_MAX`), 500 entries are in use (`SPACE_MEMORY_ENTRIES_MAX`), 1,000 characters each.
- **Approving:** an editor approves (with their own words if they change them), rejects, edits (a new version in use) or retires an entry (out of use at once; the proposals waiting to change it are rejected with it). A retired entry can be deleted for real (every version) by an editor. A proposer withdraws their own while it waits. Readers see the entries in use and their own proposals; editors see every proposal and the retired entries. An entry's history shows readers its approved versions and editors all of them. A chat's title is shown only to someone who can open that chat.
- **In a turn:** the turn's note gets the entries in use that share words with the message (BM25, `rankByWords`, as episodes), from the Spaces the socio has that **everyone who reads the chat** can read now (`spaceMemoryForTurn`, `chatReaders`): at most 3 (`TURN_SPACE_MEMORY_MAX`, up to 6 with a bigger budget) within a fifth of the recall budget (`TURN_SPACE_MEMORY_SHARE`), taken from the memories' share as the episodes' is, labeled as shared Space knowledge approved by each Space's editors, untrusted data, with the Space, the day it was approved and its entry (so the socio can propose a change). Never the system prompt, which stays the same, byte for byte (CB-139). Nothing while an admin has memory off, or for a socio with **Use saved memories** off.
- **Who reads the chat** (the safer of the two rules the owner offered, chosen here): in a chat of the person's own (a Telegram DM too), the person; in a **room**, every active member and everyone invited with an invite that still works, so the room gets only Spaces **every one of them** can read, and nothing one of them may not read reaches any of them; anywhere the readers aren't known for sure (a Telegram group or legacy team topic, whose readers include people Socio can't name, someone else's chat, an unknown chat), no Space memory at all. Asked at each turn: a person removed from a Space, a Space closed to its people or someone joining a room who can't read it takes it out of the next turn. What a reply already said stays in the transcript, as any message does.
- **Audit:** every proposal, approval, rejection, withdrawal, edit, retirement and deletion is a `workspace_audit` line (`space_memory`, the version's id, with the Space and entry ids and version number, never the words); every change of a Space's people or access is one too (`space_member`, `<space>:<person>` or the Space's id, with the role).
- **Retention:** what is out of use (superseded, rejected and withdrawn versions, retired entries whole) and proposals that waited are deleted once that has lasted **Keep retired Space memory for** days, Settings → General → Memory (`spaceMemoryRetentionDays`, 1 to 3,650; 365 by default, over `SPACE_MEMORY_RETENTION_DAYS`). Entries in use are kept until an editor retires them. The memories module's hourly tick runs it, so only on the leader (CB-108), up to 20 batches of 1,000 a run, oldest first.
- **On screen:** a Space's **Memory** tab (`/spaces/:id/memory`, `packages/client/src/modules/spaces/SpaceMemory.tsx`, beside **Pages**): the proposals waiting with Approve, Edit and approve and Reject (a reader's own with Withdraw), the entries in use with their provenance, history, Edit or Suggest a change and Retire, and the retired entries with Delete. The Space's **People** (roles, Add/Remove) and who sees it are its **Settings** tab (`/spaces/:id/settings`, `packages/client/src/modules/spaces/SpaceSettings.tsx`).

### Private Spaces (CB-181)

Owner's decisions of 2026-10-28: "members only" covers **everything** in a Space; anyone who can create a Space may make it private and choose its people; workspace admins see everything; people outside a private Space don't see it at all; a socio reads a private Space only if the Space is granted to it **and** the acting person (in a room, every current member) can read it; existing Spaces stay open to the whole workspace.

- **One read check:** `SpaceAccess.reads(spaceId, reader)`, asked afresh at every read. A reader is a person (`{ userId }`: people, and service accounts, which are users with a role) or a socio in a chat (`{ dotId, people }`, `WorkspaceStore.socioReader`): the Space granted to it (`dot_spaces`) and every person reading the chat able to read it (`WorkspaceStore.chatReaders`: a private chat's owner, a room's active members and live invites); where Socio can't name the readers (a Telegram group or team topic, `people: null`) only Spaces open to the whole workspace. `canRead`, `require` (a 404 for a Space someone may not read, the words of one that isn't there: `Space not found.`), `readable` and `spacesFor` (the Spaces a person sees, each with `private` and their `access`) are built on it; `WorkspaceStore.readsSpace` and `socioReads` hand it to the modules.
- **What goes through it:** every `/api/spaces/:id/…` page route (list, library, tree, a page, create, edit, delete, move, used, a page's chat) and memory route; `/api/pages/titles` (the palette), `/api/spaces/search` and `/api/pages/:id/location`; the Space list in `/api/workspace` (the sidebar, every Space picker) and the server-rendered library; the socios' page tools (`pageAccess`: list, search, read, create, edit, move, the chat's page context, `unfurl_link` and `insert_dataset_view` through it), `capabilities` (the Spaces it names), `propose_space_memory` and the turn's Space memory; connected agents' `pages:read` tools (`list_spaces`, `list_pages`, `search_pages`, `read_page`); the Ask panel (a page as context, and which socios may answer about it); apps shared with a Space (`AppsService.access`, on every request through the apps proxy, and their open WebSockets closed when the Space's people or access change, `closeSpaceSockets`, to reopen through it; a socio session through the proxy, on every request, also needs the socio to read the Space in the grant's conversation, `socioAccess`, as a socio's `request_app_access` does; the Space's name in app views and the launcher); datasets shared with a Space (`DataSpace.datasetsFor` and `readable`: the Data page, a dataset, its rows, exports and queries; embedded views, `DatasetViews.query`, whose page must be in a Space the viewer reads); link-card images, page covers and pictures, and socios' Space uploads (`/api/media/embeds/:id/content`, by the embed's Space; CB-524). Sharing an app or a dataset, giving a socio a Space, and choosing a Space for a promoted app's data take only Spaces the person reads.
- **Chats about a page** (a page's chat, `page_threads`; an Ask chat about a page, `context_threads`, added by the Ask module through `WorkspaceStore.addChatPages`) are hidden from their own owner while they can't read the page's Space (`chatHidden`): out of the chat lists and runs, and `not_found` from the conversation rule (`WorkspaceStore.access`, `requireOwnedThread`), so their transcript, history and page context are 404s. They come back when the person may read it again. What a socio already said in another chat stays there, as any message does.
- **Nothing leaks:** a socio's `spaceIds` in `/api/workspace` and in a saved socio are only the Spaces the viewer reads (saving keeps the others; giving one they can't read is refused as one that doesn't exist); an app's `sharedSpaceId` and name only for viewers who read it. The change counters watch `space_members` and `space_settings` (`spaces`), so every tab's shell and Space polls see a change of people or access at once. Operations, Learning and the access log stay admin-only, and admins read every Space. Exports and backups are untouched.
- **Making a Space:** `POST /api/spaces` takes `private` (an admin's default is the whole workspace, anyone else's private; a member asking for an open one is a 403) and optional `people` (`userId`, `role`); a private Space and its access are written in one unit of work, with its maker as editor unless they are an admin. **During a deploy** (CB-108) the release before this one would still show a private Space to everyone: each runtime records the `space-privacy` contract (version 1, `runtime_contracts`), and a Space is made private (at creation or later) only while no live runtime records an older one or none; otherwise a 409 says to try again in a few minutes. Opening one waits for nothing. No migration: the tables are spaces migration 1's, and with no `space_settings` row every existing Space stays open to the whole workspace. The route's rule is `createSpaceAs` (`src/server/spaces/create.ts`), which a socio's `create_space` uses too (CB-271, below).
- **A socio making a Space** (CB-271, owner's decision of 2026-10-28): `create_space` (`name`, optional `description`, `visibility`: `private` by default, or `workspace`) proposes one for the person the socio acts for; nothing is made until that person approves the request (`space.create`, `SpaceCreation`): `manualOnly`, so no bypass and no automatic review, ever. The card says its name, its description and who will see it (only its people and workspace admins, or the whole workspace), that the socio gets it, and, from a room, a Telegram group or a team topic, that the socio can't use a private one there. A member's socio makes a private Space only (`workspace` is refused at once, as the route's 403); an admin's, either. Approved, it is checked again (the person's role, a name they now see) and made by `createSpaceAs` as the person, so a member is its editor as from the create dialog, and granted to the socio (`dot_spaces`, the socio's audit records `Space access` by the person) in the same unit of work. The socio then reads it like any grant, through `SpaceAccess.reads`: a private Space in the person's own chat (or a room whose people may all read it), never in a Telegram group or team topic. A socio never makes a second Space with the name of one the person sees (case and spacing aside; a Space hidden from them doesn't count and isn't named), and asking again for the same name while a request waits returns that request. Connected agents have no `create_space`: their only Spaces scope is `pages:read`, and they have no approval card; one would need a new scope and the person's consent flow. Tests: `tests/space-creation.test.ts`.
- **Deleting a Space** (CB-277): `DELETE /api/spaces/:spaceId`, soft (CB-64's `spaces.deletedAt` and `deletedBy`, `WorkspaceStore.deleteSpace`). Who may is `SpaceAccess.requireDeletable`: a private Space's editors, and workspace admins any Space; anyone who can't read it gets the 404 of one that isn't there, a reader (or an editor of a Space for the whole workspace who isn't an admin) a 403. It is refused (409) for the workspace's last live Space and for one a live socio (archived ones too) saves new pages to by default (`dots.spaceId`), naming the socios to an admin and, to anyone else, those they use (`spaceDeleteBlocker`). Nothing in the Space is stamped or changed: its pages and revisions, page and Ask chats, memory, people and access, socio grants (`dot_spaces`) and app, dataset and link-card shares stay as they are. Every reader takes Spaces from `WorkspaceStore.spaces()`, which leaves deleted ones out, so `SpaceAccess.reads` (its `level` finds no Space), `Pages.requireSpace` and everything built on them answer it as missing, on every path above, at once and on every runtime; `tests/spaces-access-matrix.test.ts` checks each for everyone, its editors and admins included. Two paths that didn't ask the Space: a shared computer's reach to a dataset shared with a Space (`DataSpace`, now only while that Space is live), and a socio's saved Spaces, which keep a grant to a deleted Space when the socio is edited (`validateSpaceAccess` accepts grants it already has; a new grant or a default must be live). What stays with its owner stays theirs: their own app, dataset and link-card file. Apps shared with it close their open WebSockets on this runtime (`closeSpaceSockets`, as for a change of people); the change counters watch `spaces`, so every tab's shell sees it. **During a deploy** each runtime records the `space-delete` contract (version 1) and a Space is deleted only while no live runtime records an older one or none (409 otherwise), as for making one private. **Restore** is an admin's (`GET /api/admin/spaces/deleted`, each with who deleted it, when, whether it is private and its live pages; `POST /api/admin/spaces/:spaceId/restore`): it clears the stamp and everything reads again, for the people who could read it; a private one waits for the `space-privacy` contract. Both are in `workspace_audit` (`targetKind` `space`, actions `delete`, detail "private; 3 pages" or "whole workspace; …", and `restore`, "deleted by <id>"). Retention: kept until an admin restores it; nothing purges deleted Spaces (no soft-delete retention exists yet). Socios have no tool to delete a Space. Tests: `tests/space-delete.test.ts`, `packages/client/tests/space-delete-ui.test.tsx`.
- **On screen:** the **+** beside **Spaces** in the sidebar is everyone's; the create dialog asks **Who can see it** (whole workspace, for admins; only its people), saying what private covers. A Space's **Settings** tab has the same choice (a confirmation first) and its people; a member editor sees **Whole workspace** disabled. Those who may delete it find **Delete this Space** last (CB-277): a dialog lists what goes with it and asks for the Space's name; admins restore it under Settings → **Deleted Spaces**. Private Spaces carry a lock (`PrivateSpaceIcon`) in the sidebar and their heading.
- **Tests:** `tests/spaces-access-matrix.test.ts` runs every read path for someone outside the Space, its member, its editor and a workspace admin, and a socio given the Space or not, on an open and a private Space, and checks that a private Space or page is answered word for word as one that isn't there; `packages/client/tests/space-settings-ui.test.tsx` the controls.

## A room's notes and pinned facts (CB-217)

A room's shared context, the room's own and not anyone's memory:

- **Notes:** one set per room, written for everyone (CB-210 above: from a transcript naming each person, with no tool's result) and read by every socio in the room. Each fold is a version (`chat_context_note_versions`, chat migration 9) with the turns it covered, how it was written, and the socio and person whose turn folded it; the newest 20 are kept. A fold is written only while the notes are still the version it started from, so two folds at once never mix. Members see the notes and their versions in the room's **Pinned** panel.
- **Pinned facts:** what the room's people keep in front of its socios, word for word, every turn (`chat_pins`, one row per version, with who pinned, proposed, approved, edited or unpinned it and when). Room admins pin, edit and unpin; a pin's original pinner edits and unpins their own; members propose. At most 30 pins and 6,000 characters together, so they always fit. They go in the turn's note, read afresh each turn and labeled as untrusted data, never the system prompt or the notes at the prompt's start (CB-139).
- **Never private:** a pin's words are typed by a person or taken from the room's own notes' facts (only notes written for everyone). No socio pins anything, so no tool's private result, memory or episode reaches a pin. A room's folds and pins never become anyone's episodes or memories.

## Time zone

Each turn speaks to its acting person in their own time zone (CB-159), so socios never give them times in UTC by default. The zone comes from, in this order (`src/server/memory/time-zone.ts`, `turnTimeZone`):

1. **Their profile's time zone**, when it is a valid IANA name (`America/New_York`).
2. **Their browser's zone** (`Intl.DateTimeFormat().resolvedOptions().timeZone`). The web app sends it with every chat request in the `X-Time-Zone` header (`packages/client/src/modules/chat/copilotkit-options.ts`), never in a message's text. On a run request the server checks it is a real IANA name and saves it to a profile that has no time zone, marked **detected** (`timezoneDetected`, core migration 5), so the person's Telegram, scheduled and job turns get it too. A detected zone follows the browser when it reports another valid zone (CB-176: the person traveled), still detected; another name of the same zone (`Asia/Calcutta` and `Asia/Kolkata`, `Europe/Kiev` and `Europe/Kyiv`, as browsers differ) is no move. It never replaces a time zone the person set themselves, and never makes again a profile the person cleared. Nothing is written while an admin has turned memory off. Saving is best effort: a failed write is logged and never fails the chat. In each of these cases the header's zone is used for that turn only. An invalid zone is ignored. A zone in lower case gets the database's spelling (`america/new_york` becomes `America/New_York`), or, for a link the database doesn't list, the zone it links to (`us/eastern` becomes `America/New_York`).
3. **UTC**, said plainly: the turn's note says the person's zone is not known and asks the socio to say its times are UTC.

The zone is used for every turn whatever the memory switches say: it sets the clock, it isn't a memory.

- **The turn's note** gives the current time in that zone, with the zone named and its UTC offset: `Current time: Thu 22 Oct 2026, 04:46 (America/New_York, UTC−4).` The note comes after the prompt's stable part (CB-139).
- **The system prompt** never carries a zone or a time, so it stays the same, byte for byte, for every person, zone and day. It has one fixed sentence, in the variants with and without tools: speak to people in their local time from the note, translate schedule and job times (stored in UTC) into it, and give both local time and UTC where a schedule's time matters.
- **Time markers** (CB-141, `src/server/context/time-markers.ts`): a new marker states the time in the person's zone, in the same format. Markers are stored word for word, so a marker never changes once written, and markers written before in UTC stay as they were. A new day starts at the person's midnight. When a fold carries the latest marker's time into a long chat's notes, it gives it in the folding turn's zone and stores that zone with the notes (`chat_context_notes.timeZone`, chat migration 6), so the notes stay the same until the next fold; notes folded before keep their UTC wording.
- **Chats with several people** (`sharedChat`: a Telegram group or team topic, and rooms once they land): everyone reads the answers, so the turn uses the sender's zone only when they shared their profile with team chats (**Use in team chats**) and it names a zone. Otherwise the turn's note, new time markers and the notes' time at a fold are all in the workspace's time zone (Operations → time zone, UTC unless an admin set one), and the turn's note tells the socio that it is the workspace's, not the person's (CB-210). The browser's zone is never used there. A marker written while the chat was one person's own is given in UTC there, so a chat opened to others later never shows its owner's zone. Every marker and the notes name their own zone, and the system prompt says so.

**When a detected zone moves (CB-176):** the person is told once, quietly: "Your time zone is now Europe/Madrid (detected from your browser)." The note (`time_zone_notes`, core migration 6, one per person: the latest move) shows once in their next web chat of their own, as a line under the conversation (the run event `socio.time-zone-moved`, only in a turn their browser sent: never in one the server starts, such as an approval's continuation, a job's report or a call, never in Telegram or a chat with other people in it, and never sent to the model), and once on the Memories page, which says when it showed it (`POST /api/memories/time-zone-note/seen`). A note of a zone the person has since changed or set themselves is never shown. Time markers already written keep their words; new ones, and the turn's note, use the new zone.

**Seeing and changing it:** the **Time zone** field of the profile on the **Memories** page. It suggests the zones the browser knows, and a zone the person enters must be a valid IANA name (`PUT /api/memories/profile` refuses anything else with a 400 and stores the name as the time zone database spells it). A zone saved before CB-159 in their own words ("Eastern, mostly") is kept, and the profile can still be saved with it unchanged. Socios don't use it: the browser's zone is used for web turns, and UTC elsewhere. The editor says so until the person picks a zone. A detected zone shows **detected from your browser**, and stays detected when the profile is saved with it unchanged; once the person changes it, it is theirs. Emptying the field lets the next chat request detect it again; to keep UTC, write `UTC`.

## Isolation

- A turn gets only its acting person's profile and memories: the conversation's owner, or the sender in a Telegram chat. Never anyone else's, through any route, tool or turn. Every repository call names the owner.
- **Episodes** (CB-180) are the person's own chats' and are used only in another chat of their own: never in a chat with other people in it, not even the ones they marked for team chats (above).
- **A room's pinned facts and notes** (CB-217) are the room's, read by its members and given to every turn in it; they hold no one's private tool results, memories or episodes (above).
- **Space memory** (CB-181) is not anyone's private context: it is what a Space's editors approved. A turn gets it only from Spaces everyone reading the chat can read now, and none in a chat whose readers Socio can't name (above).
- **A chat with other people** (`sharedChat`): a Telegram team topic, an ordinary Telegram group (its thread is the sender's, but the group reads the replies), or any thread not the person's own. There a turn gets only the memories its person marked for team chats, and the profile only if they marked it. Another person's turn in the same chat gets none of theirs.
- **What else stays the person's there (CB-210).** Each person's message reaches the model after a label Socio writes from the sender the server stamped, `⟦Name wrote:⟧`: every message, alone or merged, and namesakes apart by id (`Alice`, `Alice (2)`, in the order they first wrote, over the whole conversation so a fold doesn't renumber them). A label someone types, in those brackets or ones like them, is their text in plain brackets; a display name can't add a line break, an invisible character or the name `Socio`, which only Socio's own notes get. The turn's note says the chat has other people in it, names who has written by label only (never a profile or an account id), and which of them the turn acts for. The raw result of a tool a turn ran for one person (their computer, data or connections), and an approval's note, which quotes the approved action's result, reach only that person's later turns: anyone else's turns, `recall` and its search get a withheld note with the tool's name and whether it worked, never its text or an error's words (`packages/foundation/src/context/room-context.ts`; the runner stamps whose turn each stored result was, `LocalAgentRunner.toolActors`, from the person its trace says started it). The chat's notes are written for everyone: from a transcript naming each person by label, with no tool's result, and notes or pinned facts kept while the chat was one person's alone are never used there (`chat_context_notes.audience`, chat migration 8): they start over. A result whose turn acted for no known person (a scheduled turn's, or one stored before traces named the person) is no one's to see in a shared chat.

## Proposing a memory

`propose_memory` (a socio tool, `src/server/memory/module.ts`) proposes one sentence for the person acting in the turn. The socio is told to propose only what the person said or confirmed, never secrets, sensitive details or anything about another person, and to tell the person. When the sentence is one of the chat's pinned facts (CB-134's fact store, `chat_context_facts`), the proposal says it came from the chat's notes. Proposing what the person already has adds nothing.

**Asked for, saved at once (CB-172).** When the person explicitly asks their socio to remember something about themselves ("remember I prefer metric units"), the memory is saved at once, with no approval, and the socio's reply links to Memories. It is the person's own (`source = 'person'`), with the socio and the chat they asked in, so the page says "You asked Mingo to remember it in Planning"; they edit or forget it as any other. A socio's word is never enough. It must say so (`asked: true`), and the server checks the person's newest message bears it out (`src/server/memory/asked.ts`): their own words, quoted lines, quoted spans ("…", “…”, «…») and code blocks left out, short (600 characters at most, so a long paste never counts), not handing the socio text to translate or summarize, asking to remember (in English or Spanish: not a question such as "do you remember…", nor "don't remember…"), in the first person, naming no one else ("he", "they", "my boss", "my lovely new team lead", "wife", "mi madre", "mi jefe"…, or a name something is said of: "Bob is…", "Sam hates…", "Bob, who…"), the memory about no one else either ("Their boss…", "Wife loves…", or "Ana is…" when they wrote of Ana), holding most of the memory's words, and saying "not" where the memory does and only there. It must also be a chat turn they started, in a chat of their own (never a team topic or Telegram group, a scheduled, job or voice turn, nor an approval's continuation), and their newest message must be one they typed: a note Socio wrote into the chat (an approval's or a job's, a call's receipt) quotes what a socio wrote, so it never counts. The check is a heuristic: a short paste with none of these marks still reads as the person's own words, and the memory is still only theirs, on Memories to edit or forget. Anything else, what the socio infers or what is about other people, waits for approval as before. Asked for what already waits, the proposal is approved.

## Data access

Memory is a bounded context of the data layer (CB-110, docs/DATA-LAYER.md). It owns `memories`, `user_profiles`, `time_zone_notes`, `memory_episodes` and `space_memories`, and its repositories are the only code that reads or writes them: the interfaces in `src/server/memory/contract.ts`, implemented on Drizzle in `src/server/memory/infra/sqlite/`, on the shared connection and its unit of work. The core store holds them for the platform (`Store.memoryItems`, `Store.profiles`, `Store.timeZoneNotes`, `Store.episodes`, `Store.spaceMemories`); `/api/state` and research tasks read the memories in use through them too. The tables were made by `core` migrations 1 to 6, which stay as they are; their changes go in `src/server/memory/migrations.ts`, whose baseline is adopted over them. Version 2 adds `memory_episodes` (CB-180) and version 3 `space_memories` (CB-181), each expand-only as CB-108's contract asks (`tests/migration-contract.test.ts`), so the build before it runs on the schema it leaves; the core store migrates the set too. A Space's people and access (`space_members`, `space_settings`) are the Spaces module's own (`src/server/spaces/`, spaces migration 1, expand-only), read synchronously by `SpaceAccess` as the rooms' access reads are. `tests/integration/memory-boundary.test.ts` fails on SQL naming these tables anywhere else, and `tests/memory-repositories.test.ts` holds the Drizzle schema to the migrated tables.

## A socio's Soul (CB-179)

Phase 2 of the PRD: each socio has a **Soul**, its persona, kept apart from the person's profile and memories. It is the socio's, not the person's: the same for everyone who chats with it.

- **What it holds** (`packages/shared/src/soul.ts`): role and standing instructions (required, up to 2,000 characters: what the socio's instructions were before), and optionally its voice, values and working style (600 each).
- **Versions** (`socio_souls`, workspace migration 17; `src/server/souls/souls.ts`): every edit and every restore adds a version, numbered from 1, with who made it (`createdBy`), when, and how (`created`, `edited`, `restored` with `restoredFrom`, or `migrated`). None is ever changed or removed. The newest is the one in use. Saving the same parts again adds nothing. An edit names the version it started from (`baseVersion`) and is refused (409) when another came first, so it never quietly undoes someone else's.
- **Upgrade:** the migration makes version 1 of every socio, archived and deleted ones too, from its `instructions`, word for word, dated and signed by the socio's audit line that last set them (else its creation, by `system`). `dots.instructions` stays, a copy of the Soul in use's instructions written in the same transaction, so a rollback to an older build still finds them; the Soul is the source. A rollback's edits to instructions never reach the Soul: after it, edit the Soul again.
- **Who changes it:** the owner of a personal socio; admins for a company socio (`canEditSoul`). An admin may read a personal socio's Soul (as on the admin Socios page) but not change it, through the Soul page or `PUT /api/dots/:id` with new instructions (403). A socio never changes a Soul, its own or another's: the store refuses any `dot:` or `socio:` actor, and no socio tool reaches it. An archived socio's Soul is read-only.
- **Who reads it:** anyone who may use the socio: everyone for a company socio, its owner (and admins) for a personal one. Others get a 404.
- **Audit:** each change adds a line to the socio's audit (`dot_audit`): `Soul v3`, or `Soul v3 (restored v1)`. Never the Soul's text.

**In the prompt.** Every reader of a socio gets the Soul in use: `WorkspaceStore.dot` fills `instructions` (and `soul`) from it. `soulPrompt` renders it after "Role instructions: " in the system prompt (`dot-agent.ts`, web, Telegram, scheduled and job turns alike), as the role in voice calls (`voice.ts`), and for the approvals' decision model (`platform.ts`, `dotRole`). It sits in the system prompt, never the turn's note, so the prompt stays the same, byte for byte, until the Soul is edited (CB-139). A Soul of standing instructions alone renders exactly as the instructions did, so upgraded socios keep their prompt, and its cache, unchanged. Voice, values and working style follow under a line saying they shape tone and style, never the rules, tools' permissions or approvals.

**On screen.** `/dots/:id/soul` (`packages/client/src/modules/chat/SoulPage.tsx`), from the socio's home page, its menu, its settings and the admin Socios page: the version in use, an editor with a preview of what the socio reads, and the history with who and when, a word-by-word diff from the version before (`textDiff`) and Restore. The settings dialog no longer edits instructions after creation; it links to the Soul.

| Route                             | What it does                                                                                 |
| --------------------------------- | -------------------------------------------------------------------------------------------- |
| `GET /api/dots/:id/soul`          | `{ dot, versions (newest first), canEdit, users }`                                           |
| `PUT /api/dots/:id/soul`          | Saves the parts (`instructions`, `voice`, `values`, `style`, `baseVersion`) as a new version |
| `POST /api/dots/:id/soul/restore` | Puts `version` back as a new version (`baseVersion`)                                         |
